## 1. 청중 / 목표 / 코어 thread

- **청중**: 5~15년차 기존 아키텍트 — AI 아키텍트로 책임을 확장 중. 분산 시스템·이벤트드리븐·관측성·운영(SRE) 영역 익숙. LLM/Agent 고유 용어는 풀어줘야 안정.
- **시간**: 2시간 (전환·Q&A 포함)
- **컷오프**: 2026-05 (MCP·A2A·ACP·Skills·Computer Use·Agentic Memory 반영)
- **본 강의 범위 외**: RAG, LLM Gateway (강사 영역 아님)
- **코어 thread (강의 내내 반복)**: `Agent = Loop + Tools + State + Policy` + **"두뇌(LLM) · 손발(Tools/APIs) · 기억(Memory)"**
  - 후자는 §1.5의 트렌드 4번에서 등장한 비즈니스 친화 표현 — 청중이 자기 조직에 가져갈 때 쓰기 좋은 한 줄
- **익숙→낯섦 비유 매핑**:
  - Agent Loop ≈ Reactor pattern (단, dispatcher가 LLM = 비결정적)
  - Tool Use ≈ RPC + JSON Schema
  - MCP ≈ OpenAPI / Service Mesh (의미 표준 + 자기서술)
  - State + Checkpointer ≈ Event Sourcing snapshot
  - Multi-Agent ≈ MSA + 비결정 라우팅
  - HITL ≈ Approval workflow
  - Observability ≈ APM + Distributed Tracing (LLM call이 1 span)
  - **AI 오케스트레이터** ≈ 매니저 / 감독자 (인간이 목표·제약·검증을 맡고 실행은 Agent로)

## 4. 학습 목표 (5)

강의 시작·종료에서 동일하게 보여주는 5개 — 끝나고 수강생이 자기 입으로 설명할 수 있어야.

1. **AI 아키텍트의 책임 영역**을 일반 SW 아키텍트와 비교해 설명, 인간 역할이 **AI 오케스트레이터**로 이동하는 트렌드(T3) 위에서 자기 직무 재정의 (사용자 ①, T3)
2. Agent를 **Loop + Tools + State + Policy** 네 요소(또는 **두뇌·손발·기억**)로 정의하고, 챗봇과의 경계를 판정 (사용자 ②, T4)
3. **Agent 설계 7대 필수 고려요소**(§4.5)를 들이대 자기 조직의 Agent 설계 1차 리스크 식별 (사용자 ⑤ + ③)
4. **Tool/MCP·Reasoning 패턴·State·Multi-Agent**의 의사결정 기준을 영역별 1개씩 들이대 권장안 도출 (사용자 ③)
5. **2026-05 4대 메가트렌드**(T1 Agentic Workflow / T2 표준화 / T3 Teammate / T4 견고성) 중 **자기 조직에 도입할 1~2개**와 그 이유 정리 (사용자 ④)

## 4.5 ★ Agent 설계 6대 필수 고려요소

> **재정제 (강사 권한)**: 사용자 5문제·4트렌드는 원천 아이디어. 통용 설계 원칙(Anthropic *Building effective agents*, OpenAI Agents SDK 가이드, Google A2A 백서, 2026 LLMOps 표준)에 맞춰 **7→6개로 통합**.
> - 기존 P3 "루프·종료 보장"은 **P2 비용·예산**에 흡수 (현실에서는 같은 cap으로 통제)
> - "비결정성"은 단독 원칙이 아니라 **모든 원칙의 공통 배경**으로 처리 → 별도 항목에서 제외, Ch2 정의에서 한 번 짚고 넘어감
> - Ch2 끝 / Ch3 시작에 **로드맵 슬라이드**로 박아 — Ch3·4·5·7이 이 6개를 하나씩 들이대는 구조

| # | 원칙 | 핵심 위험 | 비유 | 다루는 챕터 |
|---|---|---|---|---|
| **P1** | **자율성·통제 균형** (인간 검증 지점 설계) | 책임 경계 모호, 비즈니스 거래에 인간 승인 부재 | Approval workflow | Ch1·Ch5 |
| **P2** | **비용·종료 보장** (max-step·예산 cap·per-trace 회계) | 한 요청이 수십~수백 LLM 호출, 무한루프 | Cloud budget alert + Circuit breaker | Ch4·Ch7 |
| **P3** | **상태·복구** (Checkpointer·재시작·long-running) | 중간 실패 시 처음부터 재실행, 다단계 트랜잭션 | Saga compensation + Event Sourcing snapshot | Ch4 |
| **P4** | **권한·Tool 안전** (Allowlist·Sandbox·Prompt Injection 방어) | Tool 권한 탈취, 결제·DB 변조 | WAF + IAM least-privilege | Ch3·Ch7 |
| **P5** | **관측성·재현성** (Trace/Span·Eval 하니스) | 왜 실패했는지 모름, 동일 입력 다른 결과 | APM + Distributed Tracing + Flaky test 진단 | Ch4·Ch7 |
| **P6** | **표준화·상호운용** (MCP·A2A·ACP) | 벤더·플랫폼 lock-in, N×M 통합 폭발 | Service Mesh + OpenAPI | Ch3·Ch5 |

> 6개 모두 **"기존 SW 아키텍트가 알던 비유 + AI 고유 차이점"**으로 가르친다.
> Ch2가 4요소로 *Agent란 무엇인가*를 답한다면, 이 6원칙은 *Agent를 어떻게 설계하는가*에 답하는 골격.

## 6. 챕터별 상세 (초안)

### Ch1. 왜 AI 아키텍트인가 (15분, 사용자 ① + T1·T3)
**도착점**: AI 아키텍트의 책임이 일반 SW 아키텍트와 무엇이 다른지, T1·T3 트렌드 위에서 자기 직무를 재정의.

**슬라이드 후보 (4)**
- 1.1 일반 SW 아키텍트가 결정하던 것 vs Agent 시대에 새로 결정해야 할 것 — 좌우 대조
- 1.2 **트렌드 인서트 T1**: 단일 모델 → Agentic Workflow ("모델 성능보다 파이프라인 설계")
- 1.3 **트렌드 인서트 T3**: 도구 → 팀원 ("사람의 일은 목표·제약·검증, AI 오케스트레이터")
- 1.4 AI 아키텍트가 들고 다녀야 할 의사결정 카탈로그 한 장 — **6원칙(§4.5)** 로드맵 미리보기

### Ch2. Agent의 구성요소 (15분, 사용자 ②⑤ + T4)
**도착점**: Loop+Tools+State+Policy 4요소(또는 두뇌·손발·기억)로 챗봇 vs Agent 판정.

**슬라이드 후보 (5)**
- 2.1 챗봇 vs Agent 비교표 (입출력·외부 세계·상태·결정)
- 2.2 4요소 정의 (4박스 캔버스)
- 2.3 비즈니스 친화 표현: 두뇌(LLM) · 손발(Tools/APIs) · 기억(Memory) — **트렌드 T4 인서트**

### Ch3. Tool 설계와 MCP (28분, 사용자 ③④⑤ + T2 + P4·P6)
**도착점**: Tool 4요소 의사결정 + MCP 도입 손익분기 + Tool 안전(P4) + 표준화(P6).
