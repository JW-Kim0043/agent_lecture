## C1. 아키텍트의 역할 — 대체가 아니라 확장

**다이어그램**
```
                  아키텍트의 역할은 대체되지 않는다 — 확장된다
                  ──────────────────────────────────────────

   ┌──────────────────── 기존 기존 아키텍트의 책임 (그대로 유지) ────────────────────┐
   │  가용성·확장성  │  비용 최적화   │  관측성(APM)  │  보안·IAM   │  표준·계약   │ SLA │
   │  데이터·일관성  │  트랜잭션      │  리스크 관리  │  거버넌스   │  팀 협업     │ ... │
   └────────────────────────────────────────────────────────────────────────────────────┘
                                          ▲
                                          │   (위 영역은 사라지지 않는다)
                                          │
   ┌──────────────────── + AI Agent 시대에 추가되는 6 영역 ─────────────────────────────┐
   │  P1 자율성·통제 │ P2 비용·종료 │ P3 상태·복구 │ P4 권한·Tool 안전              │
   │  P5 관측·재현    │ P6 표준·상호운용 (MCP·A2A·ACP)                                  │
   └────────────────────────────────────────────────────────────────────────────────────┘

   사람의 위치 변화는 *추가 책임* 한 줄로 압축:
       실행자  ──────────►  AI 오케스트레이터  (T3: Teammate 격상)
       (기존 책임 유지하면서 + 목표·제약·검증 책임이 더해짐)
```
**핵심 표현 (강조)**: 아키텍트의 역할이 **바뀌는 것이 아니라 확장되는 것**.
- 기존 기존 아키텍트의 모든 책임은 *그대로* 유지된다.
- 그 위에 **AI Agent 고유 6 영역(P1~P6)**이 얹힌다.
- 청중은 "내가 알던 게 무용지물이 되는 게 아니다"라는 안도감 + "추가로 6개를 들고 다녀야 한다"는 책임감을 동시에 가져가야.

**기존 비유**: SRE가 알던 *재시도·타임아웃·서킷*이 LLM-level에서 다시 등장. **익숙한 책임 위에 AI 고유 6항목이 얹힌 형태**이지 별개 직무가 아니다.
**핵심 메시지(1줄)**: "**아키텍트는 대체되지 않는다 — 확장될 뿐**. 기존 책임 그대로 + AI 고유 6 영역."
**가이드/슬라이드 동일 표현**: "**확장(Extension), not 대체(Replacement)**"

## C2. Agent 4요소 + 챗봇 vs Agent 판정

**다이어그램**
```
            Agent = Loop + Tools + State + Policy
            ───────────────────────────────────────
                "두뇌(LLM) · 손발(Tools/APIs) · 기억(Memory)"

  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
  │   Loop   │   │  Tools   │   │  State   │   │  Policy  │
  │  (제어)  │   │ (액션)   │   │ (메모리) │   │ (제약)   │
  └──────────┘   └──────────┘   └──────────┘   └──────────┘
   결정 반복      외부세계         trajectory      한계·권한·
                  접근            영속화          중단조건

   비교표
   ┌─────────────┬───────────────┬─────────────────┐
   │             │ 챗봇 / 단일    │ Agent           │
   │             │ LLM 호출       │                 │
   ├─────────────┼───────────────┼─────────────────┤
   │ 입출력      │ 1-shot         │ 반복 Loop       │
   │ 외부 세계   │ 접근 없음      │ Tool 사용       │
   │ 상태        │ 대화 컨텍스트  │ 명시적 State    │
   │ 결정        │ 사용자 지시    │ 자가 결정·계획   │
   └─────────────┴───────────────┴─────────────────┘
```
**핵심 메시지**: 챗봇은 1회 응답으로 종료되고, Agent는 종료 조건에 도달할 때까지 반복한다. 네 가지 요소가 모두 갖춰져야 운영 가능한 Agent로 본다.
**동일 표현**: "Loop + Tools + State + Policy"

## C4. Tool 4요소 + 설계 선택지

**다이어그램**
```
   ┌─────────── Agent ───────────┐
   │   ┌─────┐   ┌─────────────┐ │
   │   │ LLM │──▶│  Policy     │ │  Policy:  허용/거부, 권한, 비용 cap
   │   └─────┘   └──────┬──────┘ │
   │                    ▼        │
   │             ┌─────────────┐ │  Registry: 어떤 도구 N개 있나
   │             │  Registry   │ │            (Schema·설명·태그)
   │             └──────┬──────┘ │
   │                    ▼        │
   │             ┌─────────────┐ │  Executor:  실제 호출
   │             │  Executor   │ │             (재시도·타임아웃·격리)
   │             └──────┬──────┘ │
   │                    ▼        │
   │             ┌─────────────┐ │  Formatter: 결과를 LLM 가독형으로
   │             │  Formatter  │ │             (요약·필드 추림·토큰 제어)
   │             └─────────────┘ │
   └─────────────────────────────┘

   설계 선택지 매트릭스
   ┌───────────┬──────────────────────────────────────────┐
   │ Registry  │ 정적 JSON / 동적 검색 / MCP 자기서술     │
   │ Executor  │ in-process / RPC / Sandbox(VM·Container) │
   │ Formatter │ raw / 요약 / 구조화(field allowlist)     │
   │ Policy    │ pre-call(LLM 전) / mid-call / post-call │
   └───────────┴──────────────────────────────────────────┘
```
**기존 비유**: RPC + JSON Schema. 단, 호출자가 LLM이라 **schema description이 인터페이스**다.
**핵심 메시지(1줄)**: "**Tool은 Schema가 9할**. 4요소를 분리하지 않으면 권한·비용·디버깅이 모두 엉킨다."

## C5. Tool 안전 (P4) — Allowlist · Sandbox · Prompt Injection

**다이어그램**
```
              ┌──────────────────────────────┐
   사용자 ──▶ │  Prompt Injection 방어선 1   │ ← 입력 sanitize + 의도 분류
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
   LLM ────▶  │  Tool Allowlist (Policy)     │ ← 도구 단위 권한·요율 제한
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │  Executor Sandbox            │ ← 격리 (VM/Container/jail)
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │  Output Filter (Formatter)   │ ← 민감정보·exfiltration 차단
              └──────────────────────────────┘

   3-Defense Line :  IN  ──►  TOOL  ──►  OUT
                   인젝션      권한·격리   유출
```
**기존 비유**: WAF(in) + IAM least-privilege(tool) + DLP(out).
**의사결정 기준**: 한 단계만 두면 우회된다 — **3 방어선 중 ≥2 채택**, 결제·DB 변경 도구는 모두 채택 + HITL.
**핵심 메시지(1줄)**: "**Tool 권한은 Schema가 아니라 IAM**. Prompt Injection은 항상 1차 방어선부터."

## C6. MCP 도입 판단 — 통합 비용 구조

**다이어그램**
```
   직접 통합 방식        통합 지점 = N × M

   에이전트 A ──▶ 도구 1, 2, 3, 4
   에이전트 B ──▶ 도구 1, 2, 3, 4
   에이전트 C ──▶ 도구 1, 2, 3, 4
                  (에이전트마다 별도 어댑터 작성)

   MCP 도입 후         통합 지점 = N + M

   에이전트 A ┐
   에이전트 B ┼──▶ MCP 인터페이스 ──▶ 도구 1, 2, 3, 4
   에이전트 C ┘   (도구는 한 번만 MCP 서버로 노출)
```
**MCP 개요**: Anthropic이 2024년 11월에 공개한 *Model Context Protocol*. 에이전트가 외부 도구·자원을 표준 방식으로 발견하고 호출하기 위한 개방형 프로토콜.
**판단 기준** — 정량적 손익분기점은 조직마다 다르므로 정성적 기준을 권장:
- 도구를 여러 에이전트가 공유하는 구조인가
- 외부 벤더 도구를 다수 채택할 계획인가
- 도구가 다른 팀·다른 언어로 개발되는가
위 중 하나 이상 해당하면 MCP 채택을 권장. 단일 팀·단일 언어·도구 5개 미만의 시작 단계 프로젝트는 정적 Registry로 충분.
**핵심 메시지**: 표준화의 가치는 도구 수가 늘어날수록, 또 도구를 만드는 주체가 다양할수록 비선형적으로 커진다.

## C7. 추론 패턴 — 주요 패턴과 선택 기준

**대표 패턴 (논문 발표 시점 기준)**
| 패턴 | 발표 | 한 줄 요약 |
|---|---|---|
| **ReAct** | Yao et al., 2022-10 | 사고(Reasoning)와 행동(Acting)을 한 번의 루프에서 교차 |
| **Reflexion** | Shinn et al., 2023-03 | 실패 경험을 언어로 요약해 다음 시도에 반영 |
| **ReWOO** | Xu et al., 2023-05 | 계획을 먼저 세우고 도구 호출은 일괄 실행 (관찰 분리) |
| **Plan-and-Execute** | LangChain 정식화, 2023 | 장기 작업을 하위 단계로 분해 후 순차 실행 |
| **Reasoning model 통합** | 2024~2025 | OpenAI o-시리즈, Claude의 extended thinking 등 모델이 자가 추론을 내장 |

**선택 기준 (정성적)**
- 작업이 짧고 도구가 적다면 ReAct로 시작
- 도구 호출이 많아 비용이 부담이면 ReWOO 또는 Plan-and-Execute
- 장기·다단계 작업은 Plan-and-Execute
- 고난도 추론이 핵심이고 모델이 reasoning을 지원하면 모델 자체 추론에 위임

**다이어그램**
```
        자율성 ↑ / 비용 ↑

   ReAct  →  Reflexion / ReWOO  →  Plan-and-Execute  →  Reasoning model 통합
   (단순 루프)   (자가 비평·계획 분리)   (장기 작업 분해)     (모델이 자가 추론)
```
**핵심 메시지**: 자율성과 비용은 비례한다. 단순한 패턴에서 시작하고, 작업 특성이 요구할 때 단계적으로 상위 패턴으로 이동한다.

## C8. 비용·종료 보장(P2) + State·복구(P3) — Ch4의 두 원칙 한 장

**다이어그램**
```
   ┌────────── Agent Loop ──────────┐
   │                                │
   │   step++ ─▶ LLM ─▶ Tool ─▶ ... │
   │     │                          │
   │     ▼                          │
   │  ┌─────────── 종료 조건 ────┐ │
   │  │ • max_step ≥ N           │ │   P2: 비용·종료
   │  │ • token_budget 초과       │ │       cap·circuit
   │  │ • wall_clock 초과         │ │
   │  │ • Critic이 충분 판정      │ │
   │  │ • 사용자 종료             │ │
   │  └──────────────────────────┘ │
   └────────────────────────────────┘
              │
              ▼ (각 step 끝마다 snapshot)
   ┌──────── State Store ──────────┐
   │  Checkpointer (Event Sourcing) │   P3: 상태·복구
   │  ┌──────┐ ┌──────┐ ┌──────┐    │       재시작·time-travel
   │  │  s1  │ │  s2  │ │  s3  │... │
   │  └──────┘ └──────┘ └──────┘    │
   │  실패시: 최신 snapshot에서 재개│
   └────────────────────────────────┘
```
**기존 비유**: Cloud Budget Alert + Circuit Breaker (P2) / Saga compensation + Event Sourcing snapshot (P3).
**의사결정 기준**:
- P2: 어떤 cap을 1차 방어선으로 둘지(보통 step + token + wall_clock 셋 다)
- P3: snapshot 주기(매 step / 매 tool call / 매 사용자 입력) — long-running일수록 촘촘
**핵심 메시지(1줄)**: "**종료는 예산이 보장하고, 복구는 snapshot이 보장한다**."

## C9. Memory 3계층 + Trace/Span 관측 모델 (P5)

**다이어그램**
```
   Memory 3계층
   ┌─────────────────────────────────────────────┐
   │  Short-term (Working)        ─ 대화 컨텍스트 │  ← in-memory
   │  Long-term Episodic          ─ 과거 경험 회상│  ← Vector DB
   │  Long-term Semantic·Procedural ─ 지식·절차   │  ← Graph / RDB / KV
   └─────────────────────────────────────────────┘
        ▲                ▲                ▲
        └─ Saga compensation은 Episodic에서, 정책은 Procedural에서

   Trace / Span 관측 모델 (P5)
   Trace = 한 번의 사용자 요청
   ├─ Span: LLM call (latency·tokens·model)
   ├─ Span: Tool call (name·args·result·latency)
   ├─ Span: Memory I/O (read/write·layer)
   └─ Span: HITL gate (approve·reject·edit)

   측정 지표:  loop_depth · tool_success_rate · token_cost
              decision_quality(eval) · time_to_first_byte
```
**기존 비유**: Event Sourcing 의 snapshot + projection (Memory) / Distributed Tracing (Span).
**의사결정 기준**:
- Memory: 워크로드가 *경험 학습형*이면 Episodic 필수, *지식 참조형*이면 Semantic, *반복 절차형*이면 Procedural
- Trace: 모든 LLM/Tool/Memory I/O가 1 span — 빠지면 디버깅 불가
**핵심 메시지(1줄)**: "**State는 snapshot, Memory는 projection, Trace는 LLM-aware APM**."

## C11. 에이전트 간 표준 프로토콜 + HITL 진입점 (P1·P6)

**프로토콜 개요 — 각각 독립된 개방 표준**
| 프로토콜 | 발표 주체 / 시점 | 역할 |
|---|---|---|
| **MCP** (Model Context Protocol) | Anthropic, 2024-11 | 에이전트와 외부 도구·자원 사이의 표준 인터페이스 |
| **A2A** (Agent-to-Agent) | Google, 2025-04 | 에이전트 간 발견·능력 기술·인증·통신 표준 |
| **ACP** (Agent Communication Protocol) | IBM·BeeAI 커뮤니티, 2025 | 에이전트 간 메시지·세션 교환 사양 |

> 세 프로토콜은 OSI처럼 강제 계층 관계는 아니다. 다만 책임 영역이 다르므로 **상호 보완적으로 함께 쓸 수 있다**. 본 강의에서는 이해를 돕기 위한 단순 도식으로만 묶어 표현한다.

**역할 분담 도식 (단순화)**
```
   ┌─────────────────────────────────────────────┐
   │  에이전트 간                                │
   │     ─ A2A : 발견·능력·인증                  │
   │     ─ ACP : 메시지·세션                     │
   ├─────────────────────────────────────────────┤
   │  에이전트 ↔ 도구·자원                       │
   │     ─ MCP : 도구 호출·자원 접근             │
   └─────────────────────────────────────────────┘
```

**HITL 진입점**
```
   사용자 ─▶ Agent Loop ────────────────────────▶ 결과
                │           │            │
           Pre-tool      Mid-loop     Post-output
           (사전 승인)   (중간 검토)   (사후 검토)

           Approve / Edit / Reject — 3 액션 표준
```

**판단 기준**
- 멀티 벤더·외부 에이전트 협업이 필요하면 A2A·ACP 채택. 사내 단일 스택이면 외부 표준 도입은 보류 가능.
- HITL 진입점은 도구 위험도에 따라 1~3개 선택. 결제·발주·데이터 변경 도구는 Pre-tool 검토를 포함하는 것이 권장된다.

**핵심 메시지**: MCP는 *도구* 영역의 표준, A2A·ACP는 *에이전트 간* 영역의 표준이다. HITL의 위치는 도구의 위험도와 회복 가능성으로 결정한다.

## C12. 4 메가트렌드 + 도입 우선순위 매트릭스

**다이어그램**
```
   4 메가트렌드 (2026-05)

   T1 단일모델 → Agentic Workflow         "파이프라인 설계가 경쟁력"
   T2 A2A·MCP 등 표준화                    "표준 위에서만 생태계가 확장"
   T3 도구 → 팀원(Teammate)                "사람은 목표·제약·검증, 실행은 Agent"
   T4 엔터프라이즈 견고성·통제             "답을 잘하는 것을 넘어 거래 안전"

   도입 우선순위 매트릭스
                       조직 성숙도
                       Low      Mid      High
   워크로드  Low      ┌──────┬──────┬──────┐
   위험            ▲ │      │  T2  │  T1  │  ◀ 표준부터 시작
                 Mid │  T2  │ T2/T4│ T1/T2│  ◀ 견고성 더하기
                 Hi  │  T4  │  T4  │ T4/T1│  ◀ 견고성 필수
                     └──────┴──────┴──────┘
   ▶ T3는 모든 셀에 횡단 — 사람의 역할 이동은 단계와 무관
```
**기존 비유**: Gartner Hype Cycle 의 채택 전략 — 위험과 성숙도에 따라 다른 트렌드를 우선.
**의사결정 기준**: 조직 성숙도·워크로드 위험 두 축으로 1~2개만 선택. 4개 다 동시 도입은 실패.
**핵심 메시지(1줄)**: "**트렌드는 따르는 게 아니라 들이대는 것** — 조직 성숙도 × 워크로드 위험."
