## §1. 아키텍트는 대체되지 않는다 — 확장될 뿐 (Ch1)

### 이 챕터에서 답할 질문
- AI 아키텍트는 별개의 직무인가, 기존 아키텍트의 확장인가?
- 일반 기존 아키텍트가 알던 책임 중 **사라지는 것**이 있나?
- AI Agent 시대에 *추가로* 들고 다녀야 할 6 영역은 무엇인가?
- 사람의 역할은 어떻게 이동하나 (Teammate 트렌드)?

### 핵심 표현 — Extension, not Replacement
지난 십여 년간 기존 아키텍트는 가용성·확장성·비용 최적화·관측성·보안·표준·SLA를 다뤄왔습니다. AI Agent가 등장했다고 해서 이 책임들이 사라지지 않습니다. 오히려 그 위에 **AI 고유의 6 영역**이 얹힙니다. 이 강의의 1차 메시지는 이 한 줄입니다.

> **아키텍트의 역할은 바뀌는 것이 아니라 확장되는 것이다.**

청중이 가져가야 할 두 감각이 있습니다. 하나는 *안도감* — 내가 알던 아키텍처 지식이 무용지물이 되지 않는다. 다른 하나는 *책임감* — 그 위에 6개를 새로 들고 다녀야 한다.

### 캔버스 C1 — 확장된 직무

```

   │ 가용성·확장성 │ 비용 최적화 │ 관측성(APM) │ 보안·IAM │ 표준·계약  │
   │ 데이터·일관성 │ 트랜잭션    │ 리스크 관리 │ 거버넌스 │ 팀 협업 ...│
   └────────────────────────────────────────────────────────────────┘

                                  │   (위 영역은 사라지지 않는다)

   │ P1 자율성·통제   P2 비용·종료    P3 상태·복구                  │
   │ P4 권한·Tool 안전 P5 관측·재현  P6 표준·상호운용              │

```

### 트렌드와의 연결 — T1·T3
- **T1 단일 모델 → Agentic Workflow**: 모델 성능 자체보다 *파이프라인 설계*가 경쟁력. 파이프라인 설계는 곧 아키텍트의 일.
- **T3 도구 → 팀원(Teammate)**: 인간은 직접 실행자에서 *AI 오케스트레이터*(목표 정의·제약 설정·검증)로 이동. 이건 직무 박탈이 아니라 *상위 추상으로의 이동*.

### 의사결정 — "왜 별도 직무가 아닌가"
| 질문 | 답 | 이유 |
|---|---|---|
| AI 아키텍트는 새 직무인가? | **아니오** — 확장된 직무 | 기존 책임이 그대로 살아 있음 |
| 일반 SW 아키텍처 지식은 무용한가? | **아니오** — 더 중요해짐 | 6 영역 모두 기존 패턴의 *AI 변종* |
| 일반 아키텍트가 못 다루는 영역은? | 6 영역 중 P5(관측·재현), P6(MCP·A2A) | 새 표준·새 측정 단위 학습 필요 |
| 가장 빠르게 적응할 사람은? | SRE·플랫폼 엔지니어 | "재시도/타임아웃/서킷"이 LLM-level에서 다시 등장 |

### 흔한 함정
1. "AI 아키텍트는 ML 엔지니어다" — ✗. 모델 학습이 아니라 *시스템 설계*.
2. "기존 패턴은 안 통한다" — ✗. 90%는 그대로, 10%가 새것.
3. "AI 도입 = 인력 축소" — ✗. 사람은 더 *상위 추상*으로 이동(오케스트레이터).
4. "한 번에 6 영역 다 챙긴다" — ✗. 워크로드 위험에 따라 *우선순위* 부여.

### 이 챕터의 한 줄
> **아키텍트는 대체되지 않는다 — 확장될 뿐**. 기존 책임 그대로 + AI 고유 6 영역(P1~P6).

- Anthropic, *Building effective agents* (2024-12)
- Google, *A2A whitepaper* (2025)
- McKinsey, *State of AI 2025* — 아키텍트 역할 이동 통계

## §2. 에이전트의 구성 요소 (2장)

### 이 챕터에서 답할 질문
- "AI 에이전트"의 표준 정의가 존재하는가? 주요 출처는 어떻게 정의하는가?
- Workflow와 Agent의 경계는 어디인가? 언제 어느 쪽을 선택해야 하는가?
- 챗봇과 에이전트의 차이는 무엇인가?
- 운영 관점에서 에이전트를 분해하는 4요소는 무엇인가?
- 설계 6원칙이란 무엇이며 본 강의에서 어떻게 사용되는가?

### 권위 있는 정의 — 학계와 산업의 시각
"AI 에이전트"는 단일한 표준 정의가 없습니다. 각 출처가 강조하는 면이 다릅니다.

- **Russell & Norvig** (*Artificial Intelligence: A Modern Approach*, 4판, 2020) — "환경을 인지(센서)하고 그에 작용(액추에이터)하는 모든 것". 함수 `f: P* → A`로 percept-action을 모델링. 합리적 에이전트는 성능 척도 기준 최선의 결과를 추구합니다.
- **Anthropic** (*Building effective agents*, 2024-12) — "LLM이 자신의 프로세스와 도구 사용을 동적으로 지휘하는 시스템" (verbatim). Workflow와 Agent를 자율성 스펙트럼의 양쪽으로 구분합니다.
- **OpenAI** (*A Practical Guide to Building Agents*, 2025) — "사용자를 대신해 다단계 작업을 자율적으로 수행하는 시스템". Agents SDK · Responses API와 함께 정식화. 핵심 구성은 모델·도구·지시(instructions).
- **Google** (*Agents* 백서, Wiesinger 외, 2024-09) — "세상을 관찰하고 도구로 행동하여 목표를 달성하는 시스템". 모델·도구·오케스트레이션 3계층.

세 정의의 공통 요소는 ① 환경·세계와의 상호작용, ② 자율적 의사결정, ③ 다단계 처리입니다. 본 강의의 4요소(Loop·Tools·State·Policy)는 위 정의들과 일관된 **운영 관점의 분해**이며, 강의에서 반복적으로 사용하는 약어입니다.

### Workflow와 Agent — 자율성 스펙트럼
Anthropic의 가이드는 단일 LLM 호출 → Workflow → Agent의 스펙트럼을 제시합니다. **Workflow**는 사전에 정의된 코드 경로로 LLM과 도구를 오케스트레이션하는 시스템이고, **Agent**는 LLM이 흐름을 동적으로 결정하는 시스템입니다.

선택 기준은 다음과 같습니다.

- **Workflow가 적합한 경우** : 작업이 명확하고 단계가 분해 가능, 예측 가능성·일관성이 가치, 비용·지연을 우선 통제하고 싶을 때.
- **Agent가 적합한 경우** : 문제가 열린(open-ended) 형태, 단계 수를 사전에 예측하기 어려움, 고정된 경로를 하드코딩할 수 없는 경우, 모델 판단을 신뢰할 수 있는 환경(샌드박스·가드레일 전제).

가이드는 일관되게 "단순한 해법에서 시작하라"를 권합니다. 단일 LLM 호출 + 검색만으로 충분한 경우가 많고, Agent는 비용·지연·오류 누적 리스크를 함께 가져오기 때문입니다.

### 챗봇과 에이전트의 운영 차이

| | 챗봇 / 단일 LLM 호출 | 에이전트 |
|---|---|---|
| 입출력 | 1회 응답으로 종료 | 종료 조건까지 반복 (Loop) |
| 외부 세계 | 접근 없음 | 도구를 통한 상호작용 |
| 상태 | 대화 컨텍스트에 한정 | 명시적 State 영속화 |
| 다음 행동 | 사용자가 지시 | 자가 결정 (계획·실행·관찰) |

판정 원칙은 "네 요소가 모두 갖춰진 시스템을 운영 가능한 에이전트로 본다"입니다. 빠진 요소가 있다면 그것이 곧 다음 설계 과제가 됩니다.

### 운영 관점의 4요소 — Loop · Tools · State · Policy
- **Loop (제어)** — 판단 → 행동 → 관찰의 반복. 종료 조건에 도달하면 응답을 반환합니다.
- **Tools (행동 수단)** — 외부 시스템과의 상호작용 (API · DB · 검색 · 코드 실행).
- **State (상태)** — 실행 궤적(trajectory)의 영속화. 중단 후 재시작 가능한 형태로 보관.
- **Policy (제약)** — 한도 · 권한 · 중단 조건 (예산 한도, 도구 허용 목록).

비즈니스 표현으로는 **두뇌(LLM) · 손발(Tools/APIs) · 기억(Memory)** 입니다. 임원·고객 대상 보고에서는 후자가 잘 통하고, 설계 회의에서는 전자가 정확합니다. 같은 시스템을 두 어휘로 부르는 것입니다.

### 설계 6원칙 — 강의의 척추
*에이전트란 무엇인가*는 4요소가 답하고, *에이전트를 어떻게 설계하는가*는 6원칙이 답합니다. 본 강의 3장부터 7장까지의 본문이 이 여섯 가지를 하나씩 다룹니다.

| 원칙 | 정의 | 진단 질문 (요구사항 단계) | 대표 산출물 | 다루는 장 |
|---|---|---|---|---|
| **P1 자율성·통제** | 에이전트의 자율 행위와 인간 검증 지점의 균형 | 어떤 행위가 회복 곤란한가 / 누가 승인 권한을 가지나 | HITL 진입점 매트릭스 · 위험도-액션 표 | 5장 · 7장 |
| **P2 비용·종료** | 루프 종료 보장과 요청 단위 비용 한도 | 최악의 입력에서 단계·토큰·시간이 어디까지 가는가 | cap 정의 (step·token·wall_clock) · 알람·자동 차단 | 4장 · 7장 |
| **P3 상태·복구** | 실행 궤적의 영속화와 중단·재개 능력 | RPO는 얼마인가 / 어디서부터 재시작 가능해야 하는가 | 체크포인터 설계 · 직렬화 가능한 State 스키마 | 4장 |
| **P4 권한·안전** | 도구 호출의 인가·격리·입출력 검사 | 신뢰할 수 없는 입력은 어디서 들어오나 / 도구별 권한 범위는 | 허용 목록 · 다층 방어선 · 인젝션 회귀 슈트 | 3장 · 7장 |
| **P5 관측·재현** | 트레이스 기반 진단과 평가(Eval) 가능성 | 실패 1건을 5분 안에 재현 가능한가 / 회귀 슈트 구성은 | Trace/Span 스키마 · Offline Eval · Online Canary | 4장 · 7장 |
| **P6 표준·상호운용** | 도구·에이전트 간 인터페이스 표준화 · 벤더 독립성 | 5년 후 모델·벤더를 바꾸려면 무엇을 다시 짜야 하는가 | MCP·A2A·ACP 채택 정책 · 공급망 다변화 옵션 | 3장 · 5장 |

### 흔한 함정
- "LLM 호출에 도구 하나 붙였으니 에이전트다" — Loop와 명시적 State가 없으면 여전히 단일 호출에 가깝습니다.
- "State는 대화 history면 충분" — 영속화하지 않으면 P3(상태·복구)가 무너집니다.
- "Policy는 나중에" — Tool에 권한이 붙는 순간부터 Policy가 함께 설계되어야 합니다.

### 이 챕터의 정리
> 챗봇은 1회 응답, 에이전트는 Loop. **무엇인가는 4요소, 어떻게 설계하는가는 6원칙**.

## §3. 도구 설계와 MCP (3장)

### 이 챕터에서 답할 질문
- 도구 호출(Function Calling)은 일반 RPC와 무엇이 다른가?
- 도구 4요소(Registry/Executor/Formatter/Policy)를 분리해야 하는 이유는?
- 도구 안전(P4)은 어떤 다층 방어선으로 구성하는가?
- MCP는 언제 도입을 검토해야 하는가? (P6)
- Anthropic의 5+1 패턴 카탈로그 중 도구·워크플로 설계에 어떤 것이 적합한가?

### 패턴 카탈로그 — 단일 LLM 호출에서 시작
처음부터 Agent를 작성하지 말고, 적합한 Workflow 패턴이 있는지 먼저 검토하는 것이 권장됩니다 (Anthropic, *Building effective agents*, 2024-12).

- **① Prompt Chaining** — 한 작업을 여러 호출로 분해, 이전 출력이 다음 호출 입력. 정확도 ↑, 디버깅 용이.
- **② Routing** — 분류기 LLM이 입력을 분류 → 전문화된 후속 프롬프트·모델로 분기. 카테고리별로 비용·정확도를 함께 최적화.
- **③ Parallelization** — Sectioning(독립 하위작업 병렬), Voting(같은 작업 N번 실행 후 합의). 지연 ↓ 또는 신뢰도 ↑.
- **④ Orchestrator – Workers** — 중앙 LLM이 하위 작업을 동적으로 분해, 워커 LLM에 위임 후 종합. 대표 사용 — 코드베이스 다파일 변경.
- **⑤ Evaluator – Optimizer** — 생성기 LLM 출력 → 평가기 LLM이 비평·점수 → 생성기 재시도 (반복). 번역·코드 정합성 향상.
- **⑥ Autonomous Agent** — LLM이 환경 피드백을 받으며 도구를 자율 사용. 단계 수 사전 결정 불가, 인간 체크포인트 선택적. Claude Code · SWE-agent 류.

모든 패턴의 공통 빌딩블록은 **Augmented LLM** (검색·도구·메모리가 결합된 LLM 호출)입니다.

### 도구 호출 = Function Calling — 호출자가 LLM이라는 차이
도구 호출은 본질적으로 RPC + JSON Schema입니다. 다만 **호출자가 사람이 아니라 LLM**이라는 점이 모든 차이를 만듭니다. 사람은 OpenAPI 문서를 읽지 않아도 코드 example로 호출하지만, LLM은 schema의 description을 읽고 호출 여부를 결정합니다. 즉, **description이 LLM 입장에서의 인터페이스**입니다. 도구 description은 충분히 길게 작성하고 호출 예시·반례를 포함하는 것이 권장됩니다.

### 도구 아키텍처 4요소 — 책임 분리
네 가지 구성 요소를 결합하여 설계하면 권한·비용·디버깅이 한 지점에 묶여 변경 주기가 다른 책임을 동시에 다루기 어렵습니다. 분리가 설계의 출발점입니다.

| 요소 | 책임 | 선택지 | 적용 기준 | 부재 시 신호 |
|---|---|---|---|---|
| **Registry** | 사용 가능한 도구의 스키마·설명·태그를 LLM이 검색·참조할 수 있는 형태로 노출 | 정적 JSON · 동적 검색(벡터·태그) · MCP 자기서술 | 도구 ≤20개 · 변경 적음 → 정적 / 100+ → 동적 / 외부 벤더 다수 → MCP | LLM이 엉뚱한 도구 선택, 같은 도구를 다른 이름으로 호출 |
| **Executor** | 함수 호출의 실제 실행 · 재시도·타임아웃·격리·로깅 | 인프로세스 / 원격 RPC(gRPC·HTTP) / Sandbox(컨테이너·VM·jail) | 신뢰 가능한 내부 — 인프로세스 / 외부 시스템 — 원격+회로 차단기 / 코드 실행·신뢰 불가 입력 — Sandbox 필수 | 한 도구 실패가 에이전트 전체를 멈춤, 호출 추적 불가 |
| **Formatter** | 결과를 LLM이 후속 판단에 쓰기 좋은 형태로 변환 · 토큰·민감정보 제어 | raw / 요약 / 필드 화이트리스트 / 구조화된 JSON 추출 | raw — 디버깅·작은 결과 / 요약 — 크고 노이즈 많음 / 화이트리스트 — PII·내부 식별자 차단 | 컨텍스트 윈도우 폭주, 민감정보 응답 노출 |
| **Policy** | 호출 전·중·후의 허용·차단·요율 제한 · 비용·권한·HITL 게이트 | 호출 전(허용 목록·역할) · 호출 중(요율·비용 cap) · 호출 후(출력 검증·로깅) | "기본 거부 후 명시 허용"이 안전 / 고위험 도구 — 인간 승인 결합 | 권한 탈취, 비용 폭주, 감사 추적 부재 |

### 도구 안전(P4) — 다층 방어선
단일 방어선은 우회 가능성이 큽니다. OWASP *LLM Top 10 for Apps* (2025)는 프롬프트 인젝션을 1순위 위협으로 분류합니다. 다음 네 단계 중 ≥2 단계 채택이 베이스라인입니다.

| 단계 | 위치 | 방어 대상 |
|---|---|---|
| ① 입력 검사 | 사용자 입력 단 | 프롬프트 인젝션 · 의도 위조 |
| ② 도구 허용 목록 | LLM ↔ 도구 정책 | 권한 탈취 · 요율 폭주 |
| ③ 격리 실행 | Executor | 코드 실행 · 파일 접근 |
| ④ 출력 필터 | 결과 가공 단 | 민감정보 유출 |

**위험도별 권장** — 읽기·검색은 ①·④, 변경 가능 회복 가능은 두 단계 이상, 결제·발주·삭제 등 회복 곤란 도구는 네 단계 모두 + 사전 인간 승인.

실제 사고 사례 — **EchoLeak (2025)** : Microsoft 365 Copilot에서 이메일 본문에 숨긴 지시로 사내 데이터를 외부로 유출시키는 인젝션. 입력 단계 방어 부재 + 출력 필터 부재가 동시에 발생. **Replit Agent DB 삭제 (2025)** : 에이전트가 운영 데이터베이스를 자율 삭제. 도구 권한 과다와 사전 인간 승인 부재.

### MCP — 도구 통합 표준
**MCP (Model Context Protocol)** 은 Anthropic이 2024년 11월 공개한 개방형 표준으로, 에이전트가 외부 도구·자원을 표준 방식으로 발견하고 호출하기 위한 사양입니다.

직접 통합 방식은 N개 에이전트가 M개 도구를 쓸 때 통합 지점이 *N×M* 만큼 늘어납니다. MCP는 각 도구를 한 번만 MCP 서버로 노출하면 모든 에이전트가 같은 인터페이스로 접근하므로 통합 지점이 *N+M* 으로 떨어집니다.

**도입 검토 기준** (정성적):
- 여러 에이전트가 도구를 공유하는 구조인가
- 외부 벤더 도구를 다수 채택할 계획인가
- 도구가 다른 팀·다른 언어로 개발되는가

위 중 하나 이상 해당하면 MCP 채택을 권장합니다. 단일 팀·단일 언어·도구 5개 미만의 시작 단계 프로젝트는 정적 Registry로 충분합니다.

### 흔한 함정
- "스키마 검증만 잘하면 안전하다" — 검증을 통과한 호출이 권한 밖 작업을 할 수 있음. Policy를 별도로 둘 것.
- "도구 description은 짧게" — LLM이 어떤 도구를 쓸지 판단하지 못함. description은 충분히 길게, 호출 예시·반례 포함.
- "MCP는 작은 조직에 과한 표준" — 도구 수가 적은 시작 단계는 정적 Registry로 충분. 표준의 가치는 도구·에이전트 수가 늘어날수록 비선형으로 커짐.

### 이 챕터의 정리
> 도구 설계는 description이 인터페이스이고, 안전은 단일 방어선이 아닌 다층 구성이며, 표준은 통합 비용이 비선형으로 커지는 시점에 도입합니다.

## §4. 추론 · 상태 · 메모리 (4장)

### 이 챕터에서 답할 질문
- ReAct·ReWOO·Plan-and-Execute·Reflexion·Reasoning model 통합은 언제 무엇을 쓰는가?
- 비용·종료(P2)는 어떤 한도로 보장하는가?
- 상태·복구(P3)의 스냅샷 주기는 어떻게 정하는가?
- 메모리 3계층은 어떤 저장소에 매핑되는가?
- Trace/Span 모델로 무엇을 측정하는가? (P5)

### 추론 패턴 비교 — 정의·시나리오·비용·실패 모드

**ReAct** (Yao 외, 2022) — 매 단계 (사고 → 행동 → 관찰) 루프, 도구 호출과 추론을 교차합니다. 짧은 작업·도구 0~3개·정보 검색+응답에 적합. 디버깅 용이. 긴 작업에서 컨텍스트 폭주·환각 누적 위험. 호출 수는 단계 수와 같으며 지연은 낮음~중간.

**ReWOO** (Xu 외, 2023) — Planner가 전체 도구 호출을 미리 계획 → Worker 일괄 실행 → Solver 종합. 도구 호출이 많고 의존성이 약한 작업, 토큰 비용 통제가 필요한 경우. 호출 단계 절감·병렬화 가능하나 동적 분기에 약하고 계획이 빗나가면 전체 실패.

**Plan-and-Execute** (LangChain 정식화, 2023~) — Planner가 장기 목표를 하위 단계로 분해 → Executor 단계별 실행 → 필요 시 재계획. 장기·다단계 작업, 코드 변경·여행 계획·연구 작업에 적합. 단계 분리로 SLA·비용 통제가 용이하고 부분 재시작이 가능하나, 계획 품질에 결과가 의존하고 재계획 빈도가 높으면 비용이 폭주.

**Reflexion** (Shinn 외, 2023) — 실행 후 별도 LLM이 자가 비평 → 비평을 메모리에 저장 → 다음 시도에 반영. 반복 시도가 가능하고 정답 검증 가능한 코드 생성·문제 풀이에 적합. 정답률 향상·학습 효과가 있으나 시도 N회로 비용·지연 N배가 들고 비평이 잘못되면 발산.

**Reasoning model 통합** (OpenAI o-시리즈, 2024~ · Anthropic extended thinking, 2025~) — 모델 자체가 내부 추론(chain-of-thought)을 수행, 외부에서는 도구 호출만 노출. 고난도 추론·수학·법률·복합 분석에 적합. 외부 루프 단순화·정답률 향상이 강점이나 추론 토큰 비용이 크고 일부 모델은 도구 호출 패턴이 다르며 디버깅이 어려움.

**선택 가이드 (정성적)**
- 짧은 작업·도구 적음 → ReAct
- 도구 호출 비용 부담 → ReWOO 또는 Plan-and-Execute
- 장기·다단계 작업 → Plan-and-Execute
- 고난도 추론이 핵심이고 모델이 reasoning 지원 → 모델 자체에 위임
- 품질 향상이 더 필요할 때 → Reflexion 등 자가 비평 추가

자율성이 높아질수록 비용·지연은 함께 증가합니다. **단순한 패턴에서 시작해 작업 특성이 요구할 때 단계적으로 상위 패턴으로 이동**이 권장됩니다.

### 비용·종료 (P2) — 세 가지 한도의 결합
1차 한도는 단계 수, 토큰, 시간 **세 가지를 모두** 설정합니다. 어느 하나만 두면 다른 두 곳에서 폭주합니다. 요청 단위 비용 회계와 알람을 함께 운영하고, 한도 도달 시 거절(reject)할지 격하(degraded)할지는 워크로드 SLA가 결정합니다.

실제 사례 — **Bing/Sydney 일탈 (2023)** : 장시간 대화에서 모델이 일탈 발화. 종료 조건 부재가 원인 중 하나로 지목됨. 종료 보장은 안전과 비용 모두에 직결됩니다.

### 상태·복구 (P3) — 직렬화와 스냅샷 주기
스냅샷 주기는 작업 시간이 길수록 촘촘하게 설정합니다(매 단계 또는 매 도구 호출). **상태는 반드시 직렬화 가능한 형태**여야 하며, 저장소는 워크로드별로 선택합니다 — 짧고 빈번한 작업은 인메모리·Redis, 오래 보관할 것은 Postgres·S3. 실패 시 최신 스냅샷에서 재개합니다.

### 메모리 3계층 — 저장소 매핑
| 계층 | 내용 | 저장소 후보 |
|---|---|---|
| 단기 메모리 (Working) | 현재 대화의 컨텍스트 | 인메모리 |
| 장기 · 일화 메모리 (Episodic) | 과거 경험 회상 | Vector DB |
| 장기 · 의미·절차 메모리 | 지식 · 절차 | Graph DB · RDB · KV |

**워크로드별 권장**:
- 경험 학습형 → Episodic 필수
- 지식 참조형 → Semantic 중심
- 반복 절차형 → Procedural

### 관측·재현 (P5) — Trace/Span 모델
한 번의 사용자 요청이 1 트레이스를 형성하며, 그 안의 각 작업이 1 스팬으로 기록됩니다. OpenTelemetry GenAI semantic conventions(2024~)는 `gen_ai.*` 속성 표준을 정의하고 있어 LangSmith·LangFuse·Arize Phoenix 등 도구가 모두 호환됩니다.

기록해야 할 스팬:
- **LLM 호출** — 모델·토큰·지연·비용
- **도구 호출** — 이름·인자·결과·지연
- **메모리 입출력** — 계층·키·읽기/쓰기
- **HITL 게이트** — 승인 결과·검토자

주요 측정 지표 — 루프 깊이, 도구 성공률, 요청 단위 토큰 비용, 첫 응답 시간, 의사결정 품질(Eval 하니스).

### 흔한 함정
- "max_step만 두면 충분" — 토큰 폭주를 막지 못함. 세 한도 모두.
- "상태에 LLM 객체를 통째로 저장" — 직렬화가 안 됨. 실행 궤적만 보존.
- "트레이스는 도구를 깔면 끝" — 도구가 아니라 모델. 어떤 스팬을 잡을지부터 설계.

### 이 챕터의 정리
> 상태는 스냅샷, 메모리는 projection, 종료는 예산이 보장합니다. 트레이스는 LLM-aware 관측의 출발점입니다.

## §5. 멀티 에이전트 · A2A · ACP · 사례·Best Practice (5장)

### 이 챕터에서 답할 질문
- HITL 진입점은 어디에 두는가? 검토자에게 무엇을 제공해야 하는가? (P1)
- 단일과 멀티의 경계는 어디인가?
- 토폴로지 4종은 어떤 상황에 적합한가?
- A2A·ACP·MCP는 어떻게 보완 관계를 이루는가? (P6)
- 공개된 에이전트 시스템은 어떻게 설계되어 있는가?
- 공개된 사고는 6원칙의 어느 영역에서 발생했는가?
- 주요 가이드의 권고를 설계·운영에 어떻게 반영하는가?

### 자율성·통제 (P1) — HITL 진입점 운영
인간 검증 진입점은 위치만이 아니라 검토자에게 제공할 정보·SLA·감사 기록·에스컬레이션 정책까지 함께 설계되어야 합니다.

| 진입점 | 트리거 | 검토자 정보 | SLA | 에스컬레이션 | 감사 항목 |
|---|---|---|---|---|---|
| **사전 검토** (Pre-tool) | 위험도 HIGH 도구 호출 직전 | 호출 의도 요약 · 인자 전체 · 영향 범위(레코드·금액) · 회복 가능성 | 초~분 단위 (업무 외 큐잉) | 타임아웃 시 자동 거절 + 별도 채널 알림 | 검토자 ID · 결정 시각 · 변경된 인자 · 사유 |
| **중간 검토** (Mid-loop) | 의도 변경 · 재계획 · 비용 50% 도달 · 외부 입력 수신 | 현재 vs 새 계획 diff · 변경 사유 · 누적 비용·진행률 | 분 단위 (작업 흐름 유지) | 자동 진행 또는 사용자 알림 | 계획 diff · 트리거 이벤트 · 비용 누적 |
| **사후 검토** (Post-output) | 고객 응답 · 외부 게시 · 법적 효력 | 최종 응답 전문 · 근거 인용 · 위험 신호 플래그 | 초 단위 (대기 시간 직접 영향) | 검토 큐로 이전 · 폴백 응답 또는 폐기 | 응답 본문 · diff · 폐기 사유 |

**위험도별 권장** — 위험도 LOW(읽기·검색)는 진입점 없음(자율 실행), MID(변경 가능·회복 가능)는 중간 또는 사후, HIGH(결제·발주·삭제)는 사전 검토 필수 + 사후 검토 권장.

표준 액션은 **Approve / Edit / Reject** 세 가지이며, 모든 HITL 결정은 트레이스에 1 스팬으로 기록되어야 합니다. 거절 시에는 사유와 다음 분기를 명시합니다.

### 단일 vs 멀티 — 토폴로지 4종
복잡도가 낮으면 워크플로(결정적), 중간이면 단일 에이전트 + 도구, 높으면 멀티 에이전트가 적합합니다. Anthropic의 *Building effective agents* 가이드가 이 스펙트럼을 정리하고 있습니다.

| 토폴로지 | 특징 | 비용 | 디버깅 | 적합 상황 |
|---|---|---|---|---|
| Single (도구 풍부) | 단순·빠름 | ↓ | ↑ | 책임 경계 명확, SLA 중요 |
| Supervisor (Router) | 분기 명확·SLA 통제 | 중간 | 중간 | 입력 유형이 다양하나 처리는 분기 가능 |
| Hierarchy (Tree) | 도메인 분리·깊은 위임 | ↑ | ↓ | 도메인이 다양하고 재사용 필요 |
| Network · Swarm | 동등 협력·비결정 강 | ↑↑ | ↓↓ | 본질적으로 동등한 협력이 필요 |

**의사결정 기준** : 책임 경계 명확·SLA 중요 → 단일 또는 Supervisor / 도메인 다양·재사용 → Hierarchy / 동등 협력 필요할 때만 Network. **복잡할수록 멀티가 적합하지만, 책임 경계가 모호해지면 단일로 회귀**가 종종 더 낫습니다.

### 표준 프로토콜 — MCP · A2A · ACP
세 프로토콜은 OSI와 같은 강제 계층 관계가 아닌 **책임 영역이 다른 보완적 표준**입니다.

| 프로토콜 | 발표 | 역할 |
|---|---|---|
| **MCP** (Model Context Protocol) | Anthropic, 2024-11 | 에이전트와 외부 도구·자원 사이의 표준 인터페이스 |
| **A2A** (Agent-to-Agent) | Google, 2025-04 | 에이전트 간 발견·능력 기술·인증·통신 표준 |
| **ACP** (Agent Communication Protocol) | IBM·BeeAI, 2025 | 에이전트 간 메시지·세션 교환 사양 |

**채택 기준** :
- 멀티 벤더·외부 에이전트 협업 → A2A·ACP 채택
- 사내 단일 스택 → 외부 표준 도입은 보류 가능
- 도구 표준화는 MCP부터

### 공개 사례 — 4요소·6원칙으로 분해
| 사례 | 토폴로지 | 주요 도구 | 상태·복구 (P3) | 안전·HITL (P4·P1) |
|---|---|---|---|---|
| **Claude Code** (Anthropic 2025) | 단일 + 도구 풍부 | 파일 R/W · Bash · 검색 · 서브에이전트 | 세션 트랜스크립트 · 토도 영속 | 도구 허용 모드 · 위험 명령 사전 승인 |

### 공개 실패 사례 — 6원칙 위배 관점
- **Air Canada 챗봇 (2024 BC 민사 판례)** — 챗봇이 존재하지 않는 환불 정책 안내 → 항공사 책임 인정. 위배 : P1 위험 응답 검증 부재 + P5 응답 평가 부재.
- **Replit Agent DB 삭제 (2025)** — 에이전트가 운영 DB를 자율 삭제. 위배 : P4 도구 권한 과다 + P1 사전 승인 부재.
- **EchoLeak — Microsoft 365 Copilot (2025)** — 이메일 본문에 숨긴 지시로 사내 데이터 외부 유출. 위배 : P4 입력 단계 인젝션 방어 부재 + 출력 필터 부재.
- **Bing/Sydney 일탈 (2023)** — 장시간 대화에서 모델이 일탈 발화. 위배 : P2 종료 조건 부재 + P5 안전 평가 부재.
- **NYC MyCity 챗봇 (2024)** — 시 운영 챗봇이 임대인에게 위법 행위 권장. 위배 : P5 도메인 평가 부재 + P1 고위험 응답 검증 부재.

대부분의 사고는 **P1 (검증) + P4 (권한·인젝션)** 의 부재에서 발생합니다. 운영 단계 평가(P5)가 있었다면 조기 발견이 가능했을 것입니다.

### Best Practice — 설계·운영의 14건 권고
**설계 단계**
- 단일 LLM 호출과 검색만으로 충분하면 에이전트를 만들지 말 것 (Anthropic)
- Workflow 5패턴 중 적합한 것이 있는지 먼저 검토 (Anthropic)
- 도구 description에 호출 예시·반례를 포함, 비슷한 도구 간 의미 차이 명시 (Anthropic·OpenAI)
- "최악의 입력"을 가정한 프롬프트 인젝션 회귀 슈트 구성 (OWASP LLM Top 10, 2025)
- 에이전트가 사용 가능한 도구·자원의 명시적 화이트리스트 (Google·OpenAI·Anthropic 공통)
- 단계 수·토큰·시간 세 한도 모두 설정 (Anthropic, compounding error 경고)
- 상태는 직렬화 가능한 형태로 영속화하고 재시작 시연 검증 (OpenAI)

**운영 단계**
- 모든 LLM·도구·메모리 입출력을 1 스팬으로 트레이스 (OpenTelemetry GenAI)
- 오프라인 회귀 슈트와 온라인 카나리를 분리하여 운영 (OpenAI·Anthropic)
- 위험도가 높은 도구에는 사전 인간 승인 게이트 필수화 (Anthropic)
- 멀티 에이전트로 가기 전에 단일 에이전트 + 도구로 충분한지 검증 (Anthropic·Cognition)
- 외부 도구·외부 에이전트와 연결 시 표준(MCP·A2A·ACP) 우선 검토 (각 표준 사양)
- 의사결정은 ADR(Architecture Decision Record)로 근거와 함께 문서화 (Bass·Clements·Kazman, *Software Architecture in Practice*)
- 변경·릴리스에 안전 회귀 슈트와 카나리를 모두 통과하는 정책 (Google·OpenAI·Anthropic 공통)

### 흔한 함정
- "복잡하니까 처음부터 멀티" — 디버깅 비용이 폭발. 단일 + 도구로 충분한 경우가 대부분.
- "HITL을 모든 단계에" — 자동화 가치 소실. 위험도 기반 차등 적용이 권장.
- "MCP·A2A·ACP는 같은 것" — 책임 영역이 다른 별개 표준. 한꺼번에 채택하지 말 것.

### 이 챕터의 정리
> MCP는 도구 영역, A2A·ACP는 에이전트 영역의 표준입니다. HITL은 도구 위험도가 정하며, 검증·권한 부재가 사고의 가장 큰 원인입니다.

## §6. 2026년 메가트렌드 (6장)

### 이 챕터에서 답할 질문
- 2026년 상반기 4 메가트렌드는 무엇이며 아키텍처에 어떤 영향을 미치는가?
- 도입 신호는 무엇이고 어떤 표준·도구가 대표적인가?
- 조직 성숙도·워크로드 위험에 따라 어떤 트렌드를 우선해야 하는가?

### 4 메가트렌드 — 영향·신호·사례·대응 원칙
| 트렌드 | 영향 | 도입 신호 | 대표 사례 / 표준 | 대응 원칙 |
|---|---|---|---|---|
| **T1 Agentic Workflow** | 모델 성능보다 파이프라인 설계가 경쟁력 중심 — 특화 에이전트의 단계적 협력 | 단계 분담 가능한 작업 다수 · 모델 비용 부담 · 도메인 전문 프롬프트 분리 필요 | Anthropic 5+1 패턴 · LangGraph · OpenAI Agents SDK | P2 · P5 |
| **T2 개방형 표준화** | 표준 기반 상호운용이 생태계 확장의 전제 — 벤더 종속 회피 | 외부 벤더 도구·에이전트와 연결 필요 · 다중 모델 전략 · 5년 이상 운영 가정 | MCP · A2A · ACP | P6 |
| **T3 도구 → 팀원(Teammate)** | 사람의 역할이 실행자에서 오케스트레이터로 이동 (목표·제약·검증) | 반복·정형 업무 자동화 가능 · 인간 검토자 자원 · 거버넌스 정비 완료 | Claude Code · Devin · Copilot Workspace · Computer Use | 전 영역 횡단 · 특히 P1 |
| **T4 엔터프라이즈 견고성** | 응답 품질을 넘어 거래의 안전·데이터 보안이 필수 — 평가는 운영 인프라 | 금전·법적 영향 거래 포함 · 규제 도메인 (금융·의료·공공) · 보안 사고 경험 | OWASP LLM Top 10 · OpenTelemetry GenAI · LangSmith / LangFuse / Phoenix | P1 · P4 · P5 |

### 도입 우선순위 — 성숙도 × 위험 매트릭스
조직 성숙도(낮음·중간·높음)와 워크로드 위험(낮음·중간·높음)의 9칸 매트릭스에서 **한두 가지만 선택**합니다. 4개를 동시에 도입하는 것은 비용·관리 부담을 증가시킵니다.

| | 성숙도 낮음 | 성숙도 중간 | 성숙도 높음 |
|---|---|---|---|
| 위험 낮음 | — (학습 단계) | T2 | T1 |
| 위험 중간 | T2 | T2 / T4 | T1 / T2 |
| 위험 높음 | T4 | T4 | T4 / T1 |

T3(도구→팀원)는 모든 셀을 횡단하는 변화이며, 단계와 무관합니다.

**적용 가이드** :
- 성숙도와 위험이 모두 낮음 → 우선 학습, 도입 보류
- 위험이 높음 → 무조건 T4(견고성)부터
- 표준 도입(T2) → 어떤 조직에도 진입 장벽이 비교적 낮음

### 흔한 함정
- "트렌드라서 모두 따라간다" — 4개 동시 도입은 실패.
- "성숙도가 낮은데 T1부터" — 워크플로 설계 역량 부재 시 디버깅 부담.
- "T4는 보안팀의 일" — Eval·HITL은 아키텍트의 책임 영역.

### 이 챕터의 정리
> 트렌드 도입은 조직 성숙도 × 워크로드 위험으로 결정합니다. 한두 가지를 선택해 깊이 있게 적용하는 것이 효과적입니다.

## §7. 운영 체크리스트 (7장)

### 이 챕터에서 답할 질문

- HITL의 9칸 운영 매트릭스는 어떻게 구성하는가?

### 6원칙 → 운영 체크 (점검 질문 · 통과 기준 · 증빙)
출시 전 ADR(Architecture Decision Record)에 첨부할 수 있는 형태로 정리합니다.

| 원칙 영역 | 점검 질문 | 통과 기준 | 증빙 |
|---|---|---|---|
| **P1 신뢰성 · HITL** | 위험도 HIGH 도구에 사전 인간 승인 게이트가 있는가 / 실패 시 거절·격하 정책이 명시되어 있는가 | 고위험 도구 100%에 Pre-tool 게이트 / 실패 분기에 fallback 또는 격하 동작 정의 | 도구 위험도 분류표 · HITL 운영 매트릭스 · 실패 시나리오별 Runbook |
| **P2 비용 · 종료** | 요청 단위 단계·토큰·시간 한도가 모두 설정되어 있는가 / 예산 알람·자동 차단이 운영되는가 | 3가지 한도 모두 명시 · 한도 도달 시 거절·격하 동작 정의 · 알람 SLA 정의 | cap 설정 표 · 예산 대시보드 · 차단 정책 문서 |
| **P3 상태 · 복구** | 체크포인터가 동작하는가 / RPO가 정의되어 있는가 / 장애 재시작 시연이 완료되었는가 | RPO 정의 · 시연에서 ≤ RPO 데이터 손실로 재시작 성공 | State 직렬화 스키마 · DR 시연 보고서 · RPO·RTO 표 |
| **P4 보안 · 권한** | 도구 허용 목록·샌드박스가 적용되어 있는가 / 프롬프트 인젝션 방어선 ≥2 단계인가 | 기본 거부 후 명시 허용 정책 · 인젝션 회귀 슈트 차단율 ≥ 합의 기준 | 도구 IAM 정책 · 인젝션 회귀 슈트 결과 · 침투 테스트 보고서 |
| **P5 관측 · 평가** | 모든 LLM·도구·메모리 I/O가 1 스팬으로 기록되는가 / 오프라인 회귀 + 온라인 카나리가 운영되는가 | 트레이스 커버리지 ≥ 합의 기준 · 회귀 + 카나리 통과 후 배포 | OpenTelemetry GenAI 스팬 샘플 · Eval 결과 · 카나리 정책 |
| **P6 표준 · 거버넌스** | MCP·A2A·ACP 채택 정책이 문서화되어 있는가 / 감사 로그·변경 통제가 운영되는가 | 표준 채택 사유와 적용 범위가 ADR로 존재 · 모든 운영 변경에 승인·롤백 절차 | ADR 모음 · 감사 로그 · CAB 회의록 |
| **교차 · HITL 운영** | 진입점 × 액션 매트릭스가 정의되어 있는가 / 검토자 정보·SLA가 정의되어 있는가 | 3 진입점 × 3 액션의 9 셀 모두 정의 · SLA·에스컬레이션·감사 명시 | 5장 HITL 운영 표 · 검토자 가이드 |

### HITL 9칸 매트릭스
3 진입점(사전·중간·사후) × 3 액션(Approve · Edit · Reject) = 9칸 표준. 모든 결정은 트레이스에 1 스팬으로 기록되며, 거절 시 사유와 다음 분기를 명시합니다.

| 진입점 | Approve | Edit | Reject |
|---|---|---|---|
| 사전 검토 (Pre-tool) | 위험 거래 승인 | 인자 수정 | 취소 |
| 중간 검토 (Mid-loop) | 진행 허용 | 계획 수정 | 재계획 |
| 사후 검토 (Post-output) | 배포 | 응답 수정 | 폐기 |

**HITL 과다 = 자동화 가치 소실, HITL 부재 = 비즈니스 사고**. 위험도 기반 차등 적용이 권장됩니다.

### 이 챕터의 정리
> 6원칙을 운영 시점의 점검 질문·통과 기준·증빙으로 환산하여 ADR에 첨부 가능한 형태로 관리합니다.
