## Slide 3 — LLM의 세 가지 구조적 한계
**[화면]**
- 3개 번호 카드
  - 01 Knowledge Cutoff — 학습 시점 이후 데이터 모름
  - 02 Hallucination — 근거 없는 답을 그럴듯하게
  - 03 Private Data 부재 — 사내 문서·DB는 학습 안됨

**[스크립트]**
> RAG가 왜 필요한지부터 이야기해볼게요. LLM은 굉장히 똑똑하지만, 구조적으로 세 가지 한계가 있습니다.
>
> 첫째, **Knowledge Cutoff**. 모델은 특정 시점까지의 데이터로 학습됩니다. 그 이후 일은 몰라요. 예를 들어 어제 발표된 회사 공지를 물어보면 당연히 답을 못 합니다.
>
> 둘째, **Hallucination**, 우리말로 환각이라고 부릅니다. LLM은 "모른다"라고 말하기보다 **그럴듯해 보이는 답을 만들어내는 경향**이 있어요. 법령 조항 번호를 물었는데 존재하지 않는 조항을 그럴듯하게 답하는 식입니다. 아키텍트 입장에서 이건 치명적인 리스크예요.
>
> 셋째, 가장 현실적인 문제인 **Private Data 부재**. 저희 회사의 사내 위키, 계약서, 고객 DB는 OpenAI나 구글이 학습하지 않았습니다. 학습했다면 그게 더 큰 사고죠. 그래서 일반 ChatGPT는 사내 업무에 바로 쓸 수 없는 겁니다.
>
> RAG는 이 세 가지를 **동시에** 완화하는 아키텍처입니다. 어떻게 하냐, 다음 장에서 보겠습니다.

## Slide 3-1 — Knowledge Cutoff 예시 *(신규 예시)*
**[화면]**
- 질문-응답 대조 박스
  ```
  [2024-04 학습 모델에게]
  Q: "2025년 11월 발표된 OpenAI Realtime API 가격은?"
  A: "2024년 4월 이후 정보는 제공할 수 없습니다."
  ```
- 실무 상황 3가지 번호 카드
  - 01 어제 올라온 사내 공지
  - 02 이번주 개정된 개인정보보호법
  - 03 최근 1개월 보안 패치 가이드

**[스크립트]**
> Knowledge Cutoff가 실전에서 어떻게 드러나는지 구체적으로 보여드릴게요.
>
> 화면 위 예시가 전형적인 상황이에요. 2024년 4월까지의 데이터로 학습된 모델에게 2025년 11월에 발표된 API 가격을 물어보면, 잘 설계된 모델은 "모른다"고 답합니다. 여기까진 안전해요.
>
> 문제는 모델이 "모른다"고 정직하게 답하지 않을 때예요. 가격 문의에 **과거 가격**을 최신인 것처럼 답하면, 고객은 잘못된 정보로 의사결정을 하게 됩니다.
>
> 아래 세 가지는 실무에서 정말 자주 부딪히는 상황이에요. 어제 올라온 사내 공지, 이번주 개정된 법령, 최근 보안 패치. 이건 아무리 최신 모델이라도 **학습 시점 이후에 생긴 정보**라서 절대 알 수 없어요.
>
> 핵심 포인트 — Cutoff는 모델을 교체한다고 해결되지 않습니다. 새 모델도 또 다른 Cutoff를 가져요. 이 한계를 구조적으로 푸는 게 **RAG**입니다. 검색 인덱스는 문서가 바뀔 때마다 몇 분 안에 갱신되니까요.

## Slide 3-2 — Hallucination 예시: Avianca 판례 사건 *(신규 예시)*
**[화면]**
- 실제 사건 카드
  ```
  2023년 美 연방법원 · Mata v. Avianca 소송

  • 변호사가 ChatGPT로 판례 조사
  • ChatGPT가 사건명·법원·인용번호까지 포함된
    6개 판례를 상세 인용
      — Varghese v. China Southern Airlines
      — Shaboon v. EgyptAir
      — Petersen v. Iran Air
      — ...
  • 변호사가 그대로 법원에 제출
  • 법원 확인: 6건 전부 존재하지 않음
  • 결과: 벌금 $5,000 + 공개 제재
  ```
- 하단 강조 한 줄: **"'모른다'보다 '그럴듯함'을 선호하는 구조적 경향"**

**[스크립트]**
> Hallucination이 얼마나 심각한 문제인지 유명한 실제 사건으로 보여드릴게요. 2023년 뉴욕의 Mata v. Avianca 사건입니다.
>
> 한 변호사가 항공사 상대 소송을 준비하면서 ChatGPT에게 판례 조사를 시켰어요. ChatGPT는 구체적인 사건명, 법원명, 인용 번호까지 포함된 **6개의 판례**를 굉장히 상세하게 제시했습니다. 변호사는 이걸 검토 없이 그대로 법원에 제출했어요.
>
> 판사가 확인해보니 6건 전부 존재하지 않았어요. 사건명도 가짜, 법원도 가짜, 인용 번호도 가짜. 전부 LLM이 그럴듯하게 조합해 만들어낸 허구였죠. 변호사는 벌금 5,000달러를 물고 전국적 뉴스가 됐습니다.
>
> 왜 이런 일이 생기냐 — LLM은 **"모른다"보다 "그럴듯해 보이는 답"을 선호**하는 구조적 경향이 있어요. 학습 데이터에서 "질문이 있으면 답이 따라온다"는 패턴만 배웠기 때문이에요.
>
> RAG가 이걸 완화합니다. 검색된 **실제 문서**를 근거로 답하게 만들면 오답률이 크게 떨어져요. 하지만 0이 되진 않아요. 그래서 뒤에서 **Faithfulness 평가** — 답변이 진짜로 근거 문서에 기반하는지 검증 — 가 등장하는 겁니다.

## Slide 3-3 — Private Data 부재 예시 *(신규 예시)*
**[화면]**
- 대조 박스
  ```
  [질문] "김영수 부장 남은 연차 며칠인가요?"

  ┌────────────────────────────────┐
  │ ChatGPT (기본)                 │
  │  → "사내 직원 정보는            │
  │     확인할 수 없습니다."        │
  ├────────────────────────────────┤
  │ ChatGPT + 사내 RAG             │
  │  → HR DB 검색 → "남은 연차 7일"│
  └────────────────────────────────┘
  ```
- 경고 박스: **"OpenAI가 사내 DB를 학습했다면 그게 더 큰 보안 사고입니다"**

**[스크립트]**
> Private Data 부재가 왜 "버그가 아니라 설계 결과"인지 예시로 정리할게요.
>
> 사내 챗봇에 "김영수 부장 남은 연차 며칠인가요?"를 물었다고 해봅시다. 기본 ChatGPT는 당연히 "알 수 없다"고 답해요. 이건 **정상 응답**이에요.
>
> 생각해 보세요 — 만약 OpenAI가 우리 회사 HR DB를 학습했다면, **다른 회사 사람도 김 부장 연차를 조회**할 수 있다는 의미입니다. 이건 대형 보안 사고예요. 그러니까 상용 LLM이 여러분 회사 데이터를 모르는 건 **일부러 그렇게 설계된** 겁니다.
>
> 해법이 RAG예요. 사내 HR DB를 검색 인덱스로 연결하면, 질문이 들어왔을 때 관련 정보를 찾아 모델에 주입합니다. 그러면 "남은 연차 7일"을 답할 수 있어요.
>
> 여기서 **아키텍트의 숙제**가 하나 나옵니다. **접근 권한 제어**예요. 신입사원이 "임원 급여 정보"를 물으면 답해선 안 되잖아요. 검색 시점에 사용자별로 볼 수 있는 문서를 필터링하는 구조가 필수입니다. 뒤에서 **메타데이터 태깅**이 중요하게 강조되는 이유가 바로 여기예요.

## Slide 4 — RAG란 정확히 무엇인가 *(신규)*
**[화면]**
- 간단 도식
  ```
  질문 → [검색: 관련 문서 찾기] → [문서 + 질문을 LLM에 같이 전달] → 답변
  ```
- 한 줄: **"외부 지식을 검색해서 LLM에 주입하는 구조"**

**[스크립트]**
> RAG는 Retrieval-Augmented Generation의 약자예요. 직역하면 "검색으로 보강된 생성"입니다. 개념은 단순해요.
>
> 보통 우리가 LLM에 질문하면 모델이 **머릿속에 있는 지식만으로** 답합니다. RAG는 그 중간에 검색 단계를 끼워 넣는 거예요. 질문이 들어오면 먼저 관련 문서를 찾고, 그 문서와 질문을 같이 LLM에 넘깁니다. LLM은 그 문서를 읽고 답을 만들어요.
>
> 비유하자면 **"오픈북 시험"**입니다. LLM이 모든 걸 외우는 게 아니라, 필요할 때 책을 찾아보고 답하는 거죠. 이렇게 하면 앞에서 말한 세 가지 한계가 풀립니다. 최신 문서를 인덱스에 넣으면 cutoff 문제가 해결되고, 근거 문서를 주니까 환각이 줄고, 사내 문서를 검색 대상으로 넣으면 프라이빗 데이터도 활용할 수 있어요.
>
> 오늘 우리가 볼 내용은 이 "검색" 단계와 "주입" 단계를 어떻게 엔터프라이즈 레벨로 설계하느냐입니다.

## Slide 5 — 첫 번째 의사결정: Fine-tuning vs RAG
**[화면]**
- 2열 비교표
  | | Fine-tuning | RAG |
  |---|---|---|
  | 접근 방식 | 모델 자체를 재학습 | 외부 지식을 검색해 주입 |
  | 바꾸는 것 | 모델의 가중치 | 검색 인덱스 |
  | 적합한 문제 | 스타일·톤·형식 | 사실·최신성 |
  | 근거 제시 | 어려움 | 원문 인용 가능 |

**[스크립트]**
> 첫 번째 의사결정을 이야기할 시간이에요. "우리는 파인튜닝을 해야 할까요, RAG를 해야 할까요?" 아키텍트에게 가장 자주 들어오는 질문 중 하나입니다.
>
> 먼저 **파인튜닝**이 뭔지부터 설명드릴게요. 파인튜닝은 **이미 학습된 모델에 우리 회사 데이터를 추가로 학습시키는** 겁니다. 예를 들어 GPT 모델에 한국 회사 고객 상담 대화 1만 건을 더 학습시키면, 모델이 회사 말투와 응대 스타일을 배워요. 즉, **모델의 "뇌"를 바꾸는 방식**입니다.
>
> **RAG는 모델의 뇌를 건드리지 않습니다.** 모델은 그대로 두고, 옆에 "검색 가능한 사내 지식 창고"를 만들어서 질문이 들어올 때마다 필요한 정보를 꺼내다 주는 방식이에요.
>
> 둘의 차이를 쉽게 말하면 이래요. 파인튜닝은 **직원을 교육시키는** 거고, RAG는 **직원에게 매뉴얼을 찾아보게 하는** 거예요. 교육을 시키면 별도로 매뉴얼을 갖다 둘 필요 없이 말투와 센스가 녹아들지만, 매뉴얼이 바뀔 때마다 재교육이 필요합니다. 매뉴얼을 보게 하면 내용이 바뀔 때 매뉴얼만 갱신하면 되죠.
>
> 그래서 **어떤 문제냐에 따라 선택이 달라집니다.** 답변 스타일을 일관되게 만들고 싶다 — 파인튜닝이 유리합니다. 사실 정확성과 최신성이 중요하다 — RAG가 훨씬 유리해요. 근거를 제시해야 한다 — RAG만 가능합니다. 파인튜닝된 모델은 왜 그렇게 답했는지 추적하기가 어려워요.
>
> 다음 장에서 자원 관점에서도 비교해보겠습니다.

## Slide 6 — Fine-tuning vs RAG, 자원·비용·운영 관점 *(신규)*
**[화면]**
- 3행 비교표
  | | Fine-tuning | RAG |
  |---|---|---|
  | 초기 비용 | 학습 GPU · 데이터셋 구축 (수백만~수천만원) | 문서 인덱싱 (수십만원 수준) |
  | 업데이트 | 재학습 (수시간~수일) | 인덱스 갱신 (수분) |
  | 거버넌스 | 모델에 내재 → 삭제·감사 어려움 | 검색 단계에서 필터·권한 제어 가능 |
  | 팀 역량 | ML 엔지니어 필요 | 백엔드·DevOps로 가능 |

**[스크립트]**
> 자원 관점에서 보면 차이가 더 명확해집니다.
>
> **비용 측면**. 파인튜닝은 GPU가 필요하고, 데이터셋을 정제해야 하고, 학습을 돌려야 해요. 웬만한 규모면 수백만 원에서 수천만 원 단위입니다. RAG는 문서를 벡터로 만들어 DB에 넣는 거라 훨씬 저렴해요. 작은 조직에선 한 달 몇십만 원 수준에서도 시작 가능합니다.
>
> **업데이트 속도**. 이게 정말 결정적이에요. 회사 문서가 매주 갱신된다고 생각해보세요. 파인튜닝이면 매주 재학습을 돌려야 합니다. 현실적으로 불가능해요. RAG는 바뀐 문서만 다시 인덱싱하면 되니까 몇 분이면 끝납니다.
>
> **거버넌스**. 이게 엔터프라이즈에서 가장 큰 차이예요. 개인정보가 들어간 문서가 파인튜닝 데이터에 섞여 들어갔다고 생각해보세요. 나중에 "그 정보를 지워주세요"라고 하면, 모델에서 빼낼 방법이 사실상 없어요. 재학습해야 합니다. RAG는 그냥 인덱스에서 해당 문서만 지우면 끝나요. 접근 권한도 검색 시점에 사용자별로 필터링할 수 있습니다. 어떤 팀은 이 문서만 볼 수 있고, 다른 팀은 다른 문서만 볼 수 있게 — 이런 제어가 자연스럽습니다.
>
> **팀 역량**도 다릅니다. 파인튜닝은 ML 엔지니어가 필요해요. RAG는 백엔드 엔지니어와 DevOps로 대부분 커버됩니다. 조직 입장에서 채용·운영 부담이 완전히 다른 레벨이에요.
>

## Slide 7 — 엔터프라이즈 RAG의 5계층
**[화면]**
- 5단 수직 블록 다이어그램 (하단부터)
  ```
  [5] LLM Integration & Response
  [4] Retrieval Pipeline (Hybrid + Rerank)
  [3] Embedding Model
  [2] Chunking & Indexing
  [1] Data Ingestion
  ───────────────────────────
  [0] Governance · Observability · Eval (cross-cutting)
  ```

**[스크립트]**
> 자, 이제 RAG를 아키텍트의 언어로 분해해 볼게요. 프로덕션 RAG는 거의 항상 이 5계층 구조로 수렴합니다. 아래부터 올라갈게요.
>
> **1층 — Data Ingestion**. 원본 문서를 모으고, 파싱하고, 정제하는 단계예요. PDF에서 텍스트를 뽑고, 웹페이지에서 본문만 추출하는 작업입니다.
>
> **2층 — Chunking & Indexing**. 문서를 검색 가능한 조각으로 자르고 인덱스를 만드는 단계예요. 어떻게 자르느냐가 검색 품질을 좌우합니다.
>
> **3층 — Embedding**. 텍스트를 의미가 담긴 숫자 벡터로 바꾸는 단계예요. 이게 벡터 검색의 기반이 됩니다. 나중에 자세히 설명드릴게요.
>
> **4층 — Retrieval**. 실제 검색이 일어나는 곳이에요. 벡터 검색과 키워드 검색을 합치고, 리랭킹도 여기서 합니다.
>
> **5층 — LLM Integration**. 검색된 문서와 질문을 프롬프트로 엮어 LLM에 전달하고 응답을 만드는 단계예요.
>
> 그리고 이 다섯 층을 가로지르는 **0층**이 있습니다. 거버넌스, 관측성, 평가. 이건 어느 한 층의 책임이 아니라 전체에 걸쳐 있어야 해요.
>
> 여기서 아키텍트가 꼭 기억할 포인트는 — **각 층은 독립적으로 교체할 수 있는 서비스 경계**여야 한다는 겁니다. 임베딩 모델을 바꿨는데 검색 로직까지 같이 뜯어고쳐야 한다면, 설계가 잘못된 거예요. 오늘 내내 각 층을 하나씩 확대해서 볼 겁니다.

## Slide 10 — RAG 기본 파이프라인
**[화면]**
- 한 장 다이어그램 (인덱스 타임 + 쿼리 타임)
  ```
  Docs → Parsing → Chunking → Embedding → VectorDB
                                             ▲
  Query → (Rewrite) → Embedding → Hybrid Search → Rerank → LLM
  ```

**[스크립트]**
> 이제 파이프라인 전체를 한 장에 모았습니다. 이 그림이 오늘 세션의 중심이에요.
>
> 위쪽은 **Index Time**, 사전 처리 단계입니다. 서비스를 띄우기 전이나 문서가 갱신될 때 도는 부분이에요. 문서를 가져와서 파싱하고, 잘게 자르고, 벡터로 바꿔서 DB에 넣습니다.
>
> 아래쪽은 **Query Time**, 사용자가 질문했을 때 돌아가는 부분이에요. 질문을 필요하면 다시 쓰고(rewrite), 벡터로 바꾸고, 검색하고, 리랭킹하고, LLM에 전달합니다.
>

## Slide 11 — Parsing: 가장 과소평가되는 계층
**[화면]**
- 2열 카드
  - 좌: 함정 — PDF 레이아웃 파괴, HTML 보일러플레이트, 이미지 OCR
  - 우: 도구 — Unstructured · LlamaParse · Azure Document Intelligence

**[스크립트]**
> 많은 팀이 처음부터 여기서 실패합니다. 제 경험상 RAG 프로젝트가 답을 못 찾는 이유의 상당수는 **파싱 단계에서 이미 정보가 사라져 있기** 때문이에요.
>
> 예를 들어 PDF. 단순 텍스트 추출기로 뽑으면 표가 박살 납니다. 행과 열이 뒤섞여서 순서가 엉망이 돼요. 2단 편집 레이아웃 PDF를 잘못 파싱하면 왼쪽 단과 오른쪽 단이 문장 단위로 섞여서 완전히 다른 내용이 됩니다. 법률 문서나 재무 보고서처럼 표가 핵심 정보인 문서에서는 치명적이에요.
>
> HTML도 조심해야 해요. 크롤링한 페이지 그대로 쓰면 사이드바, 푸터, 광고 텍스트까지 다 들어갑니다. "우리 회사 채용 공고"를 찾는데 전혀 관련 없는 페이지 하단의 "다른 공고 보기" 메뉴가 섞여 검색되는 거죠.
>
> 이미지가 포함된 문서, 예를 들어 스캔된 계약서라면 OCR이 필요하고, 중요한 그림이 많다면 이미지 캡셔닝도 고려해야 합니다.
>
> 도구로는 **Unstructured**, **LlamaParse**, Azure의 **Document Intelligence** 같은 것들이 요즘 많이 쓰여요. PDF가 주력 포맷이라면 이 세 개 정도는 꼭 평가해 보시길 권합니다. 파싱에 돈을 더 쓰는 게 검색 품질 개선에 훨씬 효율적인 경우가 많아요.

## Slide 11-1 — Parsing 정보 손실 시각화 *(신규 · 어떻게 사라지나)*
**[화면]**
- 좌·우 대비 다이어그램 (원본 PDF → 단순 텍스트 추출 결과)
  ```
  [원본 PDF · 표]                   [단순 텍스트 추출]
  ┌──────────────────────┐          연도 항목 매출
  │ 연도 │ 항목  │ 매출  │   ──→    2022 소프트 8천 년 웨어 만
  ├──────┼───────┼───────┤          2023 소프트 1   년 웨어 억
  │ 2022 │ 소프트│ 8천만 │          2024 소프트 1.3 년 웨어 억
  │ 2023 │ 소프트│ 1억   │          → 행·열 경계가 사라짐
  │ 2024 │ 소프트│ 1.3억 │
  └──────────────────────┘

  [원본 PDF · 2단 편집]            [좌·우 단이 뒤섞임]
  ┌──────────┬───────────┐         계약 제1조  계약 제2조
  │ 계약 1조 │ 계약 2조  │         본 계약은   갑은 을에게
  │ 본 계약은│ 갑은 을에게│  ──→   사이의 …    계약금액을 …
  │ 사이의 … │ 계약금액… │         → 두 조항이 한 문장으로 섞임
  └──────────┴───────────┘
  ```

**[스크립트]**
> 앞 슬라이드까지는 도구 비교와 결정 트리였습니다. 이 한 장은 **"왜 그렇게 신중해야 하는가"** 의 시각적 증거예요. 단순 텍스트 추출이 어떻게 정보를 망가뜨리는지 두 케이스로 보여드립니다.
>
> **첫 번째 — 표.** 원본은 깔끔하게 행·열로 정리된 매출 표입니다. 단순 텍스트 추출기로 돌리면 **셀 경계가 사라집니다.** "2022년 소프트웨어 8천만"이 "2022 소프트 8천 년 웨어 만"처럼 토큰 순서가 뒤섞입니다. RAG가 이 청크를 검색해서 LLM에 넘겨도, **답변이 정확할 가능성이 거의 없습니다.** 재무 보고서·제품 스펙·법령 표가 핵심인 도메인에서 치명적입니다.
>
> **두 번째 — 2단 편집.** 계약서나 학술 논문에서 흔한 레이아웃이에요. 단순 추출기는 **읽기 순서를 모릅니다.** 왼쪽 단의 "계약 제1조"와 오른쪽 단의 "계약 제2조"를 한 줄로 합쳐버립니다. **두 조항이 한 문장으로 섞이는** 거예요. 검색 결과의 의미가 완전히 망가집니다.
>
> 핵심 메시지 — **파싱에서 잃은 정보는 RAG 어느 단계에서도 복원되지 않습니다.** 임베딩이 아무리 좋아도, Reranker가 아무리 정확해도, **입력 자체가 망가졌으면 답이 망가집니다.** 그래서 Slide 11에서 "Parsing이 가장 과소평가되는 계층"이라고 못 박는 겁니다. 파싱에 돈을 더 쓰는 게 거의 항상 ROI가 가장 좋은 선택입니다.

## Slide 11-2 — Parsing의 3가지 접근법 *(신규 · 언제 무엇을 쓰나)*
**[화면]**
- 3단 카드 (비용·속도·적합도로 정렬)
  ```
  ┌─ 01 Simple Text Extraction ─────────────────────────┐
  │ 도구   : pdfplumber · PyPDF2 · BeautifulSoup       │
  │ 비용   : ≈ $0                                       │
  │ 속도   : ms 단위                                    │
  │ 한계   : 표 파괴 · 레이아웃 무시 · OCR 없음         │
  │ 적합   : 단일 컬럼 · 깔끔한 텍스트 위주 문서        │
  └──────────────────────────────────────────────────────┘
  ┌─ 02 Layout-aware Parsing ───────────────────────────┐
  │ 도구   : Unstructured · Docling · Marker           │
  │ 비용   : 페이지당 소액 (OSS면 연산 비용만)          │
  │ 속도   : 페이지당 수 초                             │
  │ 강점   : 2단 레이아웃 · 표 구조 · 헤딩 계층 인식    │
  │ 적합   : 일반 기업 문서 (보고서 · 매뉴얼 · 위키)    │
  └──────────────────────────────────────────────────────┘
  ┌─ 03 LLM / Vision-based Parsing ─────────────────────┐
  │ 도구   : LlamaParse · Azure Doc Intelligence ·      │
  │          GPT-4 Vision · Mistral OCR                 │
  │ 비용   : 페이지당 $0.003 ~ $0.03                     │
  │ 속도   : 페이지당 수 초 ~ 수십 초                    │
  │ 강점   : 스캔본 OCR · 복잡 표 · 다이어그램 설명     │
  │ 적합   : 스캔 PDF · 재무제표 · 계약서 · 기술 도면   │
  └──────────────────────────────────────────────────────┘
  ```

**[스크립트]**
> 파싱을 "무조건 잘해야 한다"가 아니라 **"3단계 중 어디를 쓸 것인가"** 로 생각해야 해요. 문서마다 적정선이 다릅니다.
>
> **01 단순 텍스트 추출** — pdfplumber, PyPDF2, BeautifulSoup 같은 전통 라이브러리예요. 비용 거의 0, 속도 ms 단위. 대신 표는 박살 나고 2단 편집이 섞이고 이미지는 무시돼요. **단일 컬럼 깔끔한 텍스트**라면 이걸로 충분합니다. 예를 들어 블로그 글, 사내 메모, 단순 매뉴얼.
>
> **02 Layout-aware 파싱** — Unstructured, Docling, Marker가 대표예요. 내부에 레이아웃 분석 모델이 있어서 **2단 편집, 표 구조, 헤딩 계층**을 인식해요. 비용은 OSS면 연산 비용만, 관리형이면 페이지당 소액. 속도는 페이지당 수 초. **기업에서 만나는 일반 문서의 80%는 여기가 정답**입니다.
>
> **03 LLM/Vision 기반 파싱** — LlamaParse, Azure Document Intelligence, GPT-4 Vision, Mistral OCR. 페이지를 사람처럼 읽어내는 방식이에요. **스캔된 PDF, 복잡한 재무제표, 기술 도면, 이미지 안 텍스트** — 여기서 진가를 발휘해요. 대신 페이지당 $0.003~$0.03 비용이 꼬박꼬박 붙어요.
>
> **아키텍트의 함정** — 품질만 보고 "전부 LlamaParse로 돌리자"가 가장 흔한 실수예요. 문서 10만 건에 페이지당 $0.01만 잡아도 **수백만 원**입니다. 게다가 단순 문서는 단순 도구로도 같은 품질이 나와요. **문서 타입별로 라우팅**하는 게 맞습니다. 다음 슬라이드에서 도구 비교, 그다음에 의사결정 트리로 마무리할게요.

**[스크립트]**
> 2026년 기준으로 실무에서 가장 자주 후보에 오르는 4개를 비교했어요. 벤치마크 근거도 같이 드릴게요.
>
> **Unstructured**. 최근 벤치마크에서 **표 정확도 0.84**로 수위예요. 특히 **"Tokens Added"**(잘못 추가되는 토큰) 비율이 0.027로 가장 낮아서 **Hallucination 방지**에도 유리합니다. 단점은 속도 — 페이지당 수 초가 걸려서 수십만 건 배치엔 부담입니다.
>
> **LlamaParse**. SaaS 기반이라 처리 속도가 문서 크기와 무관하게 **일정하게 약 6초**. 복잡한 표도 구조를 잘 살려요. 자체 OCR도 포함돼 있어서 스캔본도 처리됩니다. 단점은 **데이터 외부 전송** — 규제 산업에서는 첫 질문에서 탈락해요.
>
> **Docling**. IBM이 주도하는 오픈소스. **문서 계층(제목→섹션→하위 섹션)과 메타데이터(페이지 번호·좌표·블록 타입)** 을 가장 잘 보존합니다. 사내 위키, 기술 매뉴얼처럼 **구조 자체가 정보**인 문서에 강해요.
>
> **Marker**. 속도가 최고인 OSS. 단순 구조 문서는 정말 빠르게 처리합니다. 단점은 **복잡한 표에서 셀 분할 오류** — 같은 문서를 Docling에 돌리면 병합 셀을 보존하는데 Marker는 분리해버리는 식이에요.
>
> **실전 조언** — 한 도구로 전체를 처리하려 하지 마세요. "skeleton은 Docling으로, 스캔본만 LlamaParse로, 단순 텍스트는 pdfplumber로" 같은 **하이브리드 파이프라인**이 품질과 비용 둘 다 잡아요. 다음 슬라이드에서 그 라우팅을 어떻게 짜는지 결정 트리로 보겠습니다.

  ```
  문서가 들어왔다
    │
    ├─ Q1. 이미지 스캔본 (텍스트 레이어 없음)?
  ```

**[스크립트]**
> 실무에서 "내 문서엔 뭘 써야 하나?"를 판단할 결정 트리를 준비했어요. 위부터 차례로 체크하세요.
>
> **Q1. 스캔 이미지 PDF인가?** 종이 문서를 스캔한 PDF나 사진 찍은 문서는 텍스트 레이어가 없어요. pdfplumber로 돌리면 0바이트 나옵니다. **OCR이 필수**예요. LlamaParse, Azure Document Intelligence, 최근엔 Mistral OCR 같은 도구를 써야 합니다.
>
> **Q2. 표·그래프가 핵심 정보인가?** 재무 보고서, 제품 스펙, 비교표가 섞인 문서. 이걸 잘못 파싱하면 정보의 절반 이상이 날아가요. **Unstructured(표 정확도 1위)** 나 **Docling(구조 보존 강점)** 을 쓰세요.
>
> **Q3. 복잡한 레이아웃인가?** 2단 편집, 사이드바, 각주, 다단계 헤딩이 섞인 문서. Docling이나 Marker처럼 **레이아웃 인식 모델**이 있는 도구가 필요해요.
>
> **Q4. 위 모두 아니면** 단일 컬럼 깔끔한 텍스트예요. pdfplumber나 Unstructured의 "fast" 모드로 충분합니다. **고급 도구는 과잉 투자**예요.
>
> 마지막 팁 하나 — 파이프라인을 세팅했으면 **랜덤 10페이지를 뽑아 사람이 검수**하세요. 체크리스트: "표 셀이 뒤섞였나?", "문장 순서가 맞나?", "2단이 섞였나?", "이미지 설명이 빠졌나?". 이 단순한 품질 검증 한 번이 **나중에 RAG 디버깅 시간 며칠을 아껴줍니다.** 파싱에서 놓친 정보는 아무리 뛰어난 검색·생성으로도 복원 안 돼요.

## Slide 12 — Chunking 4 전략
**[화면]**
- 표
  | 전략 | 설명 | 노트 |
  |---|---|---|
  | Fixed-size | N 토큰씩 자름 | 저렴·단순, 문맥 파괴 |
  | Recursive | 단락→문장→단어 계층 | 기본 권장 |
  | Semantic | 의미 유사도 경계 | recall↑, 비용↑ |
  | Document-aware | MD·코드·표 구조 활용 | 구조적 문서에 강함 |

**[스크립트]**
> Chunking이라는 단어가 생소하실 수 있어요. 우리말로는 "문서를 검색용 조각으로 자르기" 정도로 이해하시면 됩니다.
>
> 왜 자르냐고요? LLM은 한 번에 읽을 수 있는 글자 수가 제한돼 있고, 벡터 검색도 너무 큰 문서를 통째로 비교하면 의미 해상도가 떨어져요. 그래서 책 한 권을 그대로 넣는 게 아니라, 몇 페이지씩 잘라서 넣습니다.
>
> 자르는 방법이 네 가지가 있어요.
>
> **Fixed-size**는 가장 단순합니다. 그냥 500토큰씩, 1000토큰씩 같은 크기로 자르는 거예요. 구현이 쉽지만 문장이 중간에 끊기고, 문맥이 깨집니다. "김 대리가 어제 제출한" / "보고서에는 매출이 10% 증가" — 이렇게 잘려버리는 거죠.
>
> **Recursive**는 현업에서 가장 많이 쓰이는 기본값입니다. 먼저 단락 단위로 자르고, 그래도 크면 문장 단위로, 또 크면 단어 단위로 — 이런 식으로 계층적으로 내려가요. 덕분에 문장이 중간에 끊기는 일이 거의 없습니다. LangChain의 `RecursiveCharacterTextSplitter`가 이 방식이에요. Recall 기준으로 대략 85~90% 수준이 나오고, 구현도 간단해서 출발점으로 가장 추천해요.
>
> **Semantic**은 더 똑똑하게 자릅니다. 문장들을 일일이 임베딩해서 의미가 달라지는 지점에서 끊어요. 재현율이 2~3%p 정도 올라가긴 하는데, 모든 문장을 임베딩해야 해서 인덱싱 비용이 커집니다.
>
> **Document-aware**는 문서 구조를 활용하는 방식이에요. 마크다운이면 헤딩 단위로, 코드면 함수 단위로, 표면 행 단위로 자릅니다. 구조화된 문서에 쓰면 정말 효과적이에요.
>
> 저는 항상 이 조언을 드려요. **RAG 품질이 기대만큼 안 나올 때 사람들이 제일 안 건드리는 게 chunking인데, 사실 여기가 지렛대가 가장 큽니다.** 임베딩 모델 바꾸는 것보다 chunking을 다시 설계하는 게 대부분 더 효과적이에요.

## Slide 12-1 — 문서 타입별 Chunking 매칭 *(신규 · 무엇을 무엇으로)*
**[화면]**
- 매칭 표 (타입 × 전략 × 이유)
  ```
  ┌──────────────────┬──────────────────┬─────────────────────┐
  │ 문서 타입        │ 추천 Chunking    │ 이유                │
  ├──────────────────┼──────────────────┼─────────────────────┤
  │ Markdown · HTML  │ Header-based     │ H1/H2 = 완결 아이디어│
  │                  │ + Recursive      │ 구조가 이미 경계     │
  ├──────────────────┼──────────────────┼─────────────────────┤
  │ 소스 코드         │ AST Function-    │ 함수 단위 = 논리 단위│
  │                  │ aware            │ 함수 중간 자르면 맥락│
  │                  │                  │ 상실                │
  ├──────────────────┼──────────────────┼─────────────────────┤
  │ 계약 · 법령       │ Clause-based    │ 조항 단위 인용 필수  │
  │                  │ (Parent-Child)   │ 작은 조항으로 검색, │
  │                  │                  │ 주변 조항으로 컨텍스트│
  ├──────────────────┼──────────────────┼─────────────────────┤
  │ FAQ · API 문서   │ Entry-based      │ Q&A·Endpoint는      │
  │                  │                  │ 쪼개면 의미 손상    │
  ├──────────────────┼──────────────────┼─────────────────────┤
  │ 장문 리포트·에세이 │ Recursive 512    │ 벤치마크 1위 (69%)   │
  │                  │ + 선택적 Semantic│ 대부분의 기본값     │
  ├──────────────────┼──────────────────┼─────────────────────┤
  │ 표 · Excel 시트  │ Row-based or     │ 각 행이 독립 의미    │
  │                  │ Table Summary    │ 큰 표는 요약 + 상세  │
  └──────────────────┴──────────────────┴─────────────────────┘
  ```
- 하단: **"한 가지 전략으로 모든 문서를 처리하지 마세요 — Hybrid Chunking이 2026 표준"**

**[스크립트]**
> 4가지 전략을 배웠으니, 이제 **"어떤 문서엔 어떤 전략"** 을 구체적으로 매칭해 볼게요. 실전에서 만나는 6가지 타입별로 정리했어요.
>
> **Markdown·HTML**. 이미 구조가 있어요. H1·H2·H3를 자연 경계로 쓰고, 섹션이 너무 크면 안에서 Recursive로 한 번 더 자릅니다. "Header-based + Recursive" 조합이 가장 깔끔해요. 사내 위키, 기술 블로그가 여기예요.
>
> **소스 코드**. 함수·클래스 단위가 **논리 단위**예요. 파이썬 AST나 Tree-sitter로 파싱해서 함수 경계로 자릅니다. 한 함수를 중간에 자르면 LLM이 맥락을 완전히 잃어요. "이 함수 뭐 하는 거지?" 질문에 절반만 보이면 답할 수 없어요.
>
> **계약·법령**. "§14조 2항"처럼 **조항 단위 인용**이 필수예요. Clause로 자르되, 조항만 있으면 문맥이 부족한 경우가 많아서 **Parent-Child Chunking**을 많이 씁니다. **검색은 작은 조항(Child)** 으로, **컨텍스트 제공은 주변 조항 포함(Parent)** 으로. 법률 RAG의 핵심 패턴이에요.
>
> **FAQ·API 문서**. Q&A 쌍 하나나 API endpoint 하나가 **한 청크**여야 해요. 질문과 답을 분리하면 질문만 매칭됐을 때 답이 다른 청크에 있어서 못 찾아요. endpoint 중간을 자르면 파라미터 절반만 보이니까 틀린 답이 나오고요.
>
> **장문 리포트·에세이**. 구조가 약하고 텍스트가 흐르는 문서 — 이게 가장 흔한 케이스인데 **Recursive 512 토큰**이 2026년 Vectara 벤치마크 1위(69% 정확도)였어요. 이 값으로 출발하고, 필요하면 Semantic을 실험하되 **비용 대비 이득이 적을 수 있다**는 건 인지하고 가세요.
>
> **표·Excel**. 각 행이 독립된 의미예요. 행 단위로 자르거나, 큰 표는 **요약문**을 하나 만들고 그 아래 상세 데이터를 매달아둡니다.
>
> 핵심 메시지 — **한 가지 전략으로 모든 문서를 처리하지 마세요.** 2026년 프로덕션 RAG의 특징이 **Hybrid Chunking**이에요. 문서 타입을 먼저 분류하고 각자 맞는 전략으로 라우팅하는 구조입니다.

## Slide 12-2 — Chunk 크기·Overlap 튜닝 프로세스 *(신규 · 어떻게 고르나)*
**[화면]**
- 4단계 프로세스 다이어그램
  ```
  Step 1 — 기본값으로 출발
    ├─ Chunk    : 512 tokens
    ├─ Overlap  : 10~25% (51~128 tokens)
    └─ 전략     : Recursive
         ↓
  Step 2 — Golden Dataset 베이스라인 측정
    └─ Recall@5 · MRR · nDCG 값 기록
         ↓
  Step 3 — 변수 하나씩 변경 (AB 비교)
    ├─ 크기     : 256 · 512 · 1024
    ├─ Overlap  : 0% · 10% · 25%
    └─ 전략     : Recursive ↔ Semantic
         ↓
  Step 4 — 문서 타입별 개별 튜닝
    └─ 법령 256 · 매뉴얼 1024 · FAQ entry-based
  ```
- 벤치마크 근거 박스
  ```
  • Vectara 2026: Recursive 512 = 69% (1위)
  • Microsoft Azure 권장: 512 + 25% overlap
  • Adaptive vs Fixed (임상): 87% vs 13%
  • 25 config × 48 embedding → Chunking이
    임베딩 모델만큼 영향력 큼 (NAACL 2025)
  ```

**[스크립트]**
> Chunk 크기를 어떻게 정할지 실전 프로세스예요. 한 번에 정답을 찾으려 하지 마시고 **반복 실험**으로 접근하세요.
>
> **Step 1 — 기본값으로 출발.** Chunk 512 토큰, Overlap 10~25%, Recursive 전략. 이건 2026년 Vectara 벤치마크에서 1위(69% 정확도)한 설정이고, Microsoft Azure도 같은 기본값을 권장합니다. **이걸 출발점으로 잡으세요.** 처음부터 Semantic 같은 고급 전략에 들어가지 마시고요.
>
> **Step 2 — Golden Dataset으로 베이스라인 측정.** 앞에서 말한 Recall@5, MRR, nDCG를 기록해요. **"지금 이 값이 우리의 출발선이다"** 를 명확히 해둡니다. 이게 없으면 "좋아졌다"는 주장도 근거가 없어요.
>
> **Step 3 — 변수 하나씩만 변경.** 크기부터 보세요. 256 → 512 → 1024 돌려서 지표 비교. 그 다음 overlap을 0% → 10% → 25%. **동시에 여러 개 바꾸면 뭐가 효과였는지 몰라요.** 한 번에 하나씩이 원칙입니다.
>
> **Step 4 — 문서 타입별 개별 튜닝.** 전체 평균이 좋아져도 특정 타입은 나빠질 수 있어요. **법령은 256이 맞고 매뉴얼은 1024가 맞는** 경우가 흔해요. 타입별로 나눠서 각자 최적값을 찾으세요.
>
> 벤치마크 근거 몇 개 더 기억해 두세요.
>
> **"Chunking이 임베딩 모델만큼 영향력 크다"** — Vectara의 NAACL 2025 연구에서 25개 Chunking 설정 × 48개 임베딩 모델로 실험했는데, **Chunking 설정이 임베딩 모델 선택만큼 retrieval 품질에 영향을 줬어요.** 임베딩 모델만 열심히 고르고 chunking은 default로 두는 게 가장 흔한 비대칭 실수예요.
>
> **"Adaptive 87% vs Fixed 13%"** — 임상 의사결정 연구에서 구조에 맞춘 Chunking이 Fixed-size 대비 7배 가까운 정확도를 보였어요. **문서 타입을 무시한 Fixed가 얼마나 손해인지** 보여주는 수치입니다.

## Slide 13 — 메타데이터 태깅 실전 설계 *(신규 · 무엇을 태깅하나)*
**[화면]**
- 3단계 메타데이터 체크리스트
  ```
  ┌─ [Tier 1] 항상 필수 ─────────────────────────────────┐
  │  doc_id           문서 식별자                        │
  │  doc_type         계약·FAQ·코드 등 타입              │
  │  chunk_index      문서 내 청크 순서                  │
  │  source_path      원본 파일 경로                     │
  │  created_at       문서 생성일                        │
  │  updated_at       문서 수정일                        │
  └──────────────────────────────────────────────────────┘
  ┌─ [Tier 2] 엔터프라이즈 필수 ─────────────────────────┐
  │  access_tags      접근 권한 (부서·역할)               │
  │  version          문서 버전                           │
  │  language         언어 코드                           │
  │  embedding_model  생성에 쓴 모델 ID                   │
  └──────────────────────────────────────────────────────┘
  ┌─ [Tier 3] 검색 품질 향상 ────────────────────────────┐
  │  section_title    부모 헤딩 (맥락 보강)               │
  │  page_number      페이지 번호 (원문 이동용)           │
  │  bbox             좌표 (원문 하이라이트)              │
  │  summary          청크 1줄 요약 (hybrid 검색 보조)    │
  └──────────────────────────────────────────────────────┘
  ```
- 경고 박스: **"나중에 추가하면 전체 재인덱싱 필수 — 처음부터 설계에 넣으세요"**

**[스크립트]**
> 메타데이터 태깅은 "나중에 생각하자"로 미루면 안 되는 작업이에요. 이유가 분명합니다 — **메타데이터를 추가하려면 인덱스를 전부 다시 만들어야 해요.** 문서 수십만 건이면 며칠이 걸리고, 임베딩 API 비용이 또 한 번 나갑니다.
>
> 그래서 3단계 체크리스트로 정리했어요. 프로젝트 규모에 맞춰 점진적으로 채우세요.
>
> **Tier 1 — 항상 필수.** 이 6개가 없으면 **최소한의 추적조차 안 됩니다.** `doc_id`(문서 식별), `doc_type`(계약·FAQ·코드 등), `chunk_index`(문서 안에서 몇 번째 청크), `source_path`, `created_at`, `updated_at`. **"이 답이 어느 문서 어느 부분에서 나왔지?"** 를 추적하려면 이게 기본이에요.
>
> **Tier 2 — 엔터프라이즈 필수.** 여기부터가 아키텍트의 영역입니다.
>
> - **access_tags** — 부서·역할별 접근 권한. 검색 시점에 `WHERE access_tags @> ARRAY['finance']` 같이 필터링해요. 이게 없으면 신입이 임원 급여 문서를 조회할 수 있는 사고가 납니다.
>
> - **version** — 같은 문서의 여러 버전이 인덱스에 공존할 때, 사용자가 어느 버전을 봤는지 추적해야 해요.
>
> - **language** — 다국어 환경의 필수 필드. 한국어 질문엔 한국어 청크만 필터링하는 식으로 품질과 비용을 같이 관리해요.
>
> - **embedding_model** — 앞에서 본 임베딩 모델 교체 대비용. 여러 모델이 인덱스에 섞여 있어도 "이 청크는 모델 A로 만들었다"는 걸 알아야 마이그레이션이 가능해요.
>
> **Tier 3 — 검색 품질 향상.** 여기까지 구축하면 프로덕션 RAG로서의 완성도가 올라가요.
>
> - **section_title**(부모 헤딩) — 청크만 봐서는 맥락이 부족한데, "이건 'Refund Policy' 섹션의 일부"라는 정보를 메타데이터에 달아두면 검색 결과도 좋아지고, LLM이 더 정확히 답합니다.
>
> - **page_number, bbox**(좌표) — 답변 화면에서 **원문 PDF를 하이라이트**해주는 기능이 가능해져요. 규제 산업에서 이게 엄청난 강점이에요.
>
> - **summary** — 청크 1줄 요약. 이걸 별도로 임베딩해서 BM25+Vector Hybrid에 넣으면 recall이 추가로 올라가요. 고급 패턴인데 효과가 큽니다.
>
> 마지막 한 번 더 강조 — **이 메타데이터들을 처음부터 스키마에 넣으세요.** 제가 본 실제 사례로, 메타데이터 빠뜨려서 10만 문서를 다시 돌린 팀이 있어요. 며칠과 수백만 원이 날아갔어요. **20분의 설계가 수일의 재작업을 막습니다.**

## Slide 14 — 임베딩이란 정확히 무엇인가 *(신규)*
**[화면]**
- 간단 도식
  ```
  "강아지가 뛰어간다"  →  [0.23, -0.11, 0.87, ..., 0.05]   (1536차원)
  "개가 달린다"        →  [0.21, -0.09, 0.89, ..., 0.04]   ← 가까운 벡터
  "자동차 수리"        →  [-0.45, 0.78, -0.22, ..., 0.91]  ← 먼 벡터
  ```

**[스크립트]**
> 다음 장에서 임베딩 모델 비교를 보기 전에, **"임베딩이 정확히 뭔지"**부터 짚고 가겠습니다. 용어 없이 비교표만 봐도 의미가 안 와닿아요.
>
> 임베딩은 **텍스트를 고정 길이의 숫자 배열로 바꾸는 작업**입니다. 예를 들어 OpenAI의 text-embedding-3-large는 한 문장을 3072개의 숫자로 표현해요. 이걸 벡터라고 부릅니다.
>
> 핵심 성질이 뭐냐, **"의미가 비슷한 문장은 서로 가까운 숫자 배열로 변환된다"**는 거예요. "강아지가 뛰어간다"와 "개가 달린다"는 단어는 다르지만 의미가 거의 같죠. 임베딩 모델은 이 둘을 **비슷한 숫자 배열**로 만들어냅니다. "자동차 수리"는 완전히 다른 의미니까 멀리 떨어진 숫자 배열이 나와요.
>
> 이 성질 때문에 "의미 검색"이 가능해지는 거예요. 질문을 벡터로 바꾸고, 가장 가까운 벡터를 가진 문서를 꺼내는 거죠.
>
> 그러면 자연스럽게 질문이 생기죠. **임베딩 모델이 여러 개 있다는 건데, 뭐가 다르냐?** 차원 수도 다르고, 학습된 언어도 다르고, 얼마나 긴 텍스트를 한 번에 처리할 수 있는지도 달라요. 다음 장에서 실무 기준으로 비교해 보겠습니다.

## Slide 15 — 임베딩 모델 비교 (MTEB 기준)
**[화면]**
- 3행 표
  | 모델 | MTEB | 컨텍스트 | 강점 |
  |---|---|---|---|
  | Cohere embed-v4 | 65.2 | 128k | 다국어·긴 문서 |
  | OpenAI text-embed-3-large | 64.6 | 8k | 영어 범용 |
  | BGE-M3 (OSS) | 63.0 | 8k | 셀프호스팅 |

**[스크립트]**
> 2026년 기준으로 현업에서 자주 후보에 올라오는 세 모델만 정리했어요. 표에 **MTEB**라는 지표가 있는데, 이건 **다양한 검색 태스크에서의 평균 성능**을 점수화한 공개 벤치마크입니다. 숫자가 높을수록 좋아요.
>
> **Cohere embed-v4**는 현재 MTEB 최상위권이고, 특히 **다국어와 긴 문서**에 강합니다. 컨텍스트 128k — 즉 수십 페이지짜리 문서를 통째로 하나의 벡터로 만들 수 있어요. 한국어 성능도 좋은 편입니다.
>
> **OpenAI text-embedding-3-large**는 MTEB에서 오랫동안 기준점 역할을 해왔어요. 영어 범용 성능이 안정적이고, 가격도 합리적입니다. 다만 교차 언어 검색 — 한국어 질문으로 영어 문서를 찾는 식의 시나리오 — 에선 Cohere보다 약해요.
>
> **BGE-M3**는 오픈소스예요. 자체 호스팅이 가능하다는 게 핵심 장점입니다. 데이터가 외부로 나가면 안 되는 규제 산업에서 거의 유일한 선택지예요. 성능도 63.0으로 상용 모델에 크게 뒤지지 않습니다. 1000개 이상 언어를 지원하고, 한국어도 포함돼 있어요.
>
> 이 표를 사진 찍어 두시면 실무 회의에서 유용할 겁니다.

## Slide 16 — 임베딩 선택: 4가지 질문
**[화면]**
- 번호 리스트
  - Q1. 데이터 언어는?
  - Q2. 문서 길이는?
  - Q3. 호스팅 정책? (데이터 외부 전송 가능?)
  - Q4. 차원 × 건수 = 스토리지 비용?

**[스크립트]**
> 벤치마크 점수를 보기 전에 이 네 가지 질문에 답하시는 게 먼저예요.
>
> **질문 1. 데이터 언어**. 한국어 비중이 얼마나 되나요? 한국어가 주력이면 Cohere v4나 BGE-M3를 우선 검토하세요. 영어 전용이면 OpenAI text-embedding-3도 충분합니다.
>
> **질문 2. 문서 길이**. 계약서나 백서처럼 긴 문서를 **통째로** 임베딩하고 싶다면 128k 컨텍스트가 있는 Cohere가 유리해요. 짧은 FAQ 위주라면 컨텍스트 크기는 덜 중요합니다.
>
> **질문 3. 호스팅 정책**. 이게 엔터프라이즈에선 가장 자주 걸리는 부분이에요. "우리 데이터가 Cohere나 OpenAI 서버로 나가도 되는가?" 대답이 "안 된다"면 선택지는 사실상 BGE-M3 셀프호스팅입니다. 이 질문에 먼저 답하지 않으면 뒤에서 법무팀한테 다 엎어져요.
>
> **질문 4. 스토리지 비용**. 이건 아키텍트가 잊지 말아야 할 곱셈이에요. OpenAI의 3072차원 벡터 100만 건을 저장한다고 치면, 단순 계산으로만 4기가바이트가 나와요. 거기에 인덱스 오버헤드, 메타데이터까지 더하면 10기가에 육박합니다. 관리형 VectorDB에서 10기가면 월 비용이 꽤 많이 나가요. **차원이 큰 모델이 무조건 좋은 게 아닙니다.** 작은 차원의 모델로 품질을 유지할 수 있는지 먼저 실험해 보세요.

---

## Slide 17 — 교체 비용을 설계에 포함하라
**[화면]**
- 경고: "임베딩 모델 교체 = 전체 인덱스 재구축"
- 해결: 메타데이터에 `embedding_model_id` 저장 → 점진적 마이그레이션

**[스크립트]**
> 임베딩 모델은 처음에 고른 걸 계속 쓴다는 보장이 없어요. 1년 뒤에 더 좋은 모델이 나오면 바꾸고 싶어지거든요. 그런데 여기서 함정이 있습니다.
>
> **임베딩 모델을 교체한다는 건 전체 인덱스를 다시 만든다는 의미예요.** 왜냐, 모델마다 벡터 공간이 다르거든요. A 모델이 만든 벡터와 B 모델이 만든 벡터는 같은 공간에 있지 않아서 비교 자체가 무의미합니다. 그러니까 처음부터 전부 다시 임베딩해야 해요. 수천만 건이면 며칠 걸립니다.
>
> 그래서 설계 시점에 **"우리가 임베딩 모델을 바꾸려면 얼마나 걸릴까"**를 추정해 두세요. 비용과 다운타임 계산이 가능해집니다.
>
> 그리고 실전 팁 하나. 벡터를 저장할 때 **어떤 모델로 만들었는지 메타데이터에 꼭 남겨 두세요.** `embedding_model_id` 같은 필드예요. 이게 있으면 점진적 마이그레이션이 가능합니다. 신규 데이터는 새 모델로 임베딩하고, 구 데이터는 천천히 배치로 옮기면서, 두 공간을 병렬 운영할 수 있어요. 이 필드 하나 없어서 서비스를 통째로 멈추고 재임베딩하는 경우를 생각보다 자주 봅니다.

## Slide 8 — VectorDB가 하는 일
**[화면]**
- 좌우 대비
  - 좌: 전통 DB — `WHERE id = 42` → 정확한 값 찾기
  - 우: VectorDB — 고차원 공간에서 **가까운 벡터** 찾기 (ANN)
- 키워드: HNSW · IVF-PQ

**[스크립트]**
> VectorDB가 뭔지 감이 잘 안 오실 수 있어서, 전통 DB와 비교해서 설명드립니다.
>
> 전통적인 관계형 DB는 **"정확한 값"**을 찾습니다. 예를 들어 `WHERE id = 42` 하면 42번을 정확히 가져옵니다. 빠르고 정확하지만, **"이 문장과 의미가 비슷한 걸 찾아줘"** 같은 질의는 못 합니다.
>
> VectorDB는 다릅니다. 텍스트든 이미지든 우선 **임베딩**을 거쳐 **벡터**로 바꿔놓습니다. 벡터는 숫자 배열입니다. 예를 들어 1536개의 숫자로 이뤄진 긴 배열이에요. 핵심은, **의미가 비슷한 문장은 벡터 공간에서 가까운 위치에 놓인다**는 성질입니다. "강아지"와 "개"는 가까이 있고, "강아지"와 "자동차"는 멀리 있는 식이에요.
>
> 그래서 질문이 들어오면 질문을 똑같이 벡터로 바꾸고, 그 벡터에 **가장 가까운 문서들을 꺼내옵니다**. 여기서 중요한 건, 진짜 가장 가까운 놈을 다 확인하면 너무 느립니다. 수백만 건이면 일일이 비교하는 데 몇 초가 걸려요. 그래서 VectorDB는 **조금 부정확해도 빠르게 찾는 방법** — 이를 **ANN**, Approximate Nearest Neighbor라고 부릅니다 — 을 씁니다. 정확도는 99% 정도 유지하면서 속도를 수백 배 빠르게 만듭니다.
>
> 알고리즘 이름 두 개만 기억해두시면 됩니다. **HNSW**는 2026년 기준 가장 널리 쓰이는 기본값이고, **IVF-PQ**는 메모리가 제한적일 때 쓰는 대안입니다. 어떤 VectorDB를 쓰든 내부는 거의 이 둘 중 하나입니다.

## Slide 9 — VectorDB 옵션 비교 (2026)
**[화면]**
- 4개 번호 카드
  - 01 Pinecone — 관리형, API Key 한 줄로 시작
  - 02 Qdrant — Rust, 낮은 지연(p50 ≈ 4ms)
  - 03 Weaviate — Hybrid Search 1-쿼리 내장
  - 04 pgvector — Postgres 확장, 트랜잭션 일관성

**[스크립트]**
> VectorDB 제품은 지금 정말 많습니다. 실무에서 자주 선택지에 올라오는 네 개만 추려서 보겠습니다.
>
> **Pinecone**은 완전 관리형 서비스입니다. API Key 발급받고 한 줄 코드로 바로 시작할 수 있습니다. 운영 부담이 제로에 가까워요. 대신 비용이 빠르게 올라가고, 데이터가 외부 서비스에 있다는 점이 규제가 강한 곳에선 부담이 될 수 있습니다.
>
> **Qdrant**는 Rust로 쓰인 오픈소스 VectorDB입니다. 성능이 정말 뛰어나서 p50 지연이 4ms 수준입니다. 자체 호스팅할 수 있고 Managed Cloud 옵션도 있습니다. 검색 지연이 중요한 서비스에 적합합니다.
>
> **Weaviate**는 Hybrid Search — 벡터 검색과 키워드 검색을 합치는 방식인데 곧 이어서 자세히 다룹니다 — 를 한 쿼리로 처리할 수 있는 게 큰 장점입니다. 임베딩 모델을 내부에 내장해서 텍스트를 그대로 넣으면 자동으로 벡터화도 해줍니다.
>
> **pgvector**는 조금 다릅니다. 이건 별도 DB가 아니라 **PostgreSQL의 확장 기능**입니다. 기존에 Postgres를 쓰고 있다면 별도 인프라 없이 테이블에 벡터 컬럼만 추가하면 됩니다. 2024년부터 HNSW도 지원하면서 성능도 충분히 올라왔어요. 트랜잭션 일관성이 보장된다는 것도 엔터프라이즈에선 큰 장점입니다.
>
> **선택은 기술보다 조직 상황**입니다. 이미 Postgres를 쓴다 — 일단 pgvector로 시작해보세요. 팀이 작고 운영을 최소화하고 싶다 — Pinecone. 지연에 민감하다 — Qdrant. 출처는 슬라이드 하단의 자료 참고하시면 됩니다.

## Slide 18 — 왜 Hybrid Search인가
**[화면]**
- 2박스 대비
  - Dense(Vector) — 의미 유사성 강, 정확 매칭 약
  - Sparse(BM25) — 정확 매칭 강, 의미 약
- 하단: "AX-2045-R 같은 제품 코드, §14(2) 같은 법령 조항"

**[스크립트]**
> 자, 이제 검색 전략으로 넘어갑니다. 벡터 검색만 쓰면 다 해결될 것 같지만, 실제로는 그렇지 않아요.
>
> 벡터 검색은 **의미가 비슷한 것**에 강합니다. "비밀번호 변경법"과 "비번 어떻게 바꿔요"를 같은 걸로 인식해요. 여기까진 좋아요.
>
> 그런데 약점이 있습니다. **정확한 토큰 매칭**에는 의외로 약해요. 예를 들어 제품 코드 "AX-2045-R"을 검색한다고 해봅시다. 이 문자열 자체는 벡터 공간에서 특별한 의미를 만들지 못해요. 그래서 다른 비슷해 보이는 코드들과 섞여 나오거나, 아예 엉뚱한 결과가 나옵니다. 법령 조항 번호 "§14(2)", 의약품 코드, 부품번호, 약어 같은 것들도 마찬가지예요.
>
> 그런데 이런 "정확한 매칭"에 강한 게 뭐냐? 옛날부터 있던 **BM25** 같은 키워드 검색입니다. 토큰 단위로 정확히 일치하는지 보는 방식이에요. 제품 코드, 법령 조항, 고유명사에서는 벡터 검색보다 훨씬 정확해요.
>
> 회사 문서를 한번 열어보세요. 고유명사, 제품 코드, 약어, 숫자 식별자 — 정말 한가득입니다. 그래서 **2026년 엔터프라이즈 RAG의 표준은 둘을 합치는 Hybrid Search**예요. 벡터로 의미를 잡고, BM25로 정확 매칭을 보강하는 구조입니다.

---

## Slide 18-1 — BM25 (Sparse) 원리 *(신규 · 어떻게 점수를 매기나)*
**[화면]**
- 상단 바: Query "AX-2045-R 부품 가격" + 공식 `BM25 = TF × IDF × Length-Norm`
- 3 카드 (TF / IDF / Length-Norm)
  ```
  ┌─[01] TF · 빈도 ────────────────────────────┐
  │ 단어가 많이 나오면 점수 ↑                    │
  │ Doc A · "AX-2045-R" × 3                   │
  │ Doc B · "AX-2045-R" × 1                   │
  │ Doc C · "AX-2045-R" × 0                   │
  │ → Doc A 점수 ↑↑↑                          │
  └────────────────────────────────────────────┘
  ┌─[02] IDF · 희귀도 ──────────────────────────┐
  │ 희귀할수록 가치 ↑                            │
  │ "the"        · 흔함     IDF ↓               │
  │ "가격"       · 보통     IDF 중               │
  │ "AX-2045-R"  · 희귀     IDF ↑↑              │
  │ → 제품 코드는 강력한 신호                    │
  └────────────────────────────────────────────┘
  ┌─[03] LENGTH NORM · 길이 보정 ────────────────┐
  │ 짧은 문서 + 1회 등장 → 신호 강함             │
  │ 긴 문서 + 1회 등장   → 우연일 가능성 ↓ (보정) │
  └────────────────────────────────────────────┘
  ```
- 하단: **"BM25 = TF × IDF × 길이 보정. 토큰 단위 정확 매칭에 강하지만 의미는 모름 — Dense와 짝을 이뤄야"**

**[스크립트]**
> 앞 슬라이드에서 "BM25는 토큰 매칭에 강하다"고만 말했는데, 그럼 실제로 어떻게 점수를 매기는지 한 장으로 풀어드립니다. BM25는 세 항의 곱입니다.
>
> **첫째, TF (Term Frequency).** 이 문서에 검색어가 몇 번 나왔느냐. 많이 나올수록 점수가 올라갑니다. 직관적입니다.
>
> **둘째, IDF (Inverse Document Frequency).** 희귀할수록 가치가 높습니다. "the" 같이 어디에나 있는 단어는 점수에 거의 기여하지 않고, "AX-2045-R" 같은 제품 코드는 IDF가 매우 높아 강력한 신호가 됩니다. **기업 문서의 고유명사·코드가 BM25에서 빛나는 이유**가 이 IDF에 있습니다.
>
> **셋째, Length Norm (길이 보정).** 긴 문서가 우연히 검색어를 많이 포함할 수 있습니다. 짧은 문서에서 1회 등장하는 게 긴 문서에서 1회 등장보다 강한 신호이므로, 문서 길이로 점수를 보정합니다.
>
> 이 세 항의 곱이 BM25 점수입니다. 토큰이 정확히 일치해야만 점수가 생기기 때문에, **의미가 비슷하지만 단어가 다른** 문서는 절대 못 찾아냅니다. 그래서 Dense와 짝을 이뤄야 한다는 것이 다음 두 슬라이드의 결론입니다.

---

## Slide 18-2 — Hybrid Search 정의 & 필요 예시 *(신규 · 무엇을 합치고 언제 필수인가)*
**[화면]**
- 다이어그램
  ```
  Query ─┬─► Dense (Vector)  · 의미 검색 · top 50 ──┐
         └─► Sparse (BM25)   · 정확 매칭 · top 50 ──┼─► RRF ─► Top-N
                                                    │
  ```
- 4 예시 카드 — 언제 Hybrid가 필수인가
  ```
  01 제품 코드      AX-2045-R · 시리얼·SKU
  02 법령·규정 조항 §14(2) · 시행규칙 23조
  03 의약품·검사 코드 ICD-10 E11.9 · KCD 코드
  04 약어·고유명사   SLA · API · MLOps · 사내 코드네임
  ```
- 하단: **"기업 문서엔 고유명사·코드·약어가 한가득. Dense 단독은 이 토큰들을 흘려보냄"**

**[스크립트]**
> Hybrid Search를 한 줄로 정의하면 **두 검색 결과를 합치는 것**입니다. Dense(벡터, 의미)와 Sparse(BM25, 정확 매칭)를 동시에 실행하고, 결과를 RRF 같은 융합 방식으로 합쳐 최종 Top-N을 뽑습니다. 다음 슬라이드에서 RRF는 자세히 다루고, 이 슬라이드는 **"왜 합쳐야만 하는가"**의 실증입니다.
>
> 화면의 4가지 예시가 핵심입니다. **제품 코드** "AX-2045-R", **법령 조항** "§14(2)", **의약품 코드** "ICD-10 E11.9", **약어/고유명사** "SLA · API · MLOps". 이 토큰들은 의미적 유사성보다 **글자 그대로의 정확 매칭**이 결정적입니다. 벡터 검색만으론 이 토큰들이 다른 비슷한 코드와 섞여 나옵니다.
>
> 회사 문서를 열어보세요. 한 줄에 고유명사·코드·약어가 몇 개씩 들어있는 게 보통입니다. 그래서 **2026년 엔터프라이즈 RAG의 기본은 Hybrid**입니다. Dense 단독은 사실상 미완성 시스템이라고 보셔도 됩니다.

## Slide 20 — 왜 Reranker인가
**[화면]**
- 2박스
  - Retrieval — Recall (넓게 캐스팅, top 50~100)
  - Reranker — Precision (컨텍스트 창에 넣을 만한 것만, top 5~10)
- 수치: Cohere Rerank 3.5 → BEIR +23.4%, 무관 문단 30~40% → <10%

**[스크립트]**
> Reranker가 뭐고 왜 필요한지 설명드릴게요.
>
> 앞서 말한 검색 단계의 목표는 "관련 문서를 놓치지 않고 가져오기"예요. 정보 검색 용어로는 **Recall**이라고 부릅니다. 그래서 일부러 top 50이나 top 100같이 **넓게** 가져와요. 놓치면 안 되니까요.
>
> 그런데 이걸 그대로 LLM 컨텍스트에 다 넣으면 문제가 생겨요. 정말 관련 있는 문단은 5개인데 30개를 같이 넣으면, LLM이 헷갈려서 답이 오히려 흐려집니다. 연구에 따르면 컨텍스트에 무관 문단이 섞이면 답변 품질이 확연히 떨어진다고 해요.
>
> 그래서 두 번째 단계가 필요한데, 이게 **Reranker**입니다. 검색으로 가져온 50~100개 중에서 **"정말로 질문에 답이 되는 5~10개"**만 추려내는 역할이에요. 정보 검색 용어로는 **Precision**을 확보하는 단계죠.
>
> 어떻게 하냐, Reranker는 질문과 각 문서를 **한 쌍씩** 더 정밀하게 비교해서 점수를 매깁니다. 벡터 검색보다 느리지만 훨씬 정확해요. 그래서 처음부터 Reranker로 다 훑지 않고, 1차로 거르고 2차로 Reranker를 쓰는 2단계 구조인 겁니다.
>
> 수치를 보시면, Cohere의 Rerank 3.5 모델은 BEIR 벤치마크에서 Hybrid Search 단독 대비 **23% 개선**을 보여줬어요. 실전 사례에선 무관 문단 비율이 30~40%에서 10% 아래로 떨어지는 경우가 흔합니다. **Reranker는 이제 옵션이 아니라 프로덕션 RAG의 기준선**이라고 봐도 돼요.

## Slide 20-1 — Reranker 작동 원리 & 사용 시점 *(신규 · 어떻게 작동하고 언제 쓰나)*
**[화면]**
- 2단계 파이프라인 다이어그램
  ```
  [STAGE 1] RETRIEVE — RECALL              [STAGE 2] RERANK — PRECISION
  Corpus ─► Retriever (Hybrid) ─► Top 50~100 ─► Reranker (cross-encoder) ─► Top 5~10 ─► LLM
              bi-encoder · 빠름                  (query, doc) 쌍 점수 · 정밀
  ```
- 2 카드
  ```
  ┌─ Retriever vs Reranker ────────────────────┐
  │ · Bi-encoder  — 따로 인코딩, 미리 벡터 저장 │
  │ · Cross-encoder — 쌍을 함께, 더 정밀        │
  │ · 속도 차이 ~100배 → 2단계 분리 필수         │
  └─────────────────────────────────────────────┘
  ┌─ 언제 Reranker가 효과적인가 ─────────────────┐
  │ · Recall은 OK인데 Top-K 노이즈가 많을 때     │
  │ · LLM 컨텍스트 윈도우 절약 필요              │
  │ · 답변이 무관 문단에 민감한 도메인 (법무·의료) │
  └─────────────────────────────────────────────┘
  ```

**[스크립트]**
> 앞 슬라이드에서 "왜 Reranker가 필요한가"를 봤습니다. 이 슬라이드는 **어떻게 작동하고 언제 효과적인가**를 한 장에 정리합니다.
>
> **작동 원리**부터 봅시다. RAG 검색은 2단계 파이프라인입니다. **Stage 1 — Retrieve(Recall)**: 수만~수억 건의 corpus에서 Dense+BM25로 top 50~100을 빠르게 뽑습니다. 여기서 쓰는 것이 **bi-encoder** — 쿼리와 문서를 각자 따로 인코딩해서 벡터화해두기 때문에, 쿼리만 새로 인코딩하고 미리 저장된 문서 벡터와 비교합니다. 그래서 빠릅니다. **Stage 2 — Rerank(Precision)**: 이 50~100개를 **cross-encoder**가 다시 점수 매깁니다. cross-encoder는 (query, doc) 쌍을 **함께** 인코딩하기 때문에 두 토큰 간 attention이 작용해 훨씬 정밀합니다. 대신 호출당 100~600ms로 느려서, 처음부터 corpus 전체에 못 돌립니다. 속도 차이가 약 100배라 **2단계로 분리**하는 것이 본질입니다.
>
> **언제 효과적인가**는 세 가지 신호로 봅니다.
>
> 첫째, **Recall은 OK인데 Top-K 노이즈가 많을 때**. 정답이 top 50 안에는 들어 있는데 1~5위에 못 올라오는 상황. 평가 지표로는 Recall@50은 높은데 MRR이나 Recall@5가 낮을 때입니다.
>
> 둘째, **LLM 컨텍스트 윈도우 절약**. 50개 문단을 다 LLM에 넣으면 비용·지연이 모두 폭증합니다. 5~10개로 추리면 답변 품질도 올라갑니다(컨텍스트 노이즈 감소).
>
> 셋째, **답변이 무관 문단에 민감한 도메인**. 법무·의료처럼 한 문장의 인용이 결정적인 분야. 무관 문단이 섞이면 LLM이 그쪽으로 끌려갈 위험이 큽니다.
>
> 이 세 가지 중 하나라도 해당되면 Reranker는 **선택이 아닌 기본**입니다. 다음 슬라이드에서 어떤 모델을 쓸지 옵션을 보겠습니다.

>

>

>
> 셋째, **LLM을 Reranker로 쓰는 방식**. GPT-5.5나 Claude Opus 4.7에게 "이 문서들 중에 질문에 관련 있는 것만 골라줘"라고 프롬프트로 시키는 겁니다. 설명 가능성이 좋고, 복잡한 판단이 필요한 도메인에서 유리합니다. 단점은 비용과 지연이 크다는 점이에요. 작은 도메인 평가용으로는 GPT-5.4-mini나 Haiku 4.5 같은 mid-tier 모델로도 충분히 시도해볼 수 있습니다.
>
> 공통적으로 알아두실 게, **Reranker는 지연이 100~600ms 추가됩니다.** 사용자 체감이 달라질 수 있는 수준이에요. 그래서 SLO — 서비스 레벨 목표 — 에 이 지연을 꼭 포함하시고, 앞단에 캐시를 두어서 상쇄하는 방법도 같이 고민하세요. 캐시 이야기는 섹션 2에서 다시 나옵니다.

## Slide 21-1 — Layer 5 LLM Integration *(신규 · 검색 결과를 답변으로)*
**[화면]**
- 좌·중·우 흐름 다이어그램
  ```
  [1] PROMPT ASSEMBLY                    [2] RESPONSE
  ┌─────────────────────────┐            ┌──────────────────────────┐
  │ SYSTEM                  │            │ 답변 (스트리밍)           │
  │  "컨텍스트만 사용 ·      │            │ "...답변 본문..."          │
  │   인용 [n] 표기"        │   ───►     │                           │
  │                         │   LLM       │ ───── CITATIONS ────       │
  │ CONTEXT (Top-K=5)       │  (Gateway)  │ [1] 연차제도_2024.pdf      │
  │  [1] chunk_id_X · 메타  │            │ [2] 취업규칙_v3.2.pdf §14 │
  │  [2] chunk_id_Y · 메타  │            │ [3] 사내공지_2026Q2.md    │
  │  [3] ...                │            └──────────────────────────┘
  │                         │
  │ USER QUERY              │
  │  "사용자 질문"           │
  └─────────────────────────┘
  ```
- 4 카드 (설계 고려사항)
  ```
  01 Prompt 템플릿     · System / Context / Query 분리
                        · "컨텍스트 외 추론 금지" 지시
  02 인용 구조         · chunk_id ↔ 원문 메타데이터 매핑
                        · 답변에 [n] 표기, 사용자 클릭 시 원문 점프
  03 Streaming         · 토큰 단위 스트리밍 → 체감 지연 ↓
  04 Failure 처리      · 검색 0건 → "근거 없음" 안전 거절
                        · Hallucination 방지 마지막 게이트
  ```

**[스크립트]**
> Layer 4까지가 "관련 문서 N개를 잘 뽑는 단계"였다면, **Layer 5는 그 N개를 답변으로 변환하는 단계**입니다. 5계층 중 마지막인데, 여기서 어떻게 설계하느냐에 따라 같은 검색 결과로도 답변 품질이 천차만별입니다.
>
> **흐름은 두 박스**로 이뤄집니다.
>
> **(1) Prompt Assembly.** 세 부분을 조립합니다. **System** 영역에는 "제공된 컨텍스트만 사용하고 인용 [n] 표기를 붙여라" 같은 행동 지시. **Context** 영역에는 검색해온 Top-K 청크들 — 각 청크에는 인용 번호와 메타데이터(문서 ID, 섹션, 페이지)가 같이 들어갑니다. **User Query** 영역에는 사용자 원문 질문. 이 세 부분을 명확히 분리하는 게 첫 번째 설계 원칙입니다.
>
> **(2) Response.** 이 프롬프트를 LLM(보통 Gateway 경유)에 보내면 스트리밍으로 답변이 흘러나옵니다. 답변 본문 안에 `[1]`, `[2]` 같은 인용 번호가 붙고, 사용자 화면에서는 그 번호를 클릭하면 원문 청크/문서로 점프합니다.
>
> **설계 고려사항 4가지**입니다.
>
> **01 Prompt 템플릿** — System/Context/Query를 명확히 분리. "컨텍스트 외 추론 금지"를 시스템 메시지에 못 박는 게 환각 방지의 첫 번째 방어선입니다.
>
> **02 인용 구조** — chunk_id와 원문 메타데이터를 매핑해 둬야 답변에 정확한 [n] 표기가 붙습니다. Slide 13에서 설계한 메타데이터(doc_id · page_number · bbox)가 여기서 빛납니다. 클릭하면 원문 PDF 하이라이트까지 가는 게 규제 산업의 강력한 강점입니다.
>
> **03 Streaming** — 토큰 단위 스트리밍이 표준입니다. 특히 답변이 긴 경우, 첫 토큰까지의 지연(TTFT)이 체감 품질을 좌우합니다.
>
> **04 Failure 처리** — 검색 결과가 0건이거나 신뢰도가 낮을 때, 모델이 그냥 추측해서 답하면 큰 사고입니다. **"근거가 없어 답할 수 없습니다"**라고 안전하게 거절하는 경로를 명시적으로 만드세요. Layer 5는 Hallucination 방지의 마지막 게이트입니다.

## Slide 23 — 측정 없이는 개선도 없다: Evaluation
**[화면]**
- 2열
  - Retrieval 지표: Recall@k, MRR, nDCG
  - Generation 지표: Faithfulness, Answer Relevance, Groundedness
- 도구: Ragas · TruLens · DeepEval

**[스크립트]**
> 마지막으로 꼭 짚고 갈 주제가 평가, Evaluation이에요.
>
> RAG 시스템은 측정이 까다롭습니다. 그냥 응답 만족도만 보면 어디가 문제인지 알 수가 없어요. 그래서 단계별로 지표를 분리해서 봐야 해요.
>
> **검색 단계의 지표**는 이런 것들이에요. Recall@k — 정답 문서가 상위 k개 안에 들어왔는가. MRR — 정답이 몇 번째에 나왔는가. nDCG — 순위 품질을 종합적으로 본 점수. 이 지표들이 낮으면 검색 자체를 고쳐야 하는 거예요.
>
> **생성 단계의 지표**는 또 다릅니다. Faithfulness — 답변이 실제로 검색된 문서에 기반하는가, 아니면 모델이 지어낸 부분이 있는가. Answer Relevance — 답변이 질문에 실제로 답하는가. Groundedness — 모든 주장에 근거 문서가 연결되는가. 이 지표들이 낮으면 프롬프트나 모델 쪽에 문제가 있는 거예요.
>
> 도구는 **Ragas**, **TruLens**, **DeepEval** 같은 것들이 많이 쓰여요. Ragas는 진입이 쉬워서 저는 거의 여기부터 시작하라고 권합니다.
>
> 그리고 제가 RAG 설계 리뷰에서 가장 먼저 물어보는 질문이 있어요. **"Golden Dataset 있나요?"** Golden Dataset은 "이 질문에 대한 정답 문서와 정답은 이거다"라고 사람이 정리해둔 데이터셋이에요. 이게 없으면 평가할 기준이 없는 거예요. 없으면 팀이 그냥 "느낌으로" 개선하게 되는데, 이게 몇 달 가면 아무도 정말 나아지고 있는지 모르는 상태가 됩니다. 설계 초기부터 Golden Dataset 수집 계획을 꼭 같이 세우세요.

## Slide 23-1 — 검색 지표 예시: Recall@k / MRR / nDCG *(신규 예시)*
**[화면]**
- 예시 질문: **"2024년 개인정보보호법 몇조가 개정됐나요?"**
- 정답 문서: `법령집_2024_개정판.pdf` (Doc-A)
- 검색 결과 표 (3개 시스템 비교)
  ```
  System X  : [Doc-C, Doc-A, Doc-F, Doc-B, Doc-D]  ← A가 2등
  System Y  : [Doc-A, Doc-B, Doc-C, Doc-D, Doc-E]  ← A가 1등
  System Z  : [Doc-B, Doc-C, Doc-D, Doc-E, Doc-F]  ← A가 없음
  ```
- 지표 계산 결과 미니 박스
  ```
  Recall@5 : X ✓  Y ✓  Z ✗      (상위 5개 안에 정답 포함되나)
  MRR      : X 0.50  Y 1.00  Z 0     (정답이 몇 번째?)
  nDCG@5   : X 0.63  Y 1.00  Z 0     (순위 품질 종합)
  ```

**[스크립트]**
> 검색 지표가 구체적으로 어떻게 계산되는지 예시로 보겠습니다.
>
> 질문은 "2024년 개인정보보호법 몇 조가 개정됐나요?". 정답 문서는 `법령집_2024_개정판.pdf` 하나예요. 세 시스템이 각자 상위 5개를 뽑았습니다.
>
> **Recall@k는 "상위 k개 안에 정답 문서가 있느냐"만 봐요.** System X와 Y는 정답을 5위 안에 포함했으니 1, System Z는 아예 없으니 0이에요. 이게 가장 단순한 지표인데, 순위 차이를 구분 못 하는 게 단점이에요.
>
> **MRR, Mean Reciprocal Rank는 "정답이 몇 번째에 나왔느냐"를 봐요.** 1등이면 1.0, 2등이면 0.5, 3등이면 0.33. System X는 정답이 2등이니까 0.5, Y는 1등이니 1.0, Z는 0. 순위 민감도가 있어서 Recall@k보다 섬세해요.
>
> **nDCG는 "순위 품질의 종합 점수"예요.** 정답이 여러 개고 각 정답에 중요도 점수가 있을 때까지 반영합니다. 계산식이 복잡한데, 결과만 보시면 돼요. 완벽한 순위(1등이 정답)면 1.0, 정답이 아예 없으면 0.
>
> 실무 팁 — **Recall@k로 먼저 놓치는 문서가 있는지 보고, MRR/nDCG로 순위 품질을 본다**가 일반적인 순서예요. Recall이 낮으면 검색 자체가 고장 난 거고, Recall은 괜찮은데 MRR이 낮으면 Reranker가 약한 겁니다.

## Slide 23-2 — 생성 지표 예시: Faithfulness / Answer Relevance / Groundedness *(신규 예시)*
**[화면]**
- 예시 질문: **"연차 제도 개정 내용 알려줘"**
- 검색된 문서: `연차제도_2024_개정.pdf` (연차 사용 기한 2년 → 3년으로 연장)
- 3가지 답변 비교 표
  ```
  ┌────────────────────────────────────────────────────┐
  │ 답변 A: "연차 사용 기한이 2년에서 3년으로 연장됐습니다"  │
  │  Faithfulness ✓  Relevance ✓  Groundedness ✓      │
  ├────────────────────────────────────────────────────┤
  │ 답변 B: "연차는 소중한 권리입니다. 잘 쓰세요."         │
  │  Faithfulness ✓  Relevance ✗  Groundedness ✗      │
  ├────────────────────────────────────────────────────┤
  │ 답변 C: "연차 사용 기한이 5년으로 늘어났어요"          │
  │  Faithfulness ✗  Relevance ✓  Groundedness ✗      │
  └────────────────────────────────────────────────────┘
  ```

**[스크립트]**
> 이번엔 생성 단계 지표를 실제 답변 예시로 볼게요.
>
> 질문은 "연차 제도 개정 내용 알려줘". 시스템이 `연차제도_2024_개정.pdf`를 잘 찾아왔고, 그 문서엔 "사용 기한 2년 → 3년 연장"이라고 적혀 있어요. 이 상태에서 LLM이 세 가지 다른 답을 만들 수 있는데, 지표가 각각 어떻게 나오는지 보세요.
>
> **답변 A**: "2년에서 3년으로 연장됐습니다." 문서에 있는 내용 그대로, 질문에 정확히 답했고, 근거 문서에 연결됩니다. 세 지표 모두 통과.
>
> **답변 B**: "연차는 소중한 권리입니다." 문서 내용을 **부정하진 않았으니** Faithfulness는 통과예요. 하지만 질문에 답을 안 했으니 Answer Relevance가 실패. 근거 문서와 연결되지 않으니 Groundedness도 실패. **내용이 틀리진 않았지만 쓸모없는 답**이에요.
>
> **답변 C**: "5년으로 늘어났어요." 이건 Faithfulness 실패예요. 문서엔 3년이라고 적혀 있는데 모델이 지어냈어요. 질문에는 답했으니 Relevance는 통과. 근거와 연결 안 되니 Groundedness는 실패. **가장 위험한 케이스**죠 — 그럴듯해 보이지만 틀린 답이에요.
>
> 실무 팁 — **Faithfulness가 떨어지면 프롬프트나 모델 쪽, Answer Relevance가 떨어지면 질문 해석 쪽, Groundedness가 떨어지면 인용 구조 설계 쪽**을 봐야 해요. 지표별로 원인이 다르니까 분리해서 모니터링하는 게 핵심입니다.
