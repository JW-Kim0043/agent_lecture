## Slide 3 — "모델 하나만 쓰면 되지 않나요?"
**[화면]**
- 7개 번호 박스: 가용성 · 속도 · 비용 · 프롬프트 변경 · 관측성 · 거버넌스 · 다중 팀 공유

**[스크립트]**
> 많은 팀이 처음엔 이렇게 시작합니다. `openai.ChatCompletion.create()`을 앱 코드에서 직접 부르는 거예요. 하나의 모델, 하나의 API Key, 한 줄짜리 호출. 간단하고 좋습니다.
>
> 그런데 서비스가 실제 운영에 들어가면, 이 일곱 가지가 한꺼번에 밀려와요. 빠르게 훑어볼게요.
>
> **가용성**. Azure 리전이 죽으면 어떻게 살아남죠? OpenAI가 장애 나면? 모델이 deprecation 되면? 대비책이 있어야 해요.
>
> **속도**. 같은 프롬프트여도 어떤 모델은 300ms에 답하고 어떤 모델은 30초가 걸려요. 사용자 체감이 완전히 달라집니다.
>
> **비용**. 모델을 크게 쓰면 한 달에 청구서가 몇 배로 불어요. 트래픽 많아지면 회사가 감당 못 할 수준까지 갑니다.
>
> **프롬프트 변경**. 운영 중에 프롬프트를 바꿔야 할 일이 많은데, 이게 정말 위험한 행위예요. 코드 배포급의 사건이거든요.
>
> **관측성**. 얼마나 많은 토큰이 나갔는지, 어떤 요청이 실패했는지, 누가 비용을 많이 쓰고 있는지 — 한눈에 보여야 해요.
>
> **거버넌스**. PII가 섞여 나가지는 않는지, 프롬프트 인젝션은 막았는지, 감사 로그는 남는지.
>
> **다중 팀 공유**. 여러 팀이 같은 LLM 풀을 쓰기 시작하면, 한 팀의 폭주가 다른 팀을 죽입니다.
>
> 이 일곱 가지를 앱 코드에 전부 녹여 넣으려고 하면 서비스마다 중복 구현이 생기고, 나중에 바꿀 때도 일곱 군데를 손대야 해요. 그래서 **한 계층으로 뽑아낸 게 Gateway**입니다.

## Slide 3-1 — 7가지 문제의 실제 사고 사례 *(신규 예시)*
**[화면]**
- 7개 번호 박스 (각 문제에 매칭된 현실 사례 한 줄)
  ```
  01 가용성    → "Azure East US 10분 장애 → 전 서비스 다운"
  02 속도      → "요약 API, 모델 교체 후 p95 300ms→9s"
  03 비용      → "사용자 10배 늘자 청구서 $2K→$38K/월"
  04 프롬프트  → "한 줄 수정으로 전체 응답 형식 붕괴, 롤백 불가"
  05 관측성    → "월말에 청구서 와서야 특정 팀이 70% 썼다는 걸 앎"
  06 거버넌스  → "프롬프트 로그에 주민번호 평문 노출, 감사 지적"
  07 다중 팀   → "A팀 이벤트성 트래픽이 B팀 SLO를 깨뜨림"
  ```

**[스크립트]**
> 앞 장에서 7가지 문제를 나열했는데, 실제로 어떻게 사고로 이어지는지 한 줄씩 예시로 보여드릴게요. 거의 다 제가 현장에서 실제로 본 케이스예요.
>
> **가용성** — Azure East US 10분 장애가 전 서비스 다운으로 번진 케이스. Fallback이 없어서 한 리전 장애가 그대로 사용자 장애가 됐어요.
>
> **속도** — 같은 요약 API인데 모델을 교체하니 p95 지연이 300ms에서 9초로 튀어오른 케이스. 호출이 앱 코드에 직접 박혀 있어서 모델만 바꿔도 영향을 추적 못 했어요.
>
> **비용** — 사용자가 10배 늘었더니 청구서가 $2K에서 $38K로 19배 뛴 케이스. 캐시도 Cascade도 없이 전부 비싼 모델로만 흘렀어요.
>
> **프롬프트 변경** — 운영자가 "톤만 살짝" 바꾸려고 프롬프트 한 줄 수정했다가 응답 형식이 전부 깨진 케이스. 롤백할 이전 버전이 없어서 복구에 몇 시간 걸렸어요.
>
> **관측성** — 월말 청구서가 와서야 특정 팀이 LLM 비용의 70%를 쓰고 있다는 걸 안 케이스. 요청 단위 태깅이 없으면 이런 사고가 반복됩니다.
>
> **거버넌스** — 고객 상담 프롬프트 로그에 주민등록번호가 평문으로 남아있어 감사에서 지적받은 케이스. PII 필터가 앱마다 따로 구현돼 있으면 빠진 서비스가 꼭 생겨요.
>
> **다중 팀 공유** — A팀이 이벤트성으로 순간 트래픽을 쏘니 같은 모델을 쓰는 B팀의 SLO가 깨진 케이스. 팀별 Rate Limit이 없으면 한 팀이 다른 팀을 죽입니다.
>
> 핵심 메시지 — **7가지는 "이론상 문제"가 아니에요. 전부 한 번은 만나게 됩니다.** 그래서 앱 코드에 흩어두지 말고 Gateway 한 곳에 모으자는 게 오늘의 주장이에요.

## Slide 4 — Gateway의 한 줄 원칙
**[화면]**
- 큰 문장: **"앱은 Gateway에만 말한다. Gateway가 Provider에게 말한다."**
- 다이어그램: App → Gateway → (Azure / OpenAI / Anthropic / vLLM)

**[스크립트]**
> 이 한 문장이 오늘 섹션의 심장이에요. 외우시면 좋습니다.
>
> **"앱은 Gateway에만 말한다. Gateway가 Provider에게 말한다."**
>
> 이게 무슨 말이냐. 앱 코드 안에는 OpenAI SDK도, Anthropic SDK도, Azure 클라이언트도 들어가지 않아요. 그냥 내부 Gateway에 HTTP 호출 한 번 하는 게 전부입니다. Gateway 뒤에서 실제로 어떤 Provider를 쓰는지, 어떤 모델로 가는지, 재시도는 어떻게 하는지 — 앱은 몰라도 됩니다.
>
> 이 분리가 왜 중요하냐. 앞 페이지에서 본 7가지 책임이 **전부 Gateway 안으로 들어가게** 되거든요. 앱 코드는 순수하게 비즈니스 로직만 남습니다.
>
> 비유하자면 **API Gateway 패턴**과 같아요. 웹 서비스에서 마이크로서비스들 앞에 API Gateway 두는 것처럼, LLM Provider 앞에 LLM Gateway를 두는 겁니다. 이미 알고 계신 패턴을 LLM에 적용했다고 보시면 됩니다.

## Slide 5 — Gateway가 책임질 7가지 (오늘 섹션의 로드맵)
**[화면]**
- 번호 리스트 7개 (오늘 슬라이드 챕터와 1:1 매칭)
  ```
  ┌──────────────────────────────────────────────────────────────┐
  │ 01 통합 인증·Key 관리      ─┐                                 │
  │ 02 라우팅 & Load Balancing ─┤── 이 7 책임이 오늘 섹션의 축    │
  │ 03 Fallback & 재시도       ─┤   각 책임 = 한 Chapter           │
  │ 04 Prompt 관리             ─┤   (Chapter 2 ~ 6 + 횡단 #06·07) │
  │ 05 캐싱 (Prompt·Exact·Semantic) ─┘                             │
  │ 06 관측성·비용 태깅  ─┐                                        │
  │ 07 안전·거버넌스     ─┴── 횡단 관심사 (모든 Chapter에 공통)    │
  └──────────────────────────────────────────────────────────────┘
  ```
- 하단 배너: **"오늘 남은 시간은 이 7 책임을 순서대로 한 챕터씩 깊이 파는 구조"**

**[스크립트]**
> Gateway 안에 들어가야 할 책임을 7가지로 정리했어요. 이 슬라이드가 **오늘 섹션 전체의 로드맵**입니다. 다음 슬라이드부터는 **각 책임마다 한 챕터씩** 깊이 들어갈 거예요.
>
> **01 통합 인증·Key 관리**. 앱은 자기만의 Gateway 토큰 하나만 알면 돼요. OpenAI API Key, Azure Key, Anthropic Key 같은 업스트림 키는 Gateway가 vault에 안전하게 보관합니다. 앱 로그에 찍힐 일도, 개발자 노트북에 돌아다닐 일도 없어요. → **Chapter 2 (Gateway 구축 옵션)**에서 주로 다룹니다.
>
> **02 라우팅 & Load Balancing**. 어떤 요청을 어떤 모델로 보낼지, 같은 모델이어도 어떤 배포본으로 보낼지 결정합니다. 간단한 분류는 싼 모델로, 복잡한 추론은 비싼 모델로 — 이런 규칙을 여기서 적용해요. → **Chapter 3 (라우팅·LB)**의 주제입니다. (기존 "라우팅"과 "LB"를 한 축으로 묶었습니다 — 실무에선 같이 설계되거든요.)
>
> **03 Fallback & 재시도**. Provider가 429(rate limit)나 5xx를 던지면 자동으로 다른 Provider로 전환합니다. 지수 백오프, 멱등성까지 함께 설계하죠. → **Chapter 4**에서 체크리스트로 봅니다.
>
> **04 Prompt 관리** *(이번 개정에서 명시적 책임으로 승격)*. Gateway 뒤에는 프롬프트 레지스트리가 있어야 해요. 버전, A/B, 평가, 관측성이 Prompt에 붙습니다. → **Chapter 5**.
>
> **05 캐싱 (Prompt · Exact · Semantic)**. 같은/비슷한 프롬프트는 재계산할 필요가 없으니 세 유형의 표준 캐시로 걸러냅니다. → **Chapter 6**에서 한 유형씩 봅니다.
>
> **06 관측성·비용 태깅**. 각 요청에 "어느 팀, 어느 서비스, 어느 기능"이라는 태그를 붙여서 비용을 분해해 볼 수 있게 합니다. → **모든 챕터에 횡단**으로 들어가요. Gateway 옵션(Helicone·Portkey), Prompt 관리(Langfuse), 통합 아키텍처 등에서 반복 등장합니다.
>
> **07 안전·거버넌스**. PII 마스킹, 프롬프트 인젝션 탐지, 금칙어 필터, 감사 로그. → 이것도 **횡단**이에요. Gateway 옵션 비교와 Prompt PR 리뷰·배포 챕터에서 등장합니다.
>
> 핵심 메시지 두 가지 — **첫째, 이 중 하나라도 앱마다 흩어져 있다면 그건 기술 부채**예요. 특히 01과 07은 보안·감사팀이 반드시 검증하는 항목이라 Gateway 없이는 조직 차원에서 감사를 통과하기 어렵습니다. **둘째, 오늘 덱은 이 7 책임을 순서대로 깊이 파는 구조**입니다. 지금부터 나올 챕터 표지가 매번 "7 책임 중 어디를 지나고 있는지"를 다시 찍어줄 거예요.

**[스크립트]**
> **Chapter 2 — Gateway 구축 옵션**입니다. 앞 챕터에서 정의한 6가지 책임을 어디에 얹을지, 그 그릇을 고르는 챕터입니다. Cloud Native, SaaS, OSS Framework, 자체 구축 — 이 네 갈래를 한판에 비교하고, OSS Framework 카테고리에서 LiteLLM 관리 콘솔 화면까지 직접 보여드립니다. 한 마디로 **"무엇을 살지"**를 결정하는 챕터입니다.

## Slide 7 — Gateway 구축 옵션 맵
**[화면]**
- 4 카드 (카테고리 분류)
  - 01 Cloud Native — Azure APIM + AI Gateway
  - 02 SaaS — Portkey · Helicone
  - 03 Opensource Framework — LiteLLM **(강조)**
  - 04 자체 구축 — FastAPI 직접 구현

**[스크립트]**
> 그럼 Gateway를 어떻게 만들 거냐, 크게 네 갈래로 분류할 수 있습니다.
>
> **첫째, Cloud Native**. Azure APIM + AI Gateway가 대표예요. Azure 생태계에 있다면 이게 1순위입니다. 네이티브 통합이고, 엔터프라이즈 기능이 전부 들어 있습니다.
>
> **둘째, SaaS**. Portkey, Helicone 같은 상용 서비스입니다. 강점은 **가장 빠른 도입**입니다. 회원가입 → 키 발급 → 한 줄 코드 수정으로 멀티 프로바이더 운영이 시작됩니다. Helicone은 관측성 UI가 압도적이라, 비용이 어디서 새는지 한눈에 보고 싶은 조직에 잘 맞습니다.
>
> **셋째, Opensource Framework**. LiteLLM이 사실상의 표준입니다. MIT 라이선스, 완전 셀프호스팅, 100+ Provider를 OpenAI 호환 API 하나로 통합합니다. SaaS 동급 기능을 무료로, 그리고 데이터를 외부로 보내지 않고 확보할 수 있다는 점이 결정적입니다. 그래서 오늘 강조 카테고리로 잡았습니다.
>
> **넷째, 자체 구축**. FastAPI나 Express로 직접 만드는 길입니다. 가장 자유롭지만 가장 무겁습니다. **규제·거버넌스 요구사항이 기성 솔루션으로 맞지 않거나, 라우팅 로직이 정말 특수할 때만** 자체 구축을 권합니다. 그 외 경우는 기성 솔루션 위에 얇은 커스텀 레이어를 쌓는 쪽이 유지 비용이 훨씬 낮습니다.
>
> 제가 만난 팀들의 흔한 실수 중 하나가 "우리는 특별하니까 자체로 만들자"로 출발했다가, 1년 뒤에 보면 LiteLLM이 이미 해둔 기능을 재구현하고 있는 경우입니다. 자체 구축은 신중하게 결정해야 합니다.

**[스크립트]**
> 앞 장에서 4개 카테고리로 분류했던 옵션들, 실제 결정을 하려면 한판에 정리하고 비교해야 합니다.
>
> **APIM** — 풀네임은 **Azure API Management**입니다. AI 전용 제품이 아닙니다. Azure의 범용 API Gateway 서비스인데, Microsoft가 **AI Gateway 정책 세트**를 따로 내놔서 LLM 프록시로 쓸 수 있게 만들어 둔 것입니다. 핵심 기능은 Backend Pool로 멀티 리전 묶기, 429·5xx에 대한 Retry·Backoff, Circuit Breaker, Token 단위 Rate Limit입니다. 강점은 Azure 생태계와 **네이티브 통합**입니다. Entra ID 인증, Key Vault 키 관리, Application Insights 텔레메트리가 설정 한 번으로 연결됩니다. Azure 중심 조직이면 1순위입니다.
>
> **Portkey · Helicone** — SaaS 카테고리로 묶었습니다. **Portkey**는 250+ Provider 통합과 Fallback·Load Balancing·Semantic Cache·Guardrail·Prompt Library·A/B Test·Virtual Key가 거의 전부 기본 탑재라, 가장 빠르게 프로덕션에 투입할 수 있는 게 강점입니다. **Helicone**은 원래 LLM 관측성 플랫폼으로 시작해서, 요청 로그·비용 대시보드·사용자별 분석 UI가 매우 훌륭합니다. 둘 다 빠른 도입과 가시성을 동시에 잡고 싶은 조직에 적합합니다.
>
> **LiteLLM** — 오늘 강조하는 카테고리, **Opensource Framework**입니다. MIT 라이선스이고 두 가지 형태로 쓸 수 있습니다. Python 라이브러리로 앱에 임베드하거나, Proxy Server로 띄워서 HTTP로 호출하거나. **100+ Provider**를 OpenAI 호환 API 하나로 통합해주고, 앱 코드는 항상 OpenAI SDK 그대로 씁니다. 무료이고 완전 셀프호스팅이 가능해서, 데이터를 외부로 보내지 않습니다. 다음 슬라이드에서 LiteLLM의 관리 콘솔 화면을 직접 보여드립니다.
>
> **자체 구축** — FastAPI나 Express로 직접 만드는 길입니다. 강점은 제어권 100%이고, 단점은 유지비 100%입니다. 기성 솔루션으로 못 맞추는 특수 라우팅이나 규제 요건이 있을 때만 가야 합니다.
>
> 한 줄 의사결정 트리 — **"Azure 중심 → APIM"**, **"빠른 멀티프로바이더 → Portkey·Helicone"**, **"완전 셀프호스팅·무료 → LiteLLM"**, **"기성품 안 맞는 특수 요건만 → 자체 구축"**. 네 카테고리 중 뭘 고를지가 아키텍트 인터뷰 단골 질문입니다.

## Slide 8 — 3가지 라우팅 전략
**[화면]**
- 3 카드
  - 01 Priority Fallback · 02 Weighted LB · 03 Intent/Semantic Routing

**[스크립트]**
> 라우팅 패턴 세 가지를 이해하시면 웬만한 상황에 대응할 수 있어요. 각각 목적이 다릅니다.
>
> **첫째, Priority Fallback**. 목적은 **장애 대응**이에요. 1순위를 정하고, 실패하면 2순위, 그래도 안 되면 3순위로 넘어갑니다. 예를 들어 1순위는 Azure East US, 2순위는 Azure West Europe, 3순위는 OpenAI 직접 호출. 평소엔 1순위만 쓰고, 장애 시에만 넘어가는 구조예요. 트리거는 429나 5xx 같은 실패 응답이 대부분입니다.
>
> **둘째, Weighted Load Balancing**. 목적은 **트래픽 분산과 쿼터 회피**입니다. 가중치 비율대로 **확률 추첨**하는 구조라 요청 내용을 보지 않습니다. 그래서 정석 케이스는 동일 모델을 여러 리전·배포에 균등 분배하는 겁니다 — 예를 들어 GPT-5.4를 Azure East US 50% / West Europe 50%로 나눠서 단일 리전 TPM 쿼터 한계를 회피합니다. A/B 테스트(같은 트래픽을 두 모델에 50/50으로 흘려 품질 비교)에도 정석으로 쓰입니다. "어려운 메일만 Opus로"처럼 콘텐츠를 보고 분기하는 건 Weighted LB로는 불가능합니다 — Intent Routing이나 Cascade의 영역입니다.
>
> **셋째, Intent 또는 Semantic Routing**. 이건 좀 더 똑똑합니다. 쿼리를 먼저 **분류**해서 "이건 코드 관련이네, 이건 요약이네, 이건 복잡한 추론이네" 판단한 다음 각각에 맞는 모델로 보내요. Azure에서 내놓은 **Model Router**가 이걸 자동으로 해주는 서비스예요. 내부에 분류 모델이 있어서 실시간으로 분기합니다.
>
> 어떤 걸 쓸지는 상황에 따라 조합합니다. 보통 **"가용성 위해 Priority Fallback + 비용 위해 Cascade 구조"**가 제일 흔한 패턴이에요. Cascade는 다음 다음 장에서 다룹니다.

## Slide 8-상세 — 라우팅 전략 상세 원리 *(신규)*
**[화면]**
- 3개 블록 (동작 · 트리거/기준 · 구성 요소 · 장단점)
  ```
  ━━ 01 Priority Fallback ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

          예) mini 80% + flagship 20% → 10K 요청 시 8K:2K

  기준:   정적 가중치 (사전 설정)
          동적 가중치 (지연/오류율 기반 자동 조절)
          쿼터 기반 (팀/서비스별 토큰 예산 소진 시 전환)

  구성:   - 각 타겟별 가중치 (합=100%)
          - 분배 알고리즘 (random / round-robin / least-loaded)
          - (옵션) Sticky session (같은 사용자 동일 모델 고정)

  장점:   비용 최적화 + 트래픽 분산 동시 달성
  단점:   확률적 → "이 요청이 어디로 갈지" 예측 불가
          요청별 난이도 차이 무시 (쉬운 건도 비싼 모델 가능)
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ━━ 03 Intent / Semantic Routing ━━━━━━━━━━━━━━━━━━━━━━━━
  동작:   요청을 먼저 분류 → 의도·난이도·도메인별로 모델 선택
          [분류기] → "coding" → GPT-5.4
                  → "simple FAQ" → Haiku 4.5
                  → "complex math" → o4-mini

  분류 방식:
          A) 규칙 기반 (키워드, 정규식) — 가장 단순
          B) 소형 LLM 분류기 (Haiku/nano로 카테고리 판정)
          C) 임베딩 + 유사도 (쿼리 벡터 ↔ 카테고리 벡터)
          D) 매니지드 (Azure Model Router, Portkey Conditional)

  구성:   - 분류기 (B 또는 C가 일반적)
          - 카테고리 → 모델 매핑 테이블
          - Fallback (분류 실패 시 기본 모델)

  장점:   비용·품질 최적화가 "요청별"로 정밀하게 동작
  단점:   분류 단계 자체의 지연·비용 추가 (~50~300ms)
          오분류 리스크 (감사·모니터링 필수)
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ```
- 하단: **"세 전략은 대체재가 아니라 보완재 — 보통 중첩해서 쓴다"**

**[스크립트]**
> 앞 장에서 세 전략의 이름만 언급했으니, 여기서 동작 원리·트리거·구성 요소·장단점을 각각 깊게 봅니다. 장표만 보고 바로 설계에 쓸 수 있을 정도로 풀어드릴게요.
>
> **Priority Fallback부터** 보겠습니다. 동작은 직관적입니다. 우선순위 리스트가 있고, 1순위부터 시도, 실패하면 **다음 타겟으로 즉시 전환**, 또 실패하면 그다음. 중요한 것은 **"실패"의 정의**입니다. 429 rate limit, 5xx 서버 오류, timeout은 당연하고요 — 여기에 **content-filter false positive**를 꼭 넣어야 합니다. Azure·OpenAI 컨텐츠 필터가 정상 요청을 오판해 거부하는 경우가 실제로 있는데, Fallback에 이게 빠져 있으면 그 요청은 영영 못 통과합니다. Circuit Breaker가 open 된 타겟도 트리거로 간주해서 건너뛰어야 합니다.
>
> Priority Fallback은 본질적으로 **cross-target 전환** 그 자체이지, 같은 타겟에 백오프 걸어 재시도하거나 멱등 키로 중복을 막는 영역이 아닙니다. 그건 별개의 책임이고, **Chapter 4 (Fallback & 재시도)**에서 트리거·백오프·Idempotency·관측성 네 요소로 따로 정리합니다. 여기선 "어느 타겟을 어떤 순서로 시도할지"만 보고 가시면 됩니다.
>
> 구성 요소는 우선순위 리스트와 트리거 조건 세트입니다. 장점은 단순하고 예측 가능하고 평상시 비용이 1순위 비용 그대로라는 점입니다. 단점은 다단계 실패 시 **timeout × 단계 수**만큼 사용자 대기가 늘 수 있다는 것. 그래서 각 단계 timeout을 공격적으로(예: 10초) 잡아야 합니다.
>
> **Weighted Load Balancing**. 가중치 비율대로 **확률적 분배**입니다. 50/50 주면 10,000건 요청 중 약 5,000건씩 양쪽에 분배됩니다. 가중치는 세 가지 방식이 있어요. **정적** — 우리가 직접 50:50을 박아두기. **동적** — Gateway가 각 타겟의 지연·오류율을 보고 자동 조절. **쿼터 기반** — 한 타겟의 TPM이 임박하면 자동으로 다른 쪽 비중을 올리기. 구성은 가중치 테이블, 분배 알고리즘(랜덤·라운드로빈·least-loaded 중 택1), 옵션으로 Sticky session(같은 사용자는 같은 타겟에 고정하고 싶을 때)입니다.
>
> 정석 케이스를 짚어야 합니다. **확률적 분배는 요청 내용을 보지 않습니다.** 그래서 가장 잘 맞는 곳은 **동일 모델을 여러 리전·배포에 균등 분배**하는 패턴입니다 — GPT-5.4를 Azure East US 50% / West Europe 50%로 분배하면 단일 리전의 TPM 쿼터 한계를 우회하고, 한 리전 장애에도 절반은 살아있습니다. 같은 모델·같은 가격이라 "확률적 분배"로 인한 품질 변동이 없습니다. 또 다른 정석은 **A/B 테스트** — 같은 트래픽을 GPT-5.4와 Claude Sonnet 4.6에 50/50으로 흘려 품질·비용 비교 데이터를 모으는 용도입니다.
>
> 단점이 중요합니다. **확률적**이라 "어려운 요청은 반드시 큰 모델로"를 보장 못합니다. 가격이 다른 두 모델에 80/20 가중치를 줘도 "어려운 것 20%만 큰 모델로 가는" 게 아니라 "전체의 무작위 20%가 큰 모델로 가고 거기엔 쉬운 것도 어려운 것도 섞입니다". 콘텐츠 기반 분기가 필요하면 Intent Routing이나 Cascade의 영역입니다.
>
> **Intent/Semantic Routing**. 이게 가장 똑똑한 대신 가장 복잡해요. 요청이 들어오면 **분류기**가 먼저 판정합니다 — "이건 coding", "이건 simple FAQ", "이건 complex math". 그 다음에 카테고리에 맞는 모델로 라우팅해요. 분류 방식이 네 가지 있어요. **A) 규칙 기반** — 키워드·정규식 매칭. 가장 단순하고 빠르지만 놓치는 케이스 많음. **B) 소형 LLM 분류기** — Haiku 4.5나 GPT-5.4-nano로 "이 요청의 카테고리는?"을 물어봐요. 50~200ms 정도 추가 지연. **C) 임베딩+유사도** — 쿼리를 벡터화해서 미리 정의된 카테고리 벡터와 cosine similarity 비교. 분류기 호출 없이 수 ms에 판정. **D) 매니지드 서비스** — Azure Model Router, Portkey의 Conditional Routing처럼 공급사가 내장 제공. 구성은 분류기 + 카테고리→모델 매핑 테이블 + 분류 실패 시 Fallback 모델. 장점은 **요청별로 정밀 최적화**되어 Weighted의 "확률적 블러"를 제거한다는 것. 단점은 분류 자체의 지연·비용 추가(분류기 호출이 곧 LLM 호출이면 비용 2배), 그리고 **오분류 리스크**예요. "복잡한 디버깅"을 "simple FAQ"로 잘못 분류해서 Haiku로 보내면 품질이 박살납니다. 그래서 실서비스 도입 시 분류 결과와 실제 결과를 비교하는 **분류 정확도 모니터**를 반드시 같이 붙여야 해요.
>
> 마지막 핵심 — **세 전략은 택일이 아니에요.** 실전 아키텍처는 대부분 세 개가 **중첩**합니다. 예를 들어 Intent Routing으로 큰 모델군(flagship/mid/mini)을 먼저 고르고, 각 군 내에서 Weighted LB로 여러 배포에 분산하고, 각 배포 단위에 Priority Fallback으로 리전 이중화를 걸어요. 설계할 때 "어느 한 전략을 고르자"가 아니라 **"어느 층에 어느 전략을 걸까"**로 접근하세요.

**[스크립트]**
> 세 라우팅 전략을 실전 시나리오로 매칭해보겠습니다.
>
> **Priority Fallback 시나리오** — 실시간 고객 챗봇을 예로 들게요. 평소엔 1순위인 Azure East US로만 보내요. 여기서 429나 5xx, 30초 이상 timeout이 뜨면 자동으로 Azure West Europe으로 전환. 그것도 실패하면 OpenAI 직접 호출. **평상시 비용은 그대로**고, 장애 때만 Fallback이 발동하는 구조예요.
>
> **Weighted LB 시나리오** — 한 가지 흔한 오해를 먼저 짚어야 합니다. "Haiku 80% / Opus 20%로 가중치를 줘서 어려운 메일만 Opus로 보낸다" — 이건 사실 **불가능합니다**. Weighted LB는 요청 내용을 보지 않고 가중치 비율대로 **확률 추첨**하는 구조입니다. 80/20을 줘도 "어려운 메일이 Opus로 간다"가 아니라 "전체의 무작위 20%가 Opus로 가고 거기엔 쉬운 것도 어려운 것도 섞입니다". 어려운 것을 골라 보내려면 Intent Routing이나 Cascade(Slide 18)가 필요합니다.
>
> 그럼 Weighted LB의 정석 케이스는 무엇일까요. **동일 모델을 여러 리전·배포에 분산**하는 겁니다. 예를 들어 GPT-5.4를 Azure East US에 50%, Azure West Europe에 50%로 분배합니다. 단일 리전의 TPM(Token Per Minute) 쿼터 한계를 우회하고, 한 리전 장애가 발생해도 절반은 살아있게 만드는 구조입니다. 같은 가격·같은 모델·같은 품질이라 "확률적 분배"로 인한 품질 변동이 없습니다. 이게 Weighted LB가 가장 잘 하는 일입니다. 또 다른 케이스는 **A/B 테스트** — GPT-5.4 50% / Claude Sonnet 4.6 50%로 같은 트래픽을 흘려서 품질·비용 비교 데이터를 모으는 용도입니다.
>
> **Intent Routing 시나리오** — 개발자 지원 Copilot을 예로 들게요. 사용자 질문을 먼저 분류합니다. "멀티스텝 코딩 작업"이면 Opus 4.7, "간단 FAQ"는 Haiku 4.5, "복잡한 디버깅"은 Reasoning이 필요하니 o4-mini, "초장문 문서 분석"은 2M 컨텍스트가 필요하니 Gemini 3.1 Pro로. 분류는 Portkey Conditional Routing 같은 매니지드 서비스에 맡기거나, 소형 LLM으로 직접 분류기를 돌려도 돼요.
>
> 실무에선 **세 개를 조합**합니다. 예를 들어 Intent Routing으로 모델을 고르고, 각 모델마다 Priority Fallback으로 여러 배포를 걸고, 같은 티어 내에서 Weighted LB로 분산. 하나만 쓰면 한계가 분명해요.

GPT-5.4는 3월 5일 출시된 안정 플래그십이에요. **GPT-5.4-mini**($0.75/$3)는 균형 티어 — 대부분의 요약·분류·생성 업무에 충분한 품질이에요. **GPT-5.4-nano**($0.20/$0.80)가 이 라인업의 최저가입니다. 옛날 gpt-4o-mini 포지션에 있어요. 그리고 **o4-mini**($1.10/$4.40) — o3-mini의 후속으로 나온 Reasoning 전용 모델입니다. 수학·다단계 논리·복잡한 디버깅처럼 "생각이 필요한" 작업용이에요.

Opus 4.6은 여전히 프로덕션 안정판으로 같이 운영됩니다. **Sonnet 4.6**($3/$15)은 균형 티어인데, **128K 출력과 extended thinking(추론 모드)을 같이 지원**하는 게 특징이에요. 긴 결과물이 필요한 보고서 생성·리서치에 맞습니다. **Haiku 4.5**($1/$5)가 가장 빠르고 싼 모델이에요 — Cascade 1단으로 유력합니다.

## Slide 10 — Cascade 라우팅 패턴 (2026-04 모델 기준)
**[화면]**
- 4단 흐름도 + 예상 분포
  ```
                  ┌──────────────────────────────────────────────┐
   Query   ───▶   │ [1] Haiku 4.5 / GPT-5.4-nano  ($1/$5 / nano) │
                  │     → confident? ── Yes ──▶ Response (70%)   │
                  └──────────────────┬───────────────────────────┘
                                     │ No (불충분)
                  ┌──────────────────▼───────────────────────────┐
                  │ [2] Sonnet 4.6 / GPT-5.4-mini ($3/$15 / mid)│
                  │     → confident? ── Yes ──▶ Response (20%)   │
                  └──────────────────┬───────────────────────────┘
                                     │ No
                  ┌──────────────────▼───────────────────────────┐
                  │ [3] Opus 4.7 / GPT-5.4 / Gemini 3.1 Pro      │
                  │     → 답변 반환 (7%)                          │
                  └──────────────────┬───────────────────────────┘
                                     │ (추론 요구 감지 시에만)
                  ┌──────────────────▼───────────────────────────┐
                  │ [4] o4-mini / Opus 4.7 extended thinking     │
                  │     → 최종 답변 (3%)                           │
                  └──────────────────────────────────────────────┘
  ```
- 우측 박스: **"70%가 1단에서 종결 → 평균 토큰 비용 5~10배↓, 평균 지연 3배↓"**
- 각주: *비율은 FAQ/요약 유형 워크로드 기준 실측치. 도메인마다 다름.*

**[스크립트]**
> Cascade는 비용 최적화 패턴의 대표선수예요. 직역하면 "폭포"인데, 이름처럼 상위에서 아래로 흘러내리는 구조예요. 2026년 4월 기준 모델로 다시 그리면 보통 **4단**까지 설계합니다.
>
> **1단 — 저가 티어**. Claude Haiku 4.5($1/$5) 또는 GPT-5.4-nano($0.20/$0.80)로 시작해요. 분류, FAQ, 간단한 요약, 짧은 생성은 여기서 끝납니다. 실무 워크로드 통계를 보면 이 단계에서 **약 70%가 종결**돼요.
>
> **2단 — 균형 티어**. 1단이 "자신 없다"고 판단하면 한 단계 올립니다. Claude Sonnet 4.6($3/$15) 또는 GPT-5.4-mini($0.75/$3). 고객 문의 요약, 구조화된 생성, 중간 난이도 추론이 여기서 해결돼요. 보통 **20% 추가가 이 단계**에서 끝납니다.
>
> **3단 — 플래그십 티어**. Claude Opus 4.7, GPT-5.4/5.5, Gemini 3.1 Pro. 여기까지 올라가면 진짜 어려운 요청이라는 뜻이에요. 전체의 **약 7%**가 이 단계에 도달합니다. 긴 컨텍스트가 필요하면 Gemini 3.1 Pro(2M), 코딩·Agent면 Opus 4.7, 일반 복합 질의면 GPT-5.4/5.5로 분기하는 식이죠.
>
> **4단 — Reasoning 티어**. 이건 "모든 요청"이 거쳐야 하는 단계가 아니에요. 3단에서 응답을 봤는데 "다단계 추론이 필요한 문제였다"는 신호(예: 수식 에러, 논리 불일치, 검증 LLM의 지적)가 잡히면 o4-mini($1.10/$4.40) 또는 **Opus 4.7의 extended thinking 모드**로 다시 돌립니다. **약 3%**가 이 단계까지 옵니다. 얼마 안 되지만, 이 3%가 "서비스 품질의 상한"을 결정해요.
>
> 이 분포면 평균 토큰 비용이 **플래그십 단일 운영 대비 5~10배 절감**됩니다. 평균 지연도 3배 가까이 줄어요 — 대부분이 저가·빠른 모델에서 끝나니까요.
>
> 단계 간 승격 기준 — 즉 "자신 없음을 무엇으로 판정할 것인가"는 별도의 설계 영역입니다. log-prob, 구조 검증, 평가 LLM, self-consistency 등 여러 방법이 있고 각각 비용·정확도 trade-off가 다른데, 본 슬라이드 흐름에선 다루지 않습니다. 운영 측면의 안전한 출발점만 짚자면 — 너무 엄격하면 대부분이 플래그십까지 올라가서 Cascade 의미가 없고, 너무 느슨하면 품질이 떨어집니다. **초기 튜닝은 평가셋 100건에서 1/2/3/4단 분포가 70/20/7/3에 가깝게 나오도록** 임계치를 맞추는 게 안전합니다.

## Slide 11 — Fallback 설계 체크리스트
**[화면]**
- 4개 항목
  - 트리거 · 백오프 · Idempotency · 관측성

**[스크립트]**
> Fallback은 단순히 "재시도하는 것"이 아니에요. 네 가지를 같이 설계해야 합니다.
>
> **1번, 트리거**. 어떤 상황에서 Fallback할지 정해야 해요. 429 rate limit, 5xx 서버 오류, timeout — 여기까진 상식입니다. 그런데 **content-filter false-positive**도 꼭 넣으세요. 무슨 뜻이냐, Azure나 OpenAI의 컨텐츠 필터가 "이건 부적절한 요청"이라고 오판해서 거부하는 경우가 있어요. 실제론 정상 요청인데도요. 이때 다른 Provider로 Fallback하는 설정이 있어야 운영이 안정됩니다.
>
> **2번, 백오프**. 여기서 한 가지 오해가 흔히 발생합니다. "Fallback에는 늘 지수 백오프를 건다"는 건 절반만 맞는 얘기입니다. 백오프는 **같은 타겟에 다시 쏠 때만** 의미가 있어요. OpenAI가 과부하라서 429를 던졌다면, 1~2초 기다렸다 OpenAI에 다시 쏘는 게 맞습니다. 그런데 Anthropic으로 fallback 이동한다면? Anthropic은 OpenAI 장애와 무관하니 **즉시** 보내야 합니다. 그래서 실무 모델은 두 가지를 분리합니다. **같은 타겟 재시도** — 지수 백오프(1s → 2s → 4s)에 ±20% jitter, **LLM은 1~2회만** 권장. 또 서버가 `Retry-After` 헤더를 주면 우리가 계산한 백오프 값 대신 그 값을 우선 존중해야 합니다.
>
> **3번, Idempotency**. 이게 정말 중요한데 많은 팀이 놓칩니다. Agent가 Tool 호출한 뒤 응답이 실패해서 Fallback으로 재시도한다고 해봅시다. 그 Tool이 **이메일을 보내는 함수**였다면? 이메일이 두 번 갑니다. **결제를 처리하는 함수**였다면? 결제가 두 번 돼요. 그래서 모든 Fallback 경로에 **멱등 키(idempotency key)** 를 붙여서, 같은 요청이 두 번 들어와도 한 번만 실제 실행되게 만들어야 합니다.
>
> **4번, 관측성**. "왜 Fallback됐는가"가 trace에 기록돼야 해요. 나중에 분석할 때 "Primary가 왜 실패했지?" 추적이 안 되면 문제 해결이 불가능합니다. 로그에 Fallback 발생 시점, 이유, 대체 경로를 꼭 남기세요.

**[스크립트]**
> **Chapter 5 — Prompt 관리**입니다. 여기서부터 성격이 살짝 바뀝니다. 앞 네 챕터가 "요청을 어디로 어떻게 보낼까"에 관한 것이었다면, 이 챕터는 "**요청의 내용 자체(= 프롬프트)를 어떻게 관리할 것인가**"를 다룹니다. 오늘 섹션에서 강사가 가장 강조하는 메시지 — **"프롬프트는 코드다"** — 가 여기서 나옵니다. 그 원칙을 정의하고, Langfuse·PromptLayer·Braintrust 같은 대표 툴의 차이를 비교한 뒤 마무리합니다.

## Slide 13 — Prompt는 Code다
**[화면]**

**[스크립트]**
> 이번엔 프롬프트 관리 이야기예요. 제가 이 섹션에서 가장 강조하고 싶은 메시지가 있어요.
>
> **"프롬프트는 코드다."**
>
> 많은 팀이 프롬프트를 코드와 다르게 취급합니다. 개발자가 앱 코드에 문자열로 때려박거나, Notion 문서에 적어두고 복사해서 붙여 넣거나, Slack에서 주고받아요. 이게 바로 사고의 근원입니다.
>
> 왜 코드처럼 취급해야 하냐. 프롬프트는 **프로덕션 입력**이에요. 한 글자만 바꿔도 전체 출력 분포가 바뀝니다. "친절하게 답하세요"를 "간단하게 답하세요"로 바꾸면 응답 길이가 절반으로 줄 수도 있어요. 그 변경이 실서비스에 어떻게 영향 미칠지 예측이 안 되는 상태에서 운영자가 그냥 바꿔버리는 거죠.
>
> 그래서 네 가지가 필요합니다.
>
> **Git 버전**. 프롬프트도 Git에 들어가야 해요. 언제 누가 왜 바꿨는지 이력이 남아야 합니다.
>
> **PR 리뷰**. 프롬프트 변경도 리뷰어 승인이 있어야 해요. 한 사람이 독단으로 바꾸면 안 됩니다.
>
> **배포·롤백**. 변경이 서비스에 반영될 때도 단계적으로 올라가야 하고, 문제 생기면 즉시 롤백할 수 있어야 해요.
>
> **자동 Eval**. 프롬프트 변경 시 자동으로 평가셋이 돌아서 회귀가 없는지 확인해야 합니다.
>

## Slide 17 — LLM 캐시 3가지 표준 유형
**[화면]**
- 3 카드 (업계 표준 용어: Portkey · LiteLLM · Langfuse · Redis 공통)
  ```
  ┌─ 01 Prompt Cache ────────────────────────────────────┐
  │ 관리: Provider (OpenAI·Anthropic·Google)              │
  │ 매칭: 프롬프트 prefix (토큰 단위)                      │
  │ 효과: 캐시된 입력 토큰 50~90%↓ · 지연 최대 85%↓        │
  │ 리스크: 매우 낮음 · 거의 즉시 활성화 가능               │
  └──────────────────────────────────────────────────────┘
  ┌─ 02 Exact Cache ─────────────────────────────────────┐
  │ 관리: Gateway (Redis·KV store)                        │
  │ 매칭: 전체 프롬프트 해시 (완전 일치)                   │
  │ 효과: LLM 호출 0 · 지연 ~10ms · 비용 0                 │
  │ 리스크: 낮음 · 키 설계(모델 버전 포함)만 지키면 됨      │
  └──────────────────────────────────────────────────────┘
  ┌─ 03 Semantic Cache ──────────────────────────────────┐
  │ 관리: Gateway (VectorDB · GPTCache·Redis·Qdrant)      │
  │ 매칭: 임베딩 cosine 유사도 (의미 일치)                 │
  │ 효과: 적중률 10~70% (도메인별) · 임베딩 오버헤드 5~20ms │
  │ 리스크: 높음 · 오적중 시 엉뚱한 답 반환 가능            │
  └──────────────────────────────────────────────────────┘
  ```
- 하단: **"분류 축: (가) 누가 관리하나 · (나) 무엇을 매칭하나"**

**[스크립트]**
> 이제 비용을 크게 줄일 수 있는 주제, 캐싱입니다. LLM 서비스에서 캐시는 그냥 "있으면 좋은 것"이 아니라 **필수 구성 요소**예요. 같은 질문을 두 번 받으면 두 번 계산하는 건 낭비입니다.
>
> **2026년 기준 LLM 서비스 캐시는 업계가 합의한 3가지 표준 유형이 있어요.**  **Prompt Cache, Exact Cache, Semantic Cache.**
>
> 분류 축이 두 개입니다. **(가) 누가 관리하나** — Provider가 자동 관리하느냐, Gateway가 직접 관리하느냐. **(나) 무엇을 매칭하나** — 프롬프트의 prefix 토큰이냐, 전체 해시냐, 의미적 유사도냐. 이 조합으로 세 가지가 자연스럽게 나뉩니다.
>
> **① Prompt Cache** — **Provider가 관리**하고 **프롬프트 prefix**를 재사용합니다. OpenAI·Anthropic·Google이 내부적으로 "이 프롬프트의 앞부분을 본 적 있으니 다시 계산하지 않겠다"고 판단해요. 입력 토큰 비용이 **50~90%까지** 떨어지고 지연도 크게 줄어요. 리스크가 거의 없어서 **가장 먼저 도입**하는 캐시입니다.
>
> **② Exact Cache** — **Gateway가 직접 관리**하고 프롬프트 전체를 **해시로 완전 일치** 매칭합니다. Redis에 `hash(model+prompt+params) → response`로 저장해요. 히트하면 **LLM 호출 자체가 0**, 지연 10ms 이하, 비용 0. 구현이 단순해서 FAQ·정적 응답 같은 반복 트래픽에 **즉효약**입니다.
>
> **③ Semantic Cache** — 가장 똑똑하지만 가장 까다로워요. **의미가 비슷한 프롬프트까지** 캐시로 처리합니다. 질문을 임베딩해서 VectorDB에 저장된 기존 질문들과 cosine 유사도를 비교하고, 임계치 이상이면 캐시된 응답을 반환해요. "비밀번호 어떻게 바꿔요?"와 "비번 변경법"을 같은 걸로 인식하는 거죠. 다만 **오적중 리스크**가 있어서 도입에 신중해야 합니다.
>
> 세 유형의 역할이 완전히 다르고, **도입 순서·리스크·성능 특성도 다릅니다.** 다음 장부터 각 유형마다 **"개념(무엇인가) → 구현(어떻게 하나)"** 순서로 풀어가고, 마지막 장에서 도입 순서를 정리하겠습니다.

> 다음 두 슬라이드(원리·프로바이더 비교)에 들어가기 전에, **Prompt Cache가 뭔지 한눈에** 짚고 갑시다.

> 한마디로 **"같은 prefix는 다시 계산하지 않는다."** 위쪽 그림이 토큰 시퀀스 단위로, 아래쪽 그림이 실제 자연어 프롬프트로 같은 메시지를 다른 추상화 수준에서 보여줘요.
>
> 왼쪽이 원본 프롬프트입니다. 한 번 처리되면 그 KV-state가 GPU 메모리에 임시 저장돼요. 다음 요청이 들어왔을 때 prefix가 **완전히 동일하면 Cache Hit**(초록) — 저장된 KV를 그대로 재사용해서 prefill 단계를 통째로 건너뜁니다. 비용과 지연이 동시에 떨어져요.
>
> 반대로 prefix가 **단 한 토큰이라도 다르면 Cache Miss**(주황). 아래 예시에서 `Act` 대신 `Behave`로 시작하는 순간 뒤 문장이 다 똑같아도 처음부터 다시 prefill입니다. 이게 "prefix만 캐시 가능하다"의 시각적 정의예요.
>
> 다음 슬라이드에서 **왜 이렇게 동작하는지**(원리), 그 다음 슬라이드에서 **프로바이더별로 어떻게 활성화하는지**(비교)를 봅니다.

## Slide 17-원리 — Prompt Cache는 왜·어떻게 작동하는가 *(신규)*
**[화면]**
- 3단 레이아웃: (A) 비용 구조 · (B) 작동 원리 · (C) 매칭 흐름
  ```
  ─── (A) LLM 추론의 2단계 비용 구조 ─────────────────────────────
  ┌─────────────────────────────────────┬─────────────────────────┐
  │ 1. Prefill (입력 전체 처리)          │ 2. Decode (토큰 생성)    │
  │   · 입력 N 토큰을 병렬로 처리         │   · 한 토큰씩 순차 생성  │
  │   · GPU 연산 O(N²)                   │   · 생성 토큰당 1회      │
  │   · 전체 지연의 60~80% 차지           │   · 캐시 불가능          │
  │   · ◀── Prompt Cache가 노리는 지점 ──│                         │
  └─────────────────────────────────────┴─────────────────────────┘

  ─── (B) 왜 "prefix만" 가능한가 ────────────────────────────────
  ┌─────────────────────────────────────────────────────────────┐
  │  Transformer = Causal Attention                              │
  │                                                              │
  │  Token[n]의 KV-state = f(Token[0], Token[1], …, Token[n])   │
  │                                                              │
  │  → 앞쪽 토큰이 하나라도 다르면 뒤쪽 KV-state 전부 무효        │
  │  → 반대로 prefix가 완전히 동일하면 그 구간 KV 재사용 가능     │
  │                                                              │
  │  따라서 "가변 값은 뒤로, 불변 값은 앞으로"가 물리적 제약      │
  └─────────────────────────────────────────────────────────────┘

  ─── (C) 매칭 흐름 (Block-level prefix hashing) ────────────────
     Request ──→ tokenize ──→ split into blocks (보통 1024 토큰)
                                     │
                                     ▼
                          block[0] hash == 기존 block[0]?
                                Yes │  No
                                    ▼  └──→ miss → prefill 전부 새로
                          block[1] hash == 기존 block[1]?
                                Yes │  No
                                    ▼  └──→ 앞 1블록만 재사용, 뒤부터 prefill
                                 … (계속)
                                    ▼
                        최장 일치 prefix 만큼 KV 재사용
                        + 뒤 블록부터는 새로 prefill
                        → 입력 토큰 비용 = (재사용 × 0.1~0.5) + (새 × 1.0)
                        → TTFT = 새로 처리할 토큰 수에 비례
  ```
- 하단 3줄 요약
  ```
  · 재사용 단위 = 블록(1024~4096 토큰) 단위 prefix 매치
  · 비용 절감 근원 = Prefill 연산(O(N²))을 건너뜀 → 입력 토큰 단가 급락
  · TTL의 이유 = GPU 메모리에 KV 보관 → 공간 유한, 미사용 시 evict
  ```

**[스크립트]**
> Prompt Cache를 활성화 "방법"만 알고 쓰면 금방 한계에 부딪혀요. **왜 prefix만 되는지, 왜 비용이 떨어지는지, 왜 TTL이 짧은지**를 이해하면 프롬프트 설계·디버깅이 훨씬 정확해집니다. 이 한 장에서 물리적 원리 세 가지를 설명할게요.
>
> **(A) 왜 비용이 떨어지는가 — Prefill과 Decode의 구분**
>
> LLM 추론은 **두 단계**로 나뉩니다. 첫째는 **Prefill** — 입력 프롬프트 N개 토큰을 **한 번에 병렬로** 처리해서 attention KV-state를 계산하는 단계. 계산량은 대략 **O(N²)** 이라 입력이 길수록 기하급수적으로 무거워져요. 둘째는 **Decode** — 출력 토큰을 한 개씩 순차로 생성하는 단계. 생성 토큰당 1회씩 도는 가벼운 루프입니다.
>
> 보통 긴 프롬프트 짧은 응답 시나리오(RAG, 장문 분석)에서는 **Prefill이 전체 지연의 60~80%를 차지**해요. Prompt Cache가 노리는 지점이 바로 이 Prefill입니다. **이미 계산한 KV-state를 재사용하면 Prefill을 건너뛸 수 있고**, 그만큼 비용과 TTFT가 동시에 떨어져요. Decode는 캐시 대상이 아니에요 — 매번 새로 생성되는 토큰이니까요.
>
> **(B) 왜 prefix만 가능한가 — Causal Attention의 제약**
>
> Transformer의 attention은 **causal** — 위치 n의 토큰은 위치 0..n까지만 볼 수 있어요. 따라서 Token[n]의 KV-state는 **수학적으로** f(Token[0], …, Token[n])입니다. 앞쪽 토큰이 하나라도 바뀌면 그 뒤의 모든 KV-state가 다시 계산돼야 해요.
>
> 이게 "**prefix만 캐시 가능**"의 물리적 이유입니다. 프롬프트의 중간 어딘가가 달라지면 그 뒤는 전부 다시 prefill해야 해요. 반대로 앞부분이 완전히 똑같으면 그 구간만큼은 그대로 재사용 가능합니다.
>
> 그래서 앞 장에서 본 **"불변 prefix 먼저, 가변 suffix 뒤"** 설계 원칙은 컨벤션이 아니라 **물리적 제약**이에요. "현재 시각: {now}"를 시스템 프롬프트 맨 앞에 두면 매 호출마다 prefix가 달라져서 캐시가 하나도 안 먹히는 이유가 여기 있습니다.
>
> **(C) 어떻게 매칭되는가 — Block-level Hashing**
>
> 실제 매칭은 토큰 단위가 아니라 **블록 단위**로 일어나요. Provider마다 다르지만 보통 **1,024 ~ 4,096 토큰**을 한 블록으로 묶고, 블록 해시를 비교해서 최장 일치 prefix를 찾습니다. OpenAI는 1024, Anthropic은 모델별로 1024~2048, Gemini는 4096 정도로 알려져 있어요 — 다음 슬라이드에서 자세히 봅니다.
>
> 블록 단위라서 생기는 실무 함의 두 가지. **첫째, 블록 경계를 넘지 못하는 작은 변경은 캐시 무효화가 없어요** — 예를 들어 Few-shot 예시 하나 추가하면 그 예시가 속한 블록부터만 새로 prefill됩니다. **둘째, 최소 임계치 미만 prompt는 캐시 대상이 안 됩니다** — 1,024 토큰 미만이면 아예 캐시 판정 자체를 안 해요. 짧은 프롬프트에 Prompt Cache가 안 먹히는 이유입니다.
>
> **TTL이 짧은 이유** — KV-state는 GPU 메모리에 보관됩니다. GPU 메모리는 유한하고 비싸요. Provider는 **LRU나 TTL 기반으로 오래된 KV를 주기적으로 evict**합니다. OpenAI 자동 TTL이 5~10분, Anthropic ephemeral이 5분인 이유가 여기 있어요 — 더 오래 붙잡으면 공간이 모자라 전체 처리량이 떨어집니다. Anthropic이 돈을 더 받고 1시간 persistent를 제공하는 것도 **본질적으로 GPU 자원 예약 비용**이에요.
>
> **정리** — Prompt Cache는 "같은 prefix면 무료"가 아니라 **"Prefill 연산을 GPU 메모리 임시 저장으로 우회"** 하는 최적화입니다. 이 구조를 이해하면 다음 세 가지가 설계에 자연스럽게 들어옵니다.
>
> 1. 프롬프트 맨 앞에는 절대 dynamic value를 넣지 않는다
> 2. Few-shot 예시나 tool 정의는 고정된 순서로 유지한다 (순서만 바뀌어도 hash 달라짐)
> 3. 짧은 프롬프트(수백 토큰)에는 Prompt Cache 의존하지 말고 Exact Cache로 간다

**[화면]**
- 3 프로바이더 비교 (2026-04 기준)

- 설계 팁 박스: **"불변 prefix → 가변 suffix" 구조가 캐시 적중률의 전부**
  ```
  [System Prompt]  [Few-shot 예시]  [도구 정의]  ←── 불변 (캐시됨)
  [사용자 질의]  [세션 컨텍스트]  [Timestamp]  ──→ 가변 (캐시 안 됨)
  ```
- 출처: Anthropic Docs — *Prompt caching* (2026-02-05 워크스페이스 격리 변경 반영)

**[스크립트]**
> Prompt Cache는 **가장 먼저 도입해야 할 캐시**입니다. 거의 공짜로 큰 이득을 보거든요. 3대 프로바이더 모두 2026년 4월 기준 지원하고 있어서 골라 쓸 필요도 없어요 — 여러분이 쓰는 프로바이더의 방식을 그대로 활성화하면 됩니다.
>
> **OpenAI**는 가장 단순해요. **자동 활성**이라 설정할 게 없습니다. prefix가 1,024 토큰을 넘기면 자동으로 캐시되고, 같은 prefix로 시작하는 요청이 오면 캐시된 입력 토큰에 **50% 할인**을 줍니다. TTL은 자동으로 5~10분 정도 유지돼요.
>
> **Anthropic**은 **명시적 제어**가 핵심이고, 2026년 들어 사양이 꽤 많이 정리됐어요. 네 가지를 같이 봅시다.
>
> **(1) 활성화** — `cache_control: {type: "ephemeral"}` 필드를 캐시하고 싶은 블록(시스템 메시지, 도구 정의, 메시지)에 붙이면 됩니다. **요청당 최대 4개의 breakpoint**까지 찍을 수 있어요. 5분이 기본이고, `ttl: "1h"`로 1시간으로 늘릴 수 있습니다. **1시간 캐시는 2026-04 기준 GA** — 베타 아니에요.
>
> **(2) 가격** — 이 부분이 헷갈리는데 한 번에 정리합시다. 기준은 일반 입력 토큰 가격입니다. **캐시 읽기는 ×0.1**, 즉 90% 절감. **쓰기는 ×1.25** (5분) 또는 **×2.0** (1시간) — 처음 쓸 때 약간의 추가 비용을 내고, 그 다음부터는 거의 공짜로 읽는 구조예요. 그래서 같은 prefix가 **2회 이상 호출**되면 평균 비용이 미적용 대비 80% 이상 떨어집니다. 1회만 호출되면 오히려 손해예요 — 자주 재사용되는 prefix만 골라서 breakpoint를 찍으세요.
>
> **(3) 모델별 최소 prefix** — 모델마다 다릅니다. **Opus 4.7·4.6·4.5와 Haiku 4.5는 4,096 토큰**, **Sonnet 4.6은 2,048 토큰**. 이 미만이면 breakpoint를 찍어도 캐시가 활성화되지 않아 요. 시스템 프롬프트가 짧으면 효과가 안 나니 길이 확인부터 하세요.
>
> **(4) 운영상 함정 두 가지** — **첫째**, 2026년 2월 5일부터 Claude API의 캐시 격리가 **조직 단위 → 워크스페이스 단위**로 좁혀졌어요. 워크스페이스가 분리돼 있으면 캐시도 분리됩니다(Bedrock·Vertex는 그대로 조직 단위). **둘째**, 룩백 윈도우 **20 블록 제한** — 다중 턴 대화가 길어지면 새 breakpoint를 추가로 찍어줘야 옛 대화 prefix가 캐시에서 사라지지 않아요.
>
> **Google Gemini**는 `CachedContent` API로 명시적 관리를 해요. 큰 시스템 프롬프트나 2M 컨텍스트 문서를 먼저 cache로 등록하고, 이후 요청에서 그 cache ID를 참조합니다. 장문 문서 반복 질의에 특히 강점이 있어요 — **75% 입력 토큰 절감**과 임의 TTL 지정.
>
> 여기서 아키텍트 관점의 **핵심 설계 팁** — 프롬프트를 짤 때 **"불변 prefix 먼저, 가변 suffix 뒤"** 구조를 지키세요. 이게 모든 Prompt Cache의 효율을 결정합니다.
>
> 보통 프롬프트는 네 덩어리로 구성돼요 — 시스템 프롬프트 + Few-shot 예시 + 도구 정의 + 사용자 질의. 앞 세 개는 **매 호출마다 거의 똑같습니다.** 이걸 prefix에 두고, 변하는 사용자 질의·세션 컨텍스트를 뒤에 두면 캐시가 거의 100% 히트해요. 반대로 "현재 시각: {now}" 같은 동적 값을 맨 앞에 두면, 매 호출마다 prefix가 달라져서 캐시가 **하나도 안 먹힙니다.**
>
> 실무에서 가장 흔한 실수 — **디버깅용 request-id나 timestamp를 시스템 프롬프트 맨 앞에 넣는 것.** 이것만 수정해도 청구서가 즉시 절반으로 떨어집니다.

## Slide 19-개념 — Exact Cache는 무엇인가 *(신규)*
**[화면]**
- 시각 자료: "전체 문자열이 똑같아야 캐시 히트" 개념도 (drawio/SVG 인라인)
  ```
  Stored entry — "비밀번호 어떻게 바꾸나요?"   →   hash = a1b2c3…

  ┌─ 들어오는 쿼리 ─────────────────────────┬─ hash ─┬─ 결과 ──────┐
  │ "비밀번호 어떻게 바꾸나요?"              │ a1b2c3 │ ✓ Cache HIT │
  │ "비밀번호  어떻게 바꾸나요?"  (공백 1개) │ 7f9d22 │ ✗ Cache MISS│
  │ "비밀번호 어떻게 변경하나요?" (단어)     │ 4e2c8a │ ✗ Cache MISS│
  │ "How to change my password?" (영어)    │ b88e1f │ ✗ Cache MISS│
  └─────────────────────────────────────────┴────────┴─────────────┘
  ```
- 핵심 메시지
  ```
  · 매칭 단위 = "전체 프롬프트 + 파라미터 + 모델"의 해시
  · 한 글자·한 공백·temperature 차이도 → 다른 키 → 캐시 미스
  · 의미가 같아도 글자가 다르면 캐시는 모름 (그건 Semantic Cache의 영역)
  · normalize(공백·줄바꿈) + 모델 버전 키 포함이 필수
  ```

**[스크립트]**
> Exact Cache의 정의는 이름 그대로예요 — **"완전 일치"** 캐시입니다. 들어온 프롬프트 전체를 해시해서 Redis 같은 KV에 저장하고, 다음 요청의 해시가 같으면 저장된 응답을 그대로 돌려줍니다. **LLM 호출이 아예 안 일어나요.**
>
> 핵심은 **"한 글자라도 다르면 다른 키"**라는 점. 표를 봅시다 — "비밀번호 어떻게 바꾸나요?"가 캐시에 있을 때, 들어오는 쿼리가 글자도 똑같고 띄어쓰기까지 똑같으면 히트입니다. 반면 **공백이 하나 더 있거나, "변경"으로 단어가 바뀌었거나, 영어로 번역된 같은 의미의 질문**이면 — Exact Cache는 다 다른 키로 처리해요. **의미를 모르거든요.**
>
> 그래서 두 가지가 따라옵니다. **첫째**, 프롬프트를 키로 만들 때 **공백·줄바꿈을 정규화**하지 않으면 적중률이 의미 없이 떨어져요. **둘째**, 의미적으로 비슷한 질문까지 잡고 싶으면 — 그건 다음에 볼 **Semantic Cache의 영역**입니다.
>
> Exact Cache가 빛나는 곳은 **반복이 정말 똑같은 트래픽** — FAQ 챗봇의 정형 질문, 배너 텍스트 생성 요청, 공지사항 요약처럼 입력이 거의 그대로 다시 들어오는 시나리오예요. 다음 장에서 키 설계와 흐름을 봅니다.

## Slide 19 — Exact Cache (Gateway)
**[화면]**
- 동작 흐름도
  ```
         ┌───────────┐    hit    ┌──────────────┐
  Query→ │ Hash Key  │──────────→│ Redis GET    │──→ Response (10ms)
         │ Lookup    │           └──────────────┘
         └─────┬─────┘    miss
               │
               ▼
         ┌──────────┐      ┌─────────┐     ┌──────────┐
         │ LLM Call │ ───→ │ SET     │ ──→ │ Response │
         │          │      │ w/ TTL  │     │          │
         └──────────┘      └─────────┘     └──────────┘
  ```
- 키 설계 필수 요소
  ```
  cache_key = hash(
      model_id + model_version   ←── 반드시! (stale 응답 방지)
      + normalized_prompt        ←── 공백·줄바꿈 정규화
      + temperature + top_p      ←── 비결정성 파라미터
      + max_tokens + tools_hash  ←── 응답에 영향 주는 모든 것
  )
  예시: claude-opus-4-7-20260416-abc123def...
  ```
- TTL 가이드
  ```
  · 정적 응답 (공지·FAQ)    : 24h~7d
  · 동적 응답 (사용자 컨텍스트): 1h~6h
  · 실험·디버깅               : 5~15분
  · 기본값                   : 1h
  ```

**[스크립트]**
> Exact Cache는 우리가 직접 운영하는 Gateway 내부 캐시입니다. 구현은 단순한데, **키 설계를 잘못하면 스테일 데이터 재앙**이 옵니다. 설계 포인트에 집중해서 볼게요.
>
> **동작 흐름**은 직관적이에요. 요청이 들어오면 먼저 해시 키를 생성하고 Redis에서 조회합니다. 히트하면 10ms 내에 응답 반환, 끝. 미스면 LLM 호출 → 응답을 TTL과 함께 SET → 클라이언트로 전달. 다음 동일 요청부터 히트가 쌓입니다.
>
> **키 설계가 이 패턴의 전부**예요. 네 가지 요소가 해시에 반드시 들어가야 합니다.
>
> **첫째, model_id + model_version**. 이게 제일 중요합니다. 모델을 업그레이드했는데 키가 같으면 낡은 응답이 캐시에서 흘러나와요 — 사용자는 새 모델을 쓰고 있다고 생각하는데 실제론 옛 응답이 나가는 겁니다. 그래서 `claude-opus-4-7-20260416-abc123...`처럼 **버전·날짜까지** 키에 넣어야 해요. 모델 업그레이드가 자연스럽게 캐시 무효화로 이어집니다.
>
> **둘째, normalized_prompt**. 프롬프트 원문을 그대로 쓰지 말고 **공백·줄바꿈 정규화**를 한 번 거치세요. 안 그러면 "hello  world"와 "hello world"(공백 2개 vs 1개)가 다른 키가 돼서 캐시 적중률이 급감합니다.
>
> **셋째, 비결정성 파라미터**. `temperature`, `top_p`, `seed` 등은 응답 분포를 바꾸는 값이라 키에 포함해야 합니다. temperature=0.7의 응답을 temperature=0.0 요청에 주면 안 되죠.
>
> **넷째, tools_hash와 max_tokens**. Tool 정의가 바뀌면 응답이 달라지므로 도구 정의의 해시도 키에 포함. max_tokens도 응답 길이가 잘릴 수 있어 포함.
>
> **TTL 설계**는 응답의 성격에 따라 나뉩니다. 공지사항·FAQ 요약처럼 **정적 응답**은 24시간~7일로 길게. 사용자 컨텍스트가 섞인 **동적 응답**은 1~6시간. 실험·디버깅 중이면 5~15분으로 짧게. 기본값으로 시작한다면 **1시간이 무난**합니다.
>
> 이 패턴이 효과 큰 시나리오 — **FAQ 챗봇, 배너 텍스트 생성, 공지사항 요약, 반복 번역, 테스트 환경에서의 개발 반복 호출.** 트래픽 헤드에 Exact Cache 한 장 붙이면 월 청구서의 30~50%가 즉시 사라지는 경우도 많아요.

## Slide 20-개념 — Semantic Cache는 무엇인가 *(신규)*
**[화면]**
- 시각 자료: "의미가 비슷하면 캐시 히트" 개념도 (drawio/SVG 인라인)
  ```
  Stored entry — "비밀번호 어떻게 바꾸나요?"  →  embedding [0.12, -0.34, …]

  ┌─ 들어오는 쿼리 ──────────────┬─ cosine ─┬─ 결과 (threshold 0.90) ────┐
  │ "비밀번호 어떻게 바꾸나요?"   │  1.000   │ ✓ Cache HIT (동일)         │
  │ "비번 변경법 알려줘"           │  0.94    │ ✓ Cache HIT (의미 같음)    │
  │ "패스워드 바꾸는 방법"         │  0.93    │ ✓ Cache HIT (의미 같음)    │
  │ "How to change password?"   │  0.88    │ △ threshold 따라 (경계)   │
  │ "계정 어떻게 삭제하나요?"      │  0.62    │ ✗ Cache MISS               │
  └──────────────────────────────┴──────────┴────────────────────────────┘
  ```
- 핵심 메시지
  ```
  · 매칭 단위 = 임베딩 cosine 유사도 ≥ threshold
  · 글자가 달라도 의미가 같으면 HIT — Exact Cache가 못 잡는 영역
  · 임계치(threshold) 한 줄이 적중률·오적중을 동시에 좌우
  · 위험한 한 가지: "계약 해지" vs "계약 체결"처럼 의미는 정반대인데
    단어가 겹쳐 유사도가 높아지는 오적중(false positive)
  ```

**[스크립트]**
> Semantic Cache는 한 단어로 정의하면 **"의미 기반 캐시"**예요. Exact Cache가 글자 수준에서 멈춘 자리에서 한 단계 더 나아갑니다.
>
> 동작은 이래요. 새 쿼리가 들어오면 임베딩 모델로 벡터로 바꾸고, VectorDB에 저장된 기존 쿼리 벡터들과 **cosine 유사도**를 비교합니다. 가장 비슷한 것의 유사도가 미리 정해둔 **threshold(예: 0.90)** 이상이면 — **그 쿼리의 캐시된 응답을 새 쿼리에도 돌려줍니다.**
>
> 표를 봅시다. "비밀번호 어떻게 바꾸나요?"가 캐시에 들어 있어요. "비번 변경법 알려줘", "패스워드 바꾸는 방법" 같은 쿼리는 글자가 다 다른데 의미가 거의 같아서 유사도 0.93~0.94가 나옵니다. **0.90 threshold면 셋 다 같은 응답으로 처리**돼요. Exact Cache라면 셋이 다 다른 키였겠죠. FAQ나 고객 지원처럼 사용자의 표현이 천차만별인 도메인에서 적중률이 폭발적으로 올라가는 이유입니다.
>
> 반대편을 봅시다. "계정 어떻게 삭제하나요?"는 유사도 0.62 — 의미가 다르니 캐시 미스, LLM에 정상적으로 넘어갑니다.
>
> 그런데 가장 위험한 케이스 — **"계약 해지는 어떻게?" vs "계약 체결은 어떻게?"**. 단어 4개 중 3개가 겹쳐서 cosine 유사도가 위험하게 높게 나올 수 있어요. 의도는 정반대인데 말이죠. 이게 Semantic Cache의 핵심 리스크인 **오적중(false positive)**이고, 다음 장에서 임계치 튜닝과 안전장치를 같이 봅니다.

## Slide 20 — Semantic Cache (Gateway)
**[화면]**
- 파이프라인
  ```
  Query ──→ [Embedding Model] ──→ Query Vector
                                      │
                                      ▼
                              ┌──────────────────┐
                              │ VectorDB Search  │
                              │ (Top-1 유사도)   │
                              └────────┬─────────┘
                                       │
                             similarity ≥ threshold ?
                              ┌────────┴────────┐
                           Yes│                 │No
                              ▼                 ▼
                    Cache HIT               LLM 호출 →
                    캐시 응답 반환          응답 + 새 Query Vector 저장
  ```
- 도메인별 실측 적중률 (2026-04)
  ```
  FAQ / 고객지원        : 40~70%  ◀── 가장 효과 큼
  번역 / 요약 요청       : 25~45%
  문서 Q&A              : 15~30%
  오픈 채팅 / 브레인스토밍: 10~20%
  코드 생성 / 창작       :  5~15%  ◀── 효과 제한적
  ```
- 임계치(threshold) 튜닝 가이드
  ```
  · 0.95~1.00  : 매우 엄격 · 적중 낮음 · 오적중 거의 없음
  · 0.90~0.95  : 엄격     · 적중 중간 · 안전 (권장 시작점)
  · 0.80~0.90  : 느슨     · 적중 높음 · 오적중 주의
  · <0.80     : 위험     · 엉뚱한 답 반환 빈발
  ```

**[스크립트]**
> Semantic Cache는 가장 똑똑하지만 **가장 리스크가 큰** 캐시예요. 도입 전에 설계·모니터링 전략을 확실히 세우고 시작해야 합니다.
>
> **파이프라인**을 먼저 봅시다. 질문이 들어오면 임베딩 모델로 **벡터로 변환**해요. 그 벡터를 VectorDB에 저장된 기존 질문 벡터들과 **cosine 유사도 비교**합니다. Top-1 유사도가 임계치 이상이면 **그 질문의 캐시된 응답을 반환** — LLM 호출이 일어나지 않아요. 미스면 LLM 호출 후 응답과 새 벡터를 VectorDB에 저장합니다.
>
> 임베딩·유사도 검색 오버헤드는 **5~20ms** 정도예요. 한 번 LLM 호출이 보통 1~5초니까, 히트 한 번에 그 차이만큼 이득을 봅니다.
>
> 왜 강력하냐면 — "비밀번호 어떻게 바꿔요?"와 "비번 변경법 알려줘"는 **문자열은 완전히 다르지만 의미는 같습니다.** Exact Cache는 둘을 다른 키로 처리하지만, Semantic Cache는 같은 걸로 인식해요. 사용자의 질문 표현이 천차만별인 FAQ·고객 지원에서 특히 빛납니다.
>
> **도메인별 적중률**이 극단적으로 다릅니다. FAQ·고객지원은 **40~70%**까지 올라가요. 번역·요약은 25~45%, 문서 Q&A는 15~30%, 오픈 채팅은 10~20%, 코드 생성·창작은 **5~15%밖에 안 돼요**. 도메인이 창의적이고 개방적일수록 적중이 떨어지죠. 여러분 서비스의 기대 적중률을 미리 가늠하세요.
>
> 이제 가장 중요한 **임계치 튜닝**. 0.95 이상은 매우 엄격 — 거의 Exact Cache에 가까워서 적중률이 낮습니다. **0.90~0.95가 권장 시작점**이에요. 적중률과 안전성의 균형이 가장 좋고, 오적중 사례도 드물어요. 0.80~0.90은 느슨해서 적중은 많지만 오적중이 발생하기 시작합니다. 0.80 아래는 위험해요 — 전혀 다른 의미의 질문에 엉뚱한 답이 나가는 일이 빈발합니다.
>
> **오적중(false positive)** — 이게 Semantic Cache의 최대 리스크입니다. 예: **"계약 해지는 어떻게 하나요?"에 "계약 체결은 어떻게 하나요?" 답**이 나가는 경우. 단어가 비슷해 유사도는 높지만 의도는 정반대죠. 이런 사고가 실서비스에서 한 번 발생하면 신뢰도가 크게 깎입니다.
>
> 그래서 도입 시 **세 가지 안전장치**를 반드시 붙이세요.
>
> **① 안전 도메인부터.** FAQ처럼 정답 집합이 명확하고 한정된 영역에만 먼저 적용. 결제·해지 같은 **핵심 트랜잭션 플로우는 처음엔 제외**하세요.
>
> **② 오적중 모니터링.** 캐시 응답에 대한 사용자 피드백(thumbs down, 재질의 비율)을 추적해서 **오적중 의심 사례를 추출**합니다. 일정 비율 넘으면 threshold를 올려요.
>
> **③ Negation·Intent 필터.** 질문에 "해지", "취소", "삭제" 같은 **부정 키워드**가 섞여 있으면 Semantic Cache를 스킵하고 LLM으로 직접 보내는 규칙을 걸어두세요. 이것만으로도 큰 사고가 상당히 줄어듭니다.

## Slide 21 — 적용 순서
**[화면]**
- (좌측) 도입 순서
  ```
  [1단] Prompt Cache  →  프롬프트 prefix 재구조화 (거의 공짜)
                        · 리스크: 없음
                        · 예상 이득: 입력 비용 50~90%↓

  [2단] Exact Cache   →  Redis + 해시 키 (핫패스 한정)
                        · 리스크: 낮음 (키 설계만 주의)
                        · 예상 이득: 핫패스 트래픽 30~50%↓

  [3단] Semantic Cache→  VectorDB + 임계치 튜닝 + 오적중 모니터
                        · 리스크: 중~높음 (도메인 의존)
                        · 예상 이득: FAQ 도메인 40~70%↓
  ```
- (우측) 시각 자료 — `images/llm_caching.gif`
  - 3-Layer Caching Architecture: User Question → Layer 1 Exact Match (1~5ms) → Layer 2 Semantic (5~20ms) → Layer 3 Prompt Cache (prefix) → LLM (200~2000ms)
  - Common Cache Breakers 박스 포함 (Timestamp, Session ID, User-specific headers, Dynamic tool defs, Minor formatting)

**[스크립트]**
> 세 유형을 **한꺼번에 다 깔려고 하지 마세요.** 도입 순서가 정해져 있고, 이걸 지켜야 안전합니다.
>
> **1단계, Prompt Cache부터**. 프롬프트 구조만 "불변 prefix 먼저, 가변 suffix 뒤"로 재구조화하면 끝이에요. 거의 공짜로 입력 비용이 50~90% 떨어집니다. 리스크도 없어요. 여기서 시작하세요.
>
> **2단계, Exact Cache**. 트래픽이 많은 핫패스 몇 개에만 Redis 캐시를 붙입니다. FAQ, 배너 텍스트, 공지 요약 같은 정적 응답 위주로요. Redis 한 인스턴스면 충분하고, 핫패스 트래픽의 30~50%가 즉시 사라집니다. 키 설계(모델 버전 포함)만 지키면 리스크도 낮아요.
>
> **3단계, Semantic Cache**. 위 두 개가 안정화된 **다음에**, 안전한 도메인부터 조심스럽게 도입합니다. FAQ·고객지원처럼 도메인이 좁고 정답 집합이 있는 영역이 좋아요. 임계치는 **0.90~0.95에서 시작**하고, 오적중 모니터링 없이는 절대 시작하지 마세요. 부정 키워드 필터도 같이 붙이시고요.
>
> 마지막으로 — 오른쪽 그림이 실제 런타임 흐름입니다. 사용자 질문이 들어오면 **Exact → Semantic → Prompt → LLM** 순서로 단계마다 한 번씩 캐시를 거치고, 최종 LLM은 모두 미스일 때만 호출돼요. 단계마다 지연이 1~5ms → 5~20ms → prefix 재사용 → 200~2000ms로 커지죠. 오른쪽의 **Common Cache Breakers** — 타임스탬프, 세션 ID, 동적 도구 정의 같은 단골 함정 다섯 가지는 1단부터 점검 대상입니다.

**[스크립트]**

>
> Gateway 내부로 들어가면, 먼저 **Auth** — #01. 그다음 **Prompt Registry**에서 사용할 프롬프트 버전을 가져옵니다 — **#04 Prompt 관리**. Langfuse 같은 도구가 이 자리에 들어가요. 그 다음 **Router**가 어느 모델로 갈지 결정합니다 — **#02 라우팅·LB**. Cascade, Intent, Weighted 중 하나의 전략이죠.
>
> 그 옆에 보시면 **3가지 표준 캐시**가 있어요 — **#05 캐싱**. **Prompt Cache**는 Provider 쪽 prefix 재사용(프롬프트 재구조화로 활성화), **Exact Cache**는 Gateway의 Redis 해시 매칭, **Semantic Cache**는 VectorDB 벡터 유사도. 요청은 **Prompt → Exact → Semantic 순서로** 각 유형을 체크하며 통과합니다 — 앞에서 히트하면 뒤는 건너뜀.
>
> 그 아래 가로로 길게 깔린 **세 줄의 횡단 레이어**가 나머지 책임을 담당해요. 첫 줄은 Fallback·Retry·Circuit Breaker·Rate Limit — **#03 Fallback·재시도**. 둘째 줄은 Observability·Cost Tagging·Trace — **#06 관측성·비용 태깅**. 셋째 줄은 PII Mask·Injection Detect·감사 로그 — **#07 안전·거버넌스**. #06과 #07은 오늘 "챕터로 따로 빼지 말자"고 한 횡단 책임인데, 이 그림에서 **어디에 있는지가 명확히 보입니다**. 말 그대로 요청이 지나가는 모든 단계에 가로로 깔려 있죠.
>
> 마지막으로 실제 Provider들로 나갑니다. OpenAI GPT-5.5/5.4 계열, Anthropic Opus/Sonnet/Haiku, Google Gemini 3.1 Pro·Flash Live·Lite. Azure OpenAI 멀티 리전도 여기에 끼고요.
>
> 이 한 장이 여러분의 조직 슬라이드 덱에 그대로 복사되어도 될 정도의 참조 아키텍처예요. **그림 한 장으로 오늘 섹션 전체를 꺼내 쓸 수 있도록** 외워두시길 권합니다.
