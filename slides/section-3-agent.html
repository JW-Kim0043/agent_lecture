01 · Tool Registry

Tool Registry — 무엇을 저장하나

저장 항목

  • name — LLM이 호출하는 식별자
  • description — 언제 쓰는지 자연어 설명
  • input_schema — JSON Schema · 필수/선택
  • output_schema — 반환 타입 (선택)
  • version — semver · 호환성 관리
  • owner / team — 책임 주체 추적
  • permission tag — read · write · payment

예시 (JSON Schema)

{ "name": "get_weather", "description": "도시의 실시간 날씨를 반환", "input_schema": { "type": "object", "properties": {"city": {"type":"string"}}, "required": ["city"] }, "version": "1.2.0", "owner": "platform-team", "tags": ["read", "external_api"] }
중앙 관리해야 도구 발견 · 거버넌스 · 버전 호환성 가능 · 흩어두면 추적 불가.
03 · AGENT · CH212 / 40
02 · Tool Executor

Tool Executor — Agent에 결과를 전달하는 흐름

한 호출 사이클

  • 1. LLM — tool_call JSON 발신 (name + args + tool_use_id)
  • 2. Executor — schema 검증 → sandbox 실행
  • 3. External — 실제 함수 · API · DB · Shell 호출
  • 4. Result — raw 반환 + 메타 (duration · status)
  • 5. tool_result — tool_use_id 매칭으로 Agent State에 주입

Agent 결과 전달 구조

  • messages 배열에 {role: "tool", tool_use_id, content} append
  • 다음 LLM 호출에 자동 포함 → 모델이 결과 보고 다음 판단

Executor의 안전 장치

  • Sandbox — subprocess · container · WASM 격리
  • Timeout — 호출당 상한, 무한 대기 차단
  • Retry · Idempotency 키 — 멱등성 보장 후 재시도
  • 자원 제한 — mem · cpu · net 쿼터
  • 관측 — 호출당 trace · cost 태깅

실패 처리 원칙

  • 예외 throw 금지 — 에러도 tool_result로 반환
  • 모델이 에러 메시지 보고 스스로 복구 시도
tool_use_id로 요청·응답 매칭 · 결과는 tool_result 메시지로 Agent 컨텍스트에 주입.

03 · Result Formatter

Result Formatter — LLM에 들어가기 전 정제

왜 필요한가

  • raw 결과 그대로 넣으면 컨텍스트 윈도우 폭발 (10MB JSON · 1만 row)
  • PII · 시크릿이 LLM 메시지에 그대로 노출
  • HTML · binary · 비표준 포맷은 LLM이 잘못 해석

처리 동작

  • truncate / summarize — top-N · 요약
  • redact — PII · 토큰 · 키 마스킹
  • convert — HTML → markdown · binary → 메타데이터

Before / After 예시

BEFORE
[10,234 rows]
{"tx_id":"a3f...","amount":1029.5,
"card":"4532-1234-5678-9012",
"user_email":"alice@x.com",...}
[10,234개 더 ...]
AFTER
Top 5 by amount:
1. tx_a3f - $1,029.50 (card: ****9012)
2. tx_b71 - $890.30 (card: ****4421)
...
총 10,234건 · 합 $891,203
"raw → formatted"는 비용·보안 게이트 · context 잠식과 PII 누출을 동시에 막음.

04 · Policy Layer

Policy Layer — 누가 · 언제 · 어떤 도구

입력

  • user / role — 호출 주체
  • tool name + permission tag
  • arguments — 금액 · 대상 · 환경
  • context — 이전 호출 · 시간대 · 세션

결정

  • allow · 그대로 실행
  • deny · 차단 + 사유
  • require_approval · HITL interrupt

구현 패턴

  • 룰 엔진 · OPA (Open Policy Agent)
  • Tool에 permission tag로 라벨링
  • 모든 결정은 감사 로그에 기록

현실적 규칙 예시

  • payment.* → 관리자 + HITL 필수
  • delete.* → 프로덕션 차단
  • email.send → 내부 도메인만
  • db.write → working hours만
Policy 없으면 LLM 오판 한 번이 곧 사고 · 사용자 농담을 진지하게 받아 데이터 삭제한 사례 다수.

When to Split

언제 Multi-Agent로 넘어가는가

단일 Agent로 충분

  • 도구 5~10개, 한 도메인 내 작업
  • 한 LLM이 도구·정책 머리에 다 담음
  • 예: 사내 지식 QA, 고객 문의 1차

Multi-Agent 신호

  • Tool 30개+ → 프롬프트 폭증
  • 역할 분리 자연스러움 (Researcher · Writer · Editor)
  • 도메인별 다른 모델·정책
  • 부서 간 책임 경계 (다른 팀 Agent 협업)

Tool Design

Tool 설계 6 체크리스트

  • Docstring이 명확한가 (LLM이 읽는 유일한 설명)
  • 인자 스키마가 엄격한가 (Pydantic · JSON Schema)

  • 결과 크기 제한이 있는가 (LLM 컨텍스트 보호)
