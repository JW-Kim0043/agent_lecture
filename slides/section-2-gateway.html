Routing Strategy

3가지 라우팅 전략

01

Priority Fallback

장애 대응. 1 → 2 → 3순위. 429/5xx/timeout 트리거.

02

Weighted LB

분산·쿼터 회피. 동일 모델 멀티 리전 50/50. 확률적 분배.

03

Intent / Semantic

품질·비용 균형. 쿼리 분류 후 모델 선택.

세 전략은 대체재가 아닌 보완재. 실전에서는 중첩 적용.

02 · GATEWAY · CH420 / 37
Fallback Design

Fallback 설계 체크

  • 트리거 — 429 / 5xx / timeout / content-filter false-positive / CB open
  • 백오프 — 같은 타겟 재시도에만 지수+지터. 다음 fallback 타겟 전환은 즉시
  • Idempotency — Tool 호출 재시도 시 치명적. 멱등 키 필수
  • 관측성 — "왜 Fallback됐는가" trace에 기록
흔한 사고 멱등 키 부재 → 재시도 시 이메일 2회 발송, 결제 2회 청구.
02 · GATEWAY · CH421 / 37
Deep Dive · 4 Elements

Fallback 4요소 상세

01

트리거
(Trigger)

명확한 실패
429 rate limit · 5xx 서버 오류 · timeout(>N초)
숨은 실패
content-filter false positive · schema 검증 실패 · 응답 길이 0
상태 기반
Circuit Breaker open 상태면 해당 타겟 건너뜀
주의
4xx 중 400 Bad Request는 재시도 금지 — 요청 자체가 잘못된 경우 반복해도 실패
02

백오프
(Backoff)

적용 범위
같은 타겟 재시도에만 · 다른 fallback 타겟 전환은 즉시 (지연 X)
지수 증가
1s → 2s → 4s → 8s (base × 2n)
Jitter
각 지연에 ±20% 랜덤 추가 — thundering herd 방지
상한
max_delay = 60s · LLM은 max_retries = 1~2회 권장
Retry-After 존중
서버가 Retry-After 헤더를 주면 계산값 대신 그 값을 사용
03

Idempotency
(멱등성)

왜 필요
재시도 시 Tool 호출 = 이메일 2번, 결제 2번 사고
키 설계
Idempotency-Key: {user}-{tool}-{hash(body)}-{ts}
저장소
Redis/DB에 24h TTL — 동일 키 재호출 시 캐시된 결과 반환
적용 범위
side-effect 있는 Tool 전부 — 결제·메일·DB write·외부 API
04

관측성
(Observability)

필수 기록
Fallback 발생 시점·사유·대체 경로·시도 횟수
Trace 속성
fallback.reason · fallback.from · fallback.to · retry.count
알람
Fallback 비율 임계치 초과 시 알람 — Primary 장애 조기 감지
대시보드
경로별 성공률·평균 재시도 수·timeout 분포

Prompt Cache · How It Works

Prompt Cache는 왜·어떻게 작동하는가

A. Prefill vs Decode 비용 구조

  • Prefill — 입력 N 토큰 병렬 처리, O(N²), 전체 지연의 60~80%
  • Decode — 출력 토큰 1개씩 순차 생성, 가벼운 루프
  • Prompt Cache가 노리는 건 Prefill 단계 — 여길 건너뛰면 비용·TTFT 동시 감소

B. Causal Attention 왜 prefix만?

  • Token[n]의 KV-state = f(Token[0..n])
  • 앞 토큰 하나만 바뀌어도 뒤 KV 전부 무효

C. Block-level Hashing 어떻게 매칭?

  • 토큰이 아니라 블록(1,024~4,096 tokens) 단위로 해시 비교
  • 최장 일치 prefix 만큼만 KV 재사용, 뒤 블록부터 새로 prefill
  • 최소 임계치(~1,024 토큰) 미만 프롬프트는 캐시 대상 제외

D. TTL과 GPU 메모리 왜 짧나?

  • KV-state는 GPU 메모리 상주 — 공간 유한
  • LRU/TTL evict 필수 → OpenAI 자동 5~10분, Anthropic 5분/1시간
  • Persistent TTL은 본질적으로 GPU 자원 예약 비용
설계 시사점 3가지: ① 맨 앞에 dynamic value 금지 · ② Few-shot·tool 정의 순서 고정 · ③ 짧은 프롬프트엔 Prompt Cache 대신 Exact Cache.

③ Semantic Cache · Vector Similarity

Semantic Cache 설계 & 리스크

파이프라인

  • Query → Embedding → VectorDB Top-1 유사도
  • threshold 이상 → Cache 응답 (LLM 호출 0)
  • miss → LLM 호출 + 새 벡터 저장
  • 임베딩·유사도 오버헤드 5~20ms

도메인별 적중률

  • FAQ·고객지원: 40~70%
  • 번역·요약: 25~45%
  • 문서 Q&A: 15~30%
  • 오픈 채팅·창작: 5~20%

Threshold 튜닝 (cosine)

  • 0.95~1.00: 매우 엄격 · 적중 낮음
  • 0.90~0.95: 권장 시작점
  • 0.80~0.90: 느슨 · 오적중 주의
  • <0.80: 위험 · 엉뚱한 답

오적중 방지 3종

  • ① 안전 도메인부터 (결제·해지 제외)
  • ② 사용자 피드백으로 오적중 모니터
  • ③ 부정 키워드 필터 (해지·취소·삭제)
치명적 사고 예 "계약 해지는 어떻게?" → "계약 체결은 어떻게?" 답이 나가면 신뢰도 붕괴. 도입 전 반드시 안전장치 세 개 같이 올릴 것.
