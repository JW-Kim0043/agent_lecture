## Slide 3 — 챗봇과 Agent는 무엇이 다른가
**[화면]**
- 비교표
  | | LLM 호출 | Agent |
  |---|---|---|
  | 입출력 | 1-shot | 루프(loop) |
  | 외부 세계 | 없음 | 도구 사용 |
  | 상태 | 대화 맥락뿐 | 명시적 State |
  | 결정 | 유저 지시 | 자가 결정 |

**[스크립트]**
> 먼저 챗봇과 Agent의 차이를 명확히 할게요. 이 경계가 흐릿하면 이후 이야기가 모호해집니다.
>
> **챗봇, 또는 일반 LLM 호출**은 이렇게 동작해요. 사용자가 질문하면 LLM이 한 번 생성하고 끝. 아주 단순한 요청·응답 구조예요. 외부 세계와 상호작용이 없고, 이번 대화 맥락 이상의 상태도 없습니다. 사용자가 시키는 대로 답할 뿐이에요.
>
> **Agent**는 다릅니다. 하나씩 볼게요.
>
> **첫째, 루프예요.** Agent는 한 번 답하고 끝나지 않아요. "질문 받기 → 생각 → 도구 실행 → 결과 보고 → 더 필요한가? → 또 생각 → 또 실행…" 이렇게 반복하다가 충분한 정보가 모이면 그제야 응답합니다.
>
> **둘째, 도구를 씁니다.** 검색, DB 조회, API 호출, 이메일 전송 같은 **실제 외부 동작**을 수행할 수 있어요. 챗봇은 "비행기 몇 시에 떠요?"에 그냥 추측으로 답하지만, Agent는 실제 항공 API를 호출해서 조회합니다.
>
> **셋째, 명시적 State를 가집니다.** 지금 몇 번째 반복인지, 어떤 도구를 이미 써봤는지, 중간 결과는 뭔지를 구조화된 데이터로 관리해요. 대화 이력만 있는 게 아니에요.
>
> **넷째, 스스로 결정합니다.** 다음 단계에 뭘 할지 LLM이 판단해요. 사용자가 일일이 지시하지 않습니다.
>
> 이 네 개가 다 있어야 Agent라고 부를 수 있어요. 아키텍트 관점에서 Agent는 **분산 시스템의 작은 오케스트레이터**예요. 기존 웹 서비스와는 다른 종류의 문제들이 튀어나옵니다.

## Slide 4 — Agent = Loop + Tools + State + Policy
**[화면]**
- 큰 공식: **Agent = Loop + Tools + State + Policy**
- 4 미니 박스: Loop / Tools / State / Policy

**[스크립트]**
> 이 공식을 여러분이 가져가실 한 문장이에요. 네 단어가 왜 중요한지 각각 설명할게요.
>
> **Loop**. 여러 단계를 반복할 수 있는 구조예요. 반복이 없으면 "질문 한 번, 답 한 번"으로 끝나니까 복잡한 작업을 못 해요. 여행 계획을 세우는 Agent를 생각해 보세요. 항공권 검색, 호텔 검색, 일정 충돌 체크, 결과 정리 — 이게 한 번에 안 됩니다. 반복해야 해요.
>
> **Tools**. 외부 세계와 연결되는 수단이에요. 도구 없는 Agent는 결국 LLM의 내부 지식으로만 답하는 챗봇이에요. 외부 동작이 필요한 순간 Agent로서의 가치가 생깁니다.
>
> **State**. 진행 상황을 기록하는 구조예요. "이미 이 API는 호출했어", "결과는 이거였어", "지금 세 번째 반복이야" 같은 정보를 담습니다. State가 잘 설계돼 있어야 **도중에 실패했을 때 재개**가 가능하고, 중복 작업을 막을 수 있어요.
>
> **Policy**. 가드레일이에요. 이게 없으면 Agent가 정말 위험한 걸 만들어냅니다. 예를 들어 **최대 10번까지만 루프를 돌아라**, **이 도구는 특정 사용자만 쓸 수 있다**, **한 번에 $1 이상 쓰지 말아라** 같은 규칙들이요. 앞서 말한 Loop가 너무 강력해서, Policy 없으면 무한 루프에 빠지거나 한 사용자가 서비스 비용을 다 태워버릴 수도 있어요.
>
> **네 개 중 하나라도 빠지면 Agent가 아닙니다.** 도구는 있는데 루프가 없으면 그냥 LLM + Tool use 예시예요. 루프는 있는데 State가 없으면 매번 처음부터 다시 하는 비효율적인 구조고요. Policy가 없으면 프로덕션에 못 올리죠.

## Slide 5 — Agent가 만드는 새 문제 5가지
**[화면]**
- 5 번호 카드: 비결정성 · Fan-out 비용 · 무한루프 · 실패 복구 · 권한·안전

**[스크립트]**
> Agent 시스템이 기존 웹서비스와 다른 종류의 골칫거리를 만들어내요. 아키텍트는 이 다섯 가지를 먼저 알고 있어야 합니다.
>
> **1번 비결정성**. 같은 입력이 들어와도 Agent의 실행 경로가 달라집니다. LLM이 "이번엔 도구 A를 먼저 써야겠다" 판단했다가 다음번엔 도구 B를 먼저 쓸 수 있어요. 테스트가 어려워지고, 재현이 까다로워집니다. 기존에 하던 단위 테스트 방식이 그대로 안 통해요.
>
> **2번 Fan-out 비용**. Agent는 한 요청에 LLM을 여러 번 호출합니다. 한 번 질문하면 내부적으로 5번, 10번 호출이 일어날 수 있어요. **비용과 지연이 곱해집니다.** 챗봇이 $0.01 걸리는 걸 Agent는 $0.10 들 수도 있어요. 이 비용 구조를 이해하고 사용자에게 노출할 범위를 정해야 합니다.
>
> **3번 무한루프 위험**. Loop가 있다는 건 루프가 안 끝날 수도 있다는 뜻이에요. LLM이 "아직 충분하지 않아, 더 해야겠어"를 계속 판단하면 무한정 돕니다. 토큰 예산이 단 몇 분 만에 바닥날 수 있어요. **Step 제한, 토큰 제한은 필수**입니다.
>
> **4번 실패 복구**. 10번 반복 중 7번째에 도구 호출이 실패했다고 해봅시다. 어디부터 재개할지, 이미 저장한 중간 결과는 어떻게 할지 설계해야 해요. 기존 웹서비스의 "요청 실패 시 재시도"와는 차원이 다릅니다.
>
> **5번 권한과 안전**. 도구가 실제 시스템을 건드립니다. 이메일을 보내고, 결제를 하고, 파일을 지우고요. 누가 어떤 도구를 언제 쓸 수 있는지 **권한 관리**가 엄격해야 해요. 감사 로그도 필수입니다.
>
> 이 다섯 가지를 인지하고 설계에 반영하는 게 **Agent 아키텍트의 핵심 역할**이에요.

## Slide 5-1 — Agent 5 문제의 실제 사고 사례 *(신규 예시)*
**[화면]**
- 5개 번호 카드 (문제 → 실제 사고 한 줄)
  ```
  01 비결정성
     "어제는 잘 됐던 Agent가 오늘 같은 질문에 다른 경로 →
      QA팀 '버그'로 이슈 오픈, 개발팀 '재현 안 됨'으로 종결"

  02 Fan-out 비용
     "한 질문에 LLM 17번 호출 → 사용자 1명당 $0.85 →
      무료 체험 사용자 1,000명으로 월 $25K 청구"

  03 무한루프
     "Tool 호출 실패 시 '다시 시도'를 LLM이 판단 →
      같은 도구 반복 호출로 8시간 만에 토큰 예산 고갈"

  04 실패 복구
     "여행 예약 Agent, 항공권 결제 후 호텔 예약 단계 실패 →
      사용자에게 항공권만 결제 완료, 호텔은 미확정 상태 전달"

  05 권한·안전
     "일반 사용자가 '내 데이터 다 지워줘' →
      LLM이 delete_user_data 도구 호출, 승인 절차 없이 실행"
  ```

**[스크립트]**
> 앞 장에서 말한 5가지 문제가 실제로 어떻게 사고로 번지는지 한 줄씩 예시로 보여드릴게요. 업계에서 돌아다니는 사례들이에요.
>
> **비결정성 사례** — QA팀이 "어제 잘 됐던 Agent가 오늘 다른 경로로 동작한다"고 버그 이슈를 올려요. 개발팀이 재현하려고 하면 잘 됩니다. 재현이 안 되니 "버그 아님"으로 종결되는데, 실제론 LLM의 비결정성 때문이죠. 테스트 전략을 바꿔야 하는 신호예요.
>
> **Fan-out 비용 사례** — 한 질문에 Agent가 내부적으로 LLM을 17번 호출했어요. 사용자 1명당 $0.85 비용이에요. 무료 체험 사용자 1,000명이 몰리자 월 $25,000 청구서가 튀어나왔죠. **사용자에게 노출된 비용 구조와 내부 실제 비용이 달라서** 생긴 사고예요.
>
> **무한루프 사례** — Tool 호출이 실패했을 때 "다시 시도할까"를 LLM이 판단하게 했더니, 같은 도구를 반복 호출하면서 8시간 만에 월 토큰 예산을 다 태웠어요. Step 상한만 있었어도 막혔을 사고입니다.
>
> **실패 복구 사례** — 여행 예약 Agent가 항공권은 결제했는데 호텔 예약 단계에서 실패. 사용자한테는 "항공권 결제 완료, 호텔은 미확정"이란 어정쩡한 상태가 전달됐어요. **분산 트랜잭션을 Agent에서 다루는 건 별도 설계**가 필요합니다.
>
> **권한·안전 사례** — 일반 사용자가 농담처럼 "내 데이터 다 지워줘"라고 입력. LLM이 진지하게 받아들여 `delete_user_data`를 호출했어요. Policy Layer나 Human-in-the-loop이 없으면 이런 사고가 실제로 일어납니다.
>
> 이 다섯 가지는 모두 **"앱 서비스엔 없던 실패 양상"**이에요. 그래서 Agent 아키텍트는 기존 안정성 체크리스트를 다시 짜야 합니다.

Function Calling은 2023년부터 표준이 됐고, **MCP는 2024년 11월 Anthropic이 공개**한 뒤 2025년 11월 사양 갱신, 2026년 Linux Foundation Agentic AI Foundation 이관까지 빠르게 산업 표준이 됐습니다. 작년 강의엔 없던 토픽인데, 지금은 아키텍트가 모르고 있으면 안 되는 영역입니다. Chapter 3의 추론 패턴 이야기는 이 Tool 인터페이스가 깔린 다음에야 명확해집니다.

## Slide 6 — Tool Use = Function Calling
**[화면]**
- 다이어그램: User 질문 → LLM 생성 JSON {"name":"get_weather","args":{"city":"Seoul"}} → Runtime 실행 → Result → LLM 최종 응답

**[스크립트]**
> Function Calling이 실제로 어떻게 동작하는지 흐름으로 보여드릴게요.
>
> 사용자가 "서울 날씨 알려줘"라고 묻습니다. 보통 챗봇이면 LLM이 바로 답을 만들어내는데, Function Calling에선 다릅니다.
>
> LLM은 개발자가 **사전에 등록한 도구 목록** — 예를 들어 `get_weather(city)`라는 함수가 있다는 걸 — 을 알고 있어요. 사용자 질문을 보고 "아, 이건 내가 혼자 답할 수 없고 `get_weather` 함수를 호출해야겠다" 판단합니다. 그러면 답변 대신 **구조화된 JSON**을 반환해요. `{"name": "get_weather", "args": {"city": "Seoul"}}` 이런 식이죠.
>
> 런타임 — 우리 Agent 프레임워크 — 는 이 JSON을 받아서 실제로 그 함수를 실행합니다. `get_weather("Seoul")`이 실행되면 실제 날씨 API를 호출해서 "맑음, 18도"라는 결과를 받아요.
>
> 그 결과를 **다시 LLM 컨텍스트에 주입**합니다. "방금 네가 호출한 함수의 결과는 이거야"라고요. LLM이 이 결과를 보고 **최종 답변**을 생성합니다. "서울은 현재 맑고 18도입니다."
>
> OpenAI, Anthropic, Azure, Google 전부 이 방식을 표준으로 지원해요. 이름이 조금씩 다를 뿐입니다. OpenAI는 `tools`, Anthropic은 `tool_use`, Google은 `function calling`. 개념은 동일해요.
>
> **아키텍트가 기억하실 것** — Tool Use는 "있으면 좋은 기능"이 아니라 **Agent의 기본 근육**이에요. 이게 없으면 외부 세계와 소통 못 하니까 Agent가 성립하지 않습니다.

## Slide 7 — Tool Use 아키텍처 4 요소
**[화면]**
- 4 번호 카드
  - 01 Tool Registry · 02 Tool Executor · 03 Result Formatter · 04 Policy Layer

**[스크립트]**
> Tool을 **그냥 파이썬 함수**로 생각하면 안 돼요. 프로덕션에선 네 가지 요소가 다 필요합니다.
>
> **1번 Tool Registry**. 사용 가능한 도구들의 목록과 메타데이터를 관리합니다. 각 도구의 이름, 입력 스키마(인자 타입), 설명 문장, 권한 태그 같은 걸 중앙에서 관리해요. 왜 중앙 관리가 필요하냐, 나중에 수십 개의 도구가 생기면 여기저기 흩어진 걸 다 추적 못 합니다.
>
> **2번 Tool Executor**. 실제로 함수를 실행하는 런타임이에요. 여기서 중요한 건 **샌드박스**, **타임아웃**, **리소스 제한**입니다. 도구가 외부 API를 부르는 함수인데 응답이 30초 걸리면? 전체 Agent가 거기서 멈춥니다. 타임아웃 없으면 사고예요.
>
> **3번 Result Formatter**. 도구가 반환한 결과를 LLM 컨텍스트에 넣기 전에 **정제**합니다. 너무 길면 요약하고, 개인정보 있으면 마스킹하고, 포맷을 정리해요. 도구가 10MB짜리 JSON을 돌려주면 LLM 컨텍스트 윈도우가 터집니다. 이걸 막는 게 이 계층이에요.
>
> **4번 Policy Layer**. 어떤 사용자가 어떤 도구를 언제 쓸 수 있는지 통제합니다. 예를 들어 "결제 도구는 관리자만", "이메일 전송은 사람 승인 후에만", "삭제 도구는 아예 프로덕션에서 비활성화" 같은 규칙들이요. 이게 없으면 LLM이 잘못된 판단을 했을 때 실제 사고가 납니다.
>
> 다음 네 장에서 각 요소를 한 장씩 깊이 들어갑니다.

## Slide 7-1 — Tool Registry 디테일 *(신규)*
**[화면]**
- 좌: 저장 항목 (name · description · input_schema · output_schema · version · owner · permission tag)
- 우: JSON Schema 예시 (`get_weather` 도구)
- 한 줄: 중앙 관리해야 도구 발견 · 거버넌스 · 버전 호환성 가능

**[스크립트]**
> Registry에 정확히 무엇이 들어가는지 봅니다. 일곱 가지가 표준이에요.
>
> **name**은 LLM이 함수를 호출할 때 쓰는 식별자. **description**은 언제 이 도구를 쓰는지 자연어 설명 — LLM이 도구 선택할 때 보는 핵심 정보예요. **input_schema**는 인자의 JSON Schema. 필수/선택, 타입, 기본값을 다 담습니다. **output_schema**는 반환 타입. 선택 사항이지만 강력 권장이에요. 검증 가능해집니다.
>
> 운영 메타데이터로 **version**(semver), **owner/team**(책임 주체), **permission tag**(read · write · admin · payment 같은 분류)가 같이 들어갑니다. 이게 있어야 나중에 Policy Layer가 "이 user는 payment 도구는 못 씀" 같은 결정을 할 수 있어요.
>
> 화면 오른쪽에 실제 JSON Schema 예시를 뒀어요. 이런 식의 메타데이터가 한 군데 모여 있어야 합니다. 코드에 흩어져 있으면 거버넌스도, 발견도, 버전 호환성 추적도 다 깨집니다.

## Slide 7-2 — Tool Executor 디테일 *(신규)*
**[화면]**
- 좌: 한 호출 사이클 (LLM → Executor → External → Result → tool_result)
- 우: 안전 장치 (Sandbox · Timeout · Retry · 자원 제한 · 관측) + 실패 처리 원칙
- 한 줄: tool_use_id로 요청·응답 매칭 · 결과는 tool_result 메시지로 컨텍스트 주입

**[스크립트]**
> Executor는 실제로 도구를 실행하고, **결과를 Agent 컨텍스트로 다시 넣어주는 다리**예요. 한 호출 사이클을 따라가면 이렇게 돕니다.
>
> **첫째**, LLM이 tool_call을 발신해요. 이때 함수 이름, 인자, 그리고 **tool_use_id**라는 호출 식별자가 함께 나옵니다. 이 ID가 나중에 응답 매칭에 쓰여요. **둘째**, Executor가 schema 검증하고 sandbox에서 실행. **셋째**, 외부 함수/API/DB가 진짜 일을 합니다. **넷째**, 결과가 raw로 돌아오고 메타데이터(소요 시간, 상태)가 붙어요. **다섯째**, 가장 중요한 단계 — Executor가 **tool_result 메시지**를 만들어서 Agent state의 messages 배열에 append합니다. 이때 tool_use_id로 어떤 호출의 응답인지 매칭해요.
>
> 다음 LLM 호출이 들어가면 messages가 자동으로 컨텍스트에 포함돼요. 모델이 결과를 보고 다음 행동을 결정합니다. 이게 Agent 루프의 한 사이클이에요.
>
> 안전 장치가 다섯입니다. **Sandbox** — subprocess, container, WASM으로 격리. **Timeout** — 호출당 상한, 무한 대기 차단. **Retry와 Idempotency 키** — 멱등성을 보장한 다음 재시도. 멱등성 보장 없이 재시도하면 결제 두 번, 이메일 두 번 보냅니다. **자원 제한** — 메모리, CPU, 네트워크 쿼터. **관측** — 호출당 trace, cost 태깅.
>
> 실패 처리 원칙 하나만 강조할게요. **예외 throw 금지**. 에러도 tool_result로 반환해서 모델이 보고 스스로 복구하게 해야 합니다. throw하면 Agent 전체 루프가 끊깁니다.

## Slide 7-3 — Result Formatter 디테일 *(신규)*
**[화면]**
- 좌: 왜 필요한가 (컨텍스트 폭발, PII 노출, 비표준 포맷) + 처리 동작 (truncate/summarize · redact · convert)
- 우: Before/After 예시 (10K rows raw → top 5 + 요약)
- 한 줄: raw → formatted는 비용·보안 게이트

**[스크립트]**
> 도구 결과를 그대로 LLM에 넣으면 안 되는 이유가 셋입니다.
>
> **첫째**, **컨텍스트 윈도우 폭발**. SQL 쿼리가 10MB JSON을 돌려주면? 1만 row를 LLM이 어떻게 다 읽어요. 토큰 예산도 박살나요. **둘째**, **PII와 시크릿이 LLM 메시지에 그대로 노출**. 카드번호, 이메일, 토큰이 messages에 들어가면 그대로 trace, log, 외부 LLM API 요청에 다 흘러갑니다. **셋째**, **비표준 포맷**. HTML, binary, PDF 같은 걸 그대로 넣으면 LLM이 잘못 해석해요.
>
> 처리 동작은 셋입니다.
>
> **truncate / summarize** — 너무 길면 top-N으로 자르거나 요약. 화면 우측 예시처럼 1만 행 → top 5 + 합계 요약으로 압축. 토큰 99% 절감하면서 모델이 답하는 데 필요한 정보는 다 줍니다.
>
> **redact** — PII, 토큰, 키를 마스킹. card="4532-1234-5678-9012" → card="****9012". 정규식 기반 + ML 기반 PII 디텍터를 섞어서 씁니다.
>
> **convert** — HTML → markdown, binary → 메타데이터(파일명·크기·hash)만, PDF → 텍스트 추출. LLM이 잘 읽는 형태로 변환합니다.
>
> 이 계층이 **비용 게이트와 보안 게이트를 동시에** 합니다. 빼먹으면 둘 다 잃어요.

## Slide 7-4 — Policy Layer 디테일 *(신규)*
**[화면]**
- 좌: 입력 (user/role · tool name + permission tag · arguments · context) + 결정 (allow · deny · require_approval)
- 우: 구현 패턴 (룰 엔진/OPA, permission tag, 감사 로그) + 현실적 규칙 예시
- 한 줄: Policy 없으면 LLM 오판 한 번이 곧 사고

**[스크립트]**
> Policy Layer는 도구 호출 직전에 "**이 호출 허용?**"을 결정하는 게이트입니다.
>
> 입력 네 가지를 봅니다. **user/role**(누가), **tool name + permission tag**(어떤 권한 등급의 도구), **arguments**(금액·대상·환경 등 구체값), 그리고 **context**(이전 호출, 시간대, 세션). 이 네 가지로 세 결정 중 하나를 내려요.
>
> **allow** — 그대로 실행. **deny** — 차단하고 사유를 모델에 알림. **require_approval** — Human-in-the-loop interrupt를 띄워서 사람 승인을 기다립니다.
>
> 구현은 룰 엔진을 쓰는 게 일반적이에요. **OPA(Open Policy Agent)**가 사실상 표준이에요. Tool Registry의 permission tag를 입력으로 받아서 결정합니다. 그리고 **모든 결정은 감사 로그**에 남겨야 해요. 사고 났을 때 "왜 허용/차단됐는지" 추적해야 하니까요.
>
> 현실적인 규칙 몇 개를 보여드리면, **payment.\* 도구는 관리자 + HITL 필수**, **delete.\*는 프로덕션에서 아예 차단**, **email.send는 내부 도메인만 허용**, **db.write는 working hours에만**. 이런 식의 layered defense가 있어야 LLM 오판 한 번이 사고로 번지지 않아요. 농담을 진지하게 받아 데이터 삭제한 사례가 실제로 있어요.

## Slide 8 — 도구가 많아질 때 — Tool Search Tool · Programmatic Calling *(교체)*
**[화면]**
- 문제 callout: MCP 서버 5개 · 도구 50+ → 정의만 ~77K 토큰 · GitHub MCP 하나로 Sonnet 컨텍스트 1/4 점유
- 3 카드
  - 01 Tool Search Tool — defer_loading: true · 77K → 8.7K (85% 절감) · Opus 4.5 79.5%→88.1%
  - 02 Programmatic Tool Calling — Python 코드로 오케스트레이션 · 43K → 27K (37% 절감)
  - 03 Tool-RAG 패턴 — 관련 도구 5~10개만 동적 노출
- 한 줄: 좋은 description은 여전히 필수 · 모두 등록 ≠ 모두 노출

**[스크립트]**
> 도구가 늘어나는 게 좋은 일 같지만, 한도가 있어요. MCP 서버 다섯 개에 도구 50개 정도 연결하면 **도구 정의만 77,000 토큰**을 잡아먹어요. 대화가 시작되기 전부터요. GitHub MCP 하나가 Sonnet 컨텍스트의 1/4를 가져갑니다.
>
> 정확도도 같이 떨어집니다. 도구 10개 넘어가면 LLM이 엉뚱한 도구를 고르기 시작해요. Anthropic 자체 평가에서 Opus 4가 49% 정확도까지 떨어졌어요. 이건 **함정**이에요.
>
> Anthropic이 2026년 1월에 공식 해법을 냈습니다. 세 가지를 같이 알아두세요.
>
> **첫째, Tool Search Tool.** Tool Registry에서 도구를 등록할 때 `defer_loading: true`로 마킹합니다. 그러면 그 도구의 정의는 **컨텍스트에 안 올라가요**. 대신 Claude가 작업 중에 "지금 필요한 도구를 찾아줘"라고 검색하면, 그 시점에만 해당 정의를 컨텍스트에 로드합니다. **77K → 8.7K 토큰, 85% 절감**. 정확도도 같이 회복돼요. Opus 4.5가 79.5%에서 **88.1%로 올라갔어요**. 2026년 1월부터 Claude Code에 기본 탑재됐고, 더 이상 옵트인이 아닙니다.
>
> **둘째, Programmatic Tool Calling.** 이건 다른 접근이에요. LLM이 매 도구를 한 번씩 호출하지 않고, **Python 코드를 작성해서 도구들을 한 번에 오케스트레이션**합니다. 결과는 sandbox에서 처리되고, **필요한 것만 컨텍스트에 올라가요**. 10,000개 expense line item을 LLM 머릿속을 거치지 않고 코드로 필터링하는 식이에요. **43K → 27K 토큰, 37% 절감**.
>
> **셋째, Tool-RAG 패턴.** 가장 단순한 자체 구현이에요. 사용자 질문을 받으면 먼저 **관련 있을 만한 도구 5~10개만** 검색해서 LLM에 노출합니다. 도구도 RAG의 retrieval source처럼 취급하는 거예요. Anthropic API의 Tool Search Tool이 이걸 1급 기능으로 지원하지만, 자체 구현도 어렵지 않아요.
>
> 한 줄로 — **좋은 description은 여전히 필수예요**. 검색·매칭의 입력은 결국 도구 description이거든요. 하지만 **모든 도구를 등록한다고 모두를 매번 노출할 필요는 없습니다**. 이게 2026년 표준입니다.

## Slide 8-1 — MCP: Model Context Protocol *(신규)*
**[화면]**
- 한 줄 정의: **"LLM 앱 ↔ 도구·데이터 소스의 USB-C"**
- 등장 배경 / 표준화 항목 / 거버넌스 3블록
  ```
  ━━ 등장 배경 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  · 모든 Agent가 도구·DB·SaaS 통합을 매번 자체 구현
  · OpenAI Function Calling은 LLM ↔ Tool만 표준화
  · "도구 자체"의 표준 인터페이스 부재 → 통합 폭증

  ━━ MCP가 표준화한 4가지 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  · Tools     — 호출 가능한 함수 (Function Calling 호환)
  · Resources — 읽기 전용 데이터 (파일·DB row·KB 문서)
  · Prompts   — 재사용 가능한 프롬프트 템플릿
  · Sampling  — Server가 Client LLM 추론을 요청 (역방향)

  ━━ 2026 거버넌스 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  · 2024-11 Anthropic 공개
  · 2025-11 사양 갱신 (Async · Stateless · Server identity)
  · 2026 Agentic AI Foundation (Linux Foundation) 이관
  · 후원: Anthropic·Block·OpenAI·Google·MS·AWS·Cloudflare
  · 공식 SDK 다운로드 9,700만+/월 (Python·TypeScript)
  · 커뮤니티 Registry에 검증된 커넥터 75+
  ```

**[스크립트]**
> MCP, 풀네임은 **Model Context Protocol**. 한 줄로 표현하면 **LLM 애플리케이션과 도구·데이터 소스 사이의 USB-C**입니다. 모든 도구를 하나의 표준 인터페이스로 꽂게 만든 게 핵심이에요.
>
> 등장 배경부터 보겠습니다. 2024년까지 모든 Agent 팀은 같은 일을 반복하고 있었어요. Slack 연동, Jira 연동, GitHub 연동, 내부 DB 연동 — **각자 자체 구현**했습니다. OpenAI Function Calling은 LLM과 Tool 사이 인터페이스를 표준화했지만, **Tool 자체의 표준 인터페이스는 없었어요**. 그래서 같은 Slack 통합을 LangChain용, AutoGen용, 자체 Agent용으로 따로따로 만들고 있었습니다.
>
> MCP는 네 가지를 표준화합니다.
>
> **첫째, Tools.** 호출 가능한 함수입니다. Function Calling과 호환되는 인터페이스라, 기존 도구를 MCP로 노출하면 어느 LLM에서든 그대로 씁니다.
>
> **둘째, Resources.** 읽기 전용 데이터입니다. 파일, DB row, 지식 문서 같은 것들을 일관된 방식으로 노출합니다. RAG의 retrieval source와 비슷한 자리지만 표준화돼 있어요.
>
> **셋째, Prompts.** 재사용 가능한 프롬프트 템플릿입니다. "이 서버는 이런 프롬프트로 호출하세요"라는 가이드를 서버가 직접 노출합니다.
>
> **넷째, Sampling.** 이게 흥미롭습니다. **MCP Server가 Client의 LLM 추론을 요청**할 수 있어요. 역방향 호출입니다. 서버 쪽에서 "이 데이터를 LLM에 한 번 더 돌려달라"고 Client에 요청할 수 있습니다.
>
> 거버넌스도 중요합니다. 2024년 11월 Anthropic이 공개했고, 2025년 11월 사양 갱신에서 **비동기·Stateless·Server identity**가 추가됐습니다. 2026년에는 Linux Foundation 산하 **Agentic AI Foundation**으로 이관됐고, 후원사는 Anthropic·Block·OpenAI·Google·Microsoft·AWS·Cloudflare·Bloomberg입니다. 한 회사의 표준이 아닙니다. **공식 SDK는 월 9,700만 다운로드**, Python과 TypeScript가 메인입니다. 커뮤니티 Registry에 검증된 커넥터가 75개 이상 등록돼 있습니다.
>
> 아키텍트가 기억하실 한 줄 — **MCP는 도구를 만들 때 자체 인터페이스 대신 표준에 맞추라는 신호**입니다. 1년 뒤엔 자체 인터페이스가 부채로 돌아옵니다.

## Slide 9 — ReAct 패턴
**[화면]**
- 논문 정보: Yao et al., 2022 · ICLR 2023
- 루프 다이어그램: Thought → Action → Observation → Thought → Final Answer

**[스크립트]**
> Agent 설계의 원형은 2022년 Yao et al.의 **ReAct** 논문입니다. Re는 Reasoning의 Re, Act는 Acting의 Act예요. 말 그대로 "**생각하고 행동하기**"를 합쳤다는 뜻이죠.
>
> 이 논문이 왜 중요하냐. 그 전까진 LLM 에이전트의 핵심 접근이 **Chain-of-Thought**라고 해서, 모델이 혼자서 길게 추론하는 방식이었어요. 그런데 이 방식은 문제가 있었어요. 중간에 잘못된 사실을 도입해도 계속 밀고 나가서 결국 틀린 답에 도달하는 **환각(hallucination)** 문제가 심했습니다.
>
> ReAct는 이걸 고쳤어요. 어떻게? **중간에 실제 도구를 호출해서 관찰된 결과를 넣으라**고 한 거예요. 앞 챕터의 Function Calling이 바로 이 "Action" 자리를 채우는 표준 메커니즘입니다.
>
> 화면의 흐름을 보시면. **Thought**에서 LLM이 "이걸 먼저 찾아봐야겠다"라고 계획을 세워요. **Action**으로 실제 검색 도구를 호출합니다. **Observation**에서 도구가 반환한 진짜 데이터를 보고요. 그 다음 **Thought**에서 "이제 답할 수 있겠다"라고 판단하면 **Final Answer**로 마무리합니다.
>
> 이게 왜 강력하냐, **환각이 중간중간 현실 데이터로 교정**되기 때문이에요. 모델이 혼자 상상으로 풀어가는 게 아니라, 중간에 실제 사실을 받아서 계속 검증하면서 가는 거예요.
>
> 오늘날 우리가 쓰는 거의 모든 Agent 프레임워크 — LangChain, LangGraph, CrewAI, AutoGen 전부 — 의 기저에 이 ReAct 아이디어가 깔려 있습니다.

## Slide 10 — ReAct의 효과와 한계
**[화면]**
- 2 박스
  - 효과: HotpotQA·FEVER 환각 감소, WebShop +10%p, ALFWorld +34%p
  - 한계: 작은 모델 포맷 깨짐, 14B급 75%+ 안정성, Function Calling 권장

**[스크립트]**
> 논문의 수치를 간단히 볼게요.
>
> **WebShop** — 쇼핑몰에서 상품 찾는 벤치마크 — 에서 **기존 Imitation Learning 방식 대비 10%p 개선**. **ALFWorld** — 집 안에서 물건 찾는 시뮬레이션 — 에서 **34%p 개선**. 강화학습 없이 in-context 예시 몇 개만 넣는 프롬프트 엔지니어링만으로 이 정도 수치를 냈다는 건 정말 큰 의미예요.
>
> 그런데 실전에서 그대로 쓰면 안 되는 **한계**도 있어요.
>
> 첫째, **작은 모델은 포맷을 잘 안 지킵니다.** "Thought: ... Action: ... Observation: ..."이라는 형식을 지켜야 파싱이 되는데, 7B, 13B 같은 작은 모델은 이 형식을 자주 깨먹어요. 한 줄 빼먹거나, 순서가 틀어지거나요. 그러면 Agent 로직이 멈춥니다.
>
> 둘째, 그래서 2026년 현재 실무에선 **Function Calling**이라는 방식을 더 많이 씁니다. 이건 ReAct의 아이디어는 유지하면서 포맷을 **LLM이 구조화된 JSON을 반환**하도록 강제하는 방식이에요. 파싱 실패가 거의 없어집니다. Chapter 2에서 본 Function Calling이 바로 이 안정화 메커니즘이에요.
>
> 셋째, 보고에 따르면 **14B급 정도의 모델**부터 ReAct 루프를 75% 이상 안정적으로 수행합니다. 작은 모델로 실험하다 "왜 안 되지?" 하시지 말고, 모델 크기도 감안하세요.

## Slide 10-1 — ReWOO: Reasoning WithOut Observation *(신규)*
**[화면]**
- 논문 정보: Xu et al. *ReWOO: Decoupling Reasoning from Observations*, 2023
- 3 모듈 다이어그램
  ```
  사용자 질문
      ↓
  ┌─────────────┐
  │  Planner    │  전체 계획 + 도구 호출 placeholder 생성
  │   (LLM)     │   #E1 = search[..]
  │             │   #E2 = calc[#E1.price * 1.1]  ...
  └──────┬──────┘
         ↓
  ┌─────────────┐
  │   Worker    │  도구 일괄 실행 (의존 없는 호출은 병렬)
  │  (no LLM)   │   #E1, #E2 결과 수집
  └──────┬──────┘
         ↓
  ┌─────────────┐
  │   Solver    │  계획 + 결과 종합 → 최종 답변
  │   (LLM)     │
  └─────────────┘
  ```
- 효과: HotpotQA 토큰 5배 절감 · 정확도 +4% · 지연 50~70% 감소

**[스크립트]**
> ReAct를 실서비스에 올리면 한 가지 비효율이 보입니다. **매 단계마다 LLM을 다시 부른다**는 점이에요. 도구 결과를 받을 때마다 "다음 뭘 할까"를 LLM이 또 판단합니다. 도구를 5번 호출하는 작업이면 LLM 호출도 5번이 됩니다. **토큰도 지연도 누적**됩니다.
>
> ReWOO는 이 문제를 정면으로 풉니다. 풀네임은 **Reasoning Without Observation**. "도구 결과(Observation)를 보지 않고 추론한다"는 뜻입니다. 어떻게요?
>
> **Planner 단계**에서 LLM을 한 번만 부릅니다. 이때 전체 계획을 한 번에 만들어요. 도구 결과 자리는 `#E1`, `#E2` 같은 **placeholder**로 둡니다. 예를 들어 `#E1 = search["iPhone 15 spec"]`, `#E2 = calc[#E1.price * 1.1]` 식이에요. 도구 호출의 의존 관계까지 한 번에 그려냅니다.
>
> **Worker 단계**는 LLM을 안 씁니다. 그냥 계획대로 도구를 실행해요. **의존 관계가 없는 호출은 병렬 실행**도 가능합니다. ReAct의 순차 실행보다 빨라지는 핵심 포인트입니다.
>
> **Solver 단계**에서 LLM을 한 번 더 불러서 계획과 결과를 종합합니다. 최종 답변 생성. **결국 LLM 호출은 2번**으로 끝납니다.
>
> 논문 수치를 보면 HotpotQA 벤치마크에서 **토큰 5배 절감**, 정확도 +4%, 지연 50~70% 감소. 그래서 **호출량이 많은 RAG-Agent, 비용이 ROI를 결정하는 운영 워크로드**에 강합니다.
>
> 단점도 있습니다. 계획이 처음에 잘못되면 **중간 교정이 어렵습니다**. ReAct는 매 단계 LLM이 다시 판단해서 코스 수정이 가능하지만, ReWOO는 Plan을 한 번에 짜기 때문에 **불확실성이 큰 작업**(웹 탐색, 사용자 입력에 따라 분기가 큰 작업)엔 잘 안 맞습니다. **도메인이 좁고 도구 호출 패턴이 예측 가능할 때** ReWOO가 빛납니다.

## Slide 10-2 — Plan-and-Act: 장기 작업 전용 *(신규)*
**[화면]**
- 논문 정보: Erdogan et al. *Plan-and-Act: Improving Planning of Agents for Long-Horizon Tasks*, UC Berkeley · ICML 2025
- 2 모듈 다이어그램
  ```
  사용자 목표 (장기·다단계)
        ↓
  ┌──────────────┐    "고수준 계획"
  │   Planner    │ → 1. 검색 페이지 진입
  │   (큰 LLM)   │   2. 조건 필터 입력
  │              │   3. 결과 정렬
  └──────┬───────┘   4. 첫 항목 클릭 …
         ↓ (1단계씩 위임)
  ┌──────────────┐    "환경 동작"
  │   Executor   │ → click / type / scroll
  │  (작은 LLM)  │   환경 피드백 반영
  └──────┬───────┘
         ↓ (단계 완료 후)
   Re-Plan? → Yes → Planner로 복귀
            → No  → 종료
  ```
- 효과: WebArena-Lite 57.6% (SOTA) · WebVoyager 81.4%

**[스크립트]**
> 2025년 3월 UC Berkeley 팀이 발표한 **Plan-and-Act**입니다. ReWOO와 비슷하게 계획·실행을 분리하지만 목표가 다릅니다. ReWOO는 **비용 효율**을 노리고, Plan-and-Act는 **장기 작업의 계획 정확도**를 노립니다.
>
> 핵심 통찰은 이거예요. 장기 작업에서 LLM이 헤매는 이유는 "계획"과 "실행"이 한 모델 머릿속에서 섞여있기 때문입니다. 계획을 잘 세우려면 추상적 사고가, 실행을 잘하려면 환경의 미세한 신호를 읽는 능력이 필요한데, 한 모델이 한 번에 둘 다 잘 하긴 어렵습니다.
>
> 그래서 **Planner는 큰 모델**(추론 능력 우선), **Executor는 작은 모델**(환경 동작에 특화)로 분리합니다. Planner가 고수준 계획을 짜면 한 단계씩 Executor에 넘기고, Executor가 실제 환경에서 click·type·scroll 같은 동작을 수행합니다. 단계가 끝나면 Planner에 리포트하고, Planner는 진행 상황을 보고 **Re-Plan 여부**를 결정합니다.
>
> 또 하나 특징은 **합성 데이터로 Planner를 학습**시킨다는 점입니다. 실제 작업 trajectory를 거꾸로 거슬러 가면서 "이 결과에 도달하려면 어떤 계획이 적합했을까"를 LLM이 다시 만들고, 이를 학습 데이터로 씁니다. 이걸로 Planner의 일반화 능력을 끌어올렸습니다.
>
> 결과는 WebArena-Lite에서 **57.6% SOTA**, WebVoyager에서 81.4%. **웹 자동화나 GUI 자동화처럼 Agent가 환경과 길게 대화하는 작업**에 강합니다.
>
> ReAct·ReWOO·Plan-and-Act 한 줄 비교 — **짧은 작업·코스 수정 필요**면 ReAct, **호출 많고 의존 관계 명확**하면 ReWOO, **장기·복잡한 환경 상호작용**이면 Plan-and-Act. 셋 다 알아두시면 패턴 선택의 폭이 훨씬 넓어집니다.

## Slide 11 — 그 외 주요 Agent 패턴
**[화면]**
- 4 번호 카드
  - 01 Plan-and-Execute · 02 Reflexion · 03 Multi-Agent Supervisor · 04 Graph-based

**[스크립트]**
> ReAct 말고도 자주 쓰이는 패턴이 몇 가지 있어요. 짧게 소개할게요.
>
> **Plan-and-Execute**. 먼저 **계획 단계**에서 전체 작업을 여러 step으로 나눕니다. 그 다음 **실행 단계**에서 각 step을 차례로 수행해요. 다단계 리서치나 프로젝트 관리 같은 복잡한 작업에 적합해요. ReAct가 한 번에 한 걸음씩 생각한다면, Plan-and-Execute는 전체를 미리 설계하고 실행합니다.
>
> **Reflexion**. 자기 평가 후 개선하는 패턴이에요. Agent가 답을 만들고, 스스로 "이 답이 괜찮은가?" 평가하고, 부족하면 다시 개선하는 루프를 돕니다. 고난도 코드 생성처럼 **품질이 정말 중요한 영역**에 쓰여요.
>
> **Multi-Agent Supervisor**. 여러 Agent가 팀을 이루고, 그 위에 **Supervisor Agent**가 작업을 라우팅합니다. "이 작업은 리서치 Agent가, 이건 코드 Agent가, 이건 QA Agent가 해라"라고 지시하는 구조예요. CrewAI가 이 방식을 채택하고 있습니다.
>
> **Graph-based**. 상태 기계로 명시적 전이를 정의합니다. 각 단계를 **노드**로, 전이 조건을 **엣지**로 표현해요. 가장 복잡하지만 가장 통제가 강해요. **LangGraph의 철학**입니다.
>
> 오늘 다룰 패턴은 가장 엔터프라이즈에 가까운 **Graph-based**, 즉 LangGraph입니다.

## Slide 11-1 — 4 Agent 패턴의 실전 유스케이스 *(신규 예시)*
**[화면]**
- 4 카드 (패턴 → 실제 적용 예시)
  ```
  ┌─ 01 ReAct ───────────────────────────────────────┐
  │ 유스케이스: 사내 지식 QA Agent                    │
  │  Q: "지난 분기 매출 1위 제품은?"                   │
  │  Thought: 매출 DB를 조회해야 함                    │
  │  Action: query_sales_db(quarter="Q3 2025")       │
  │  Observation: 제품 A, $3.2M                       │
  │  Final: "제품 A (매출 $3.2M)"                     │
  └──────────────────────────────────────────────────┘
  ┌─ 02 Plan-and-Execute ────────────────────────────┐
  │ 유스케이스: 시장 조사 리포트 생성                  │
  │  Plan: [경쟁사 조사, 제품 비교, 차트 생성, 요약]    │
  │  Execute: 각 단계 순차 수행 (장기 실행)            │
  │  → 20분 소요, 10페이지 리포트                      │
  └──────────────────────────────────────────────────┘
  ┌─ 03 Reflexion ───────────────────────────────────┐
  │ 유스케이스: 고난도 코드 생성                       │
  │  1차 답안 → 자가 평가 "테스트 3개 중 1개 실패"    │
  │  → 개선 후 2차 답안 → 재평가 → 통과               │
  │  → HumanEval 벤치마크 +20%p 향상 사례              │
  └──────────────────────────────────────────────────┘
  ┌─ 04 Multi-Agent Supervisor ──────────────────────┐
  │ 유스케이스: 자동 블로그 작성 팀                    │
  │  Supervisor → Researcher Agent (자료 수집)        │
  │             → Writer Agent (초안 작성)            │
  │             → Editor Agent (교정·검수)            │
  │  → CrewAI가 이 방식으로 유명                       │
  └──────────────────────────────────────────────────┘
  ```

**[스크립트]**
> 4가지 패턴을 실제 유스케이스와 매칭해서 보겠습니다. 각각 언제 쓰는 게 맞는지 감을 잡으시면 됩니다.
>
> **ReAct 유스케이스** — 사내 지식 QA Agent예요. "지난 분기 매출 1위 제품은?" 질문에 Thought로 "DB 조회가 필요"라고 판단, Action으로 매출 DB 쿼리, Observation으로 결과 받기, Final로 답변. **짧은 루프, 도구 1~3번 호출**로 끝나는 케이스에 가장 자연스러워요.
>
> **Plan-and-Execute 유스케이스** — 시장 조사 리포트 생성을 예로 들게요. 먼저 계획 단계에서 "경쟁사 조사 → 제품 비교 → 차트 생성 → 요약"으로 step을 나눕니다. 그 다음 각 step을 순차 수행. 20분 걸려서 10페이지 리포트가 나와요. **작업이 길고 단계가 명확할 때** 적합합니다.
>
> **Reflexion 유스케이스** — 고난도 코드 생성에 주로 씁니다. 첫 답안을 쓰고 직접 테스트를 돌려 봅니다. 3개 중 1개가 실패하면 "어디가 문제였는지 반성"하고 다시 씁니다. HumanEval 벤치마크에서 기본 대비 **20%p 향상** 사례가 있어요. **정답이 명확히 검증 가능한 영역**(코드, 수학)에서 강해요.
>
> **Multi-Agent Supervisor 유스케이스** — 블로그 자동 작성 팀이 대표 예시예요. Supervisor Agent가 작업을 배분하고, Researcher가 자료 수집, Writer가 초안, Editor가 교정. 역할 분리로 **각 Agent의 프롬프트가 단순**해지고, 품질이 올라가요. **CrewAI**가 이 방식을 기본 철학으로 채택하고 있어요.
>
> 선택 기준 한 줄 — **단순 조회엔 ReAct, 장기 작업엔 Plan-Execute, 품질 중요하면 Reflexion, 역할 분리가 자연스러우면 Multi-Agent**. 오늘은 가장 기본이 되는 ReAct 스타일(Graph 위에서)을 중심으로 봅니다.

## Slide 11-2 — 언제 Multi-Agent로 넘어가는가 *(신규)*
**[화면]**
- 좌·우·하단 3블록
  ```
  ━━ 단일 Agent로 충분한 경우 ━━━━━━━━━━━━━━━━━━━━━━━━━
  · 도구 5~10개 이내, 한 도메인 내 작업
  · 한 LLM이 모든 도구·정책을 머리에 담아도 깔끔
  · 단일 Loop에 모든 책임을 넣어도 프롬프트 정리 가능
  · 예: 사내 지식 QA, 고객 문의 1차 응대

  ━━ Multi-Agent가 필요해지는 신호 ━━━━━━━━━━━━━━━━━━━━
  · Tool 30개+ → 한 LLM 프롬프트 길이 폭증
  · 역할 분리가 자연스러움 (Researcher · Writer · Editor)
  · 도메인별 다른 모델·정책 (legal · sales · infra)
  · 부서 간 책임 경계 (다른 팀 소유 Agent와 협업)
  · 예: 자동 리포트 생성, 부서 간 워크플로

  ━━ 비용·관측성 함정 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  · Agent N개 → LLM 호출 N배, 잘못 설계 시 N제곱 가능
  · Trace가 Agent 경계를 가로질러야 → OpenTelemetry 필수
  · 호출 루프(A→B→A) 방지를 위한 Hop Count 상한 정책
  ```

**[스크립트]**
> Multi-Agent로 가는 시점을 판단하는 기준입니다. 결론부터 말씀드리면 **단일 Agent로 풀 수 있으면 단일 Agent로 푸세요**. 분리는 비용을 동반합니다.
>
> **단일로 충분한 경우** — 도구가 5~10개 이내이고, 한 도메인 안에서 끝나는 작업이면 단일 Agent가 좋습니다. 한 LLM이 도구와 정책을 모두 머리에 담아도 프롬프트가 깔끔하게 유지됩니다. 사내 지식 QA, 고객 문의 1차 응대 같은 케이스가 여기 해당합니다.
>
> **Multi-Agent로 가야 하는 신호 4가지**.
>
> 첫째, **Tool 30개 이상**. 한 Agent에 도구가 30개를 넘기 시작하면 프롬프트 길이가 폭증하고 정확도가 떨어집니다. 도메인별로 쪼개서 각자 담당 도구만 보게 만드는 게 깨끗합니다.
>
> 둘째, **역할 분리가 자연스러운 작업**. 자료 조사 → 초안 → 교정 같은 흐름이면 Researcher·Writer·Editor 세 Agent로 나누는 게 직관적입니다. 각 Agent의 프롬프트가 단순해집니다.
>
> 셋째, **도메인별 다른 모델·정책**. 법무 영역엔 보수적 정책의 큰 모델, 세일즈엔 빠른 모델, 인프라엔 코드 특화 모델 — 이렇게 다른 모델을 써야 한다면 Multi-Agent 분리가 자연스럽습니다.
>
> 넷째, **부서 간 책임 경계**. 다른 팀이 소유한 Agent와 협업해야 하면 단일 Agent로 합칠 수 없습니다. 이 케이스에서 A2A·ACP 같은 통신 프로토콜이 필요해집니다.
>
> 함정 세 가지도 같이 알아두세요. **Agent가 N개면 LLM 호출이 N배**, 잘못 설계하면 N제곱까지 갑니다. **Trace가 Agent 경계를 넘어가야** 하니 OpenTelemetry 같은 표준 추적이 사실상 필수입니다. **A→B→A 같은 호출 루프 방지**를 위해 Hop Count 상한을 두세요. ReAct의 step budget이 Multi-Agent의 hop budget으로 확장됩니다.

## Slide 11-3 — A2A: Agent-to-Agent Protocol *(신규)*
**[화면]**
- 한 줄 정의: **"opaque Agent들 간 협업의 공통 규약 (Google · LF · 2025-04)"**
- 핵심 개념 4블록
  ```
  ━━ 1. Agent Card (Discovery) ━━━━━━━━━━━━━━━━━━━━━━━━
  · Agent 자체가 JSON 카드를 노출 (capabilities·auth·endpoint)
  · Agent를 "찾을 수 있는 단위"로 만드는 표준
  · Tool Search의 Agent 버전

  ━━ 2. Task lifecycle ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  · 모든 협업은 Task 객체 단위 (id · state · artifacts · history)
  · 상태: submitted → working → input-required → completed
  · 장기 Task에서 진행 상황을 양쪽이 동기화

  ━━ 3. Transport ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  · JSON-RPC 2.0 over HTTP(S) 베이스
  · 동기 request/response · SSE 스트리밍 · Push notification
  · 장시간 작업은 비동기 푸시로 결과 전달

  ━━ 4. Opacity 원칙 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  · 내부 메모리·프롬프트·툴 구현은 공유하지 않음
  · "Black Box를 그대로 두고 협업" → 보안·IP 보호
  · 다른 벤더·다른 프레임워크 Agent와 직접 통신 가능
  ```
- 하단: **2026-04 기준 150+ 조직이 프로덕션 도입**

**[스크립트]**
> **A2A**, 풀네임은 **Agent2Agent Protocol**입니다. **2025년 4월 Google이 공개**했고 곧 Linux Foundation 산하로 이관됐습니다. **2026년 4월 기준 150개 이상의 조직이 프로덕션에서 운영** 중입니다. 더 이상 데모가 아니고 실서비스 표준이에요.
>
> 한 줄로 정의하면 **opaque Agent들이 서로 협업하기 위한 공통 규약**입니다. opaque이라는 단어가 핵심입니다. 다른 팀, 다른 회사가 만든 Agent의 **내부를 모르는 상태에서도 협업하게 만드는 것**이 A2A의 목표입니다.
>
> 핵심 개념 4가지를 봅니다.
>
> **첫째, Agent Card.** 모든 A2A Agent는 JSON 카드를 노출합니다. 자기 capabilities, 인증 방식, 엔드포인트를 적어둡니다. **발견할 수 있는 단위로 Agent를 만든다**는 발상입니다. MCP의 Tool 노출과 비슷한 자리지만, 단위가 Tool이 아니라 Agent입니다.
>
> **둘째, Task lifecycle.** A2A의 모든 협업은 Task라는 객체 위에서 진행됩니다. id, state, artifacts, history를 가지고 있고, 상태는 submitted → working → input-required → completed로 흘러갑니다. 장기 작업에서 양쪽 Agent가 진행 상황을 동기화하는 표준 메커니즘입니다.
>
> **셋째, Transport.** JSON-RPC 2.0 over HTTP(S)가 베이스입니다. 동기 호출, SSE 스트리밍, 비동기 Push notification 셋 다 지원합니다. 장시간 걸리는 Task는 push로 결과를 받습니다.
>
> **넷째, Opacity 원칙.** Agent는 내부 메모리나 프롬프트, 도구 구현을 상대 Agent에 노출하지 않습니다. **블랙박스를 블랙박스인 채로 협업**시키는 것이 A2A의 강점입니다. 보안 측면에서도 IP 보호 측면에서도 중요합니다. 그래서 다른 벤더, 다른 프레임워크의 Agent와도 직접 통신이 가능해집니다.
>
> 정리하면, **MCP가 단일 Agent의 도구 표준이라면, A2A는 Agent 간 협업 표준**입니다. 둘은 같은 층에 있는 게 아니라 **다른 층**입니다. 이 차이가 다음 슬라이드의 3-Layer 스택입니다.

## Slide 11-4 — ACP & 3-Layer 프로토콜 스택 *(신규)*
**[화면]**
- 상단 박스: **"ACP (IBM · 2025) → A2A로 통합 (2026)"**
  - HTTP-native, REST 기반 Agent 통신 프로토콜
  - 비동기·동기 동시 지원, 멀티모달 메시지
  - LF 산하에서 A2A와 합쳐져 단일 표준으로 일원화
- 3-Layer 스택 다이어그램
  ```
  ┌──────────────────────────────────────────────────────┐
  │  Layer 3 — WebMCP                                    │
  │  Agent ↔ 웹 환경 (브라우저·웹 콘텐츠 표준화)         │
  ├──────────────────────────────────────────────────────┤
  │  Layer 2 — A2A (← ACP merged)                        │
  │  Agent ↔ Agent (Task · Card · JSON-RPC)              │
  ├──────────────────────────────────────────────────────┤
  │  Layer 1 — MCP                                       │
  │  Agent ↔ Tool · Resource (단일 Agent의 외부 통합)    │
  └──────────────────────────────────────────────────────┘
  ```
- 하단: **"2026년 컨센서스 — 3층 모두 Agentic AI Foundation 산하"**

**[스크립트]**
> 마지막 한 장입니다. **ACP**(Agent Communication Protocol, IBM)는 A2A와 거의 같은 시기에 등장한 형제 표준이었습니다. HTTP·REST 기반에 비동기 우선이라는 점에서 강점이 있었어요. **그런데 2026년 Linux Foundation 산하에서 A2A에 통합**됐습니다. IBM ACP 팀은 자기 기술과 노하우를 A2A에 기여하고 활성 개발은 종료했습니다. 결과적으로 **Agent 간 통신 표준은 A2A 하나로 일원화**됐습니다. 실무자가 외우셔야 할 핵심 사실입니다.
>
> 그래서 2026년 컨센서스가 된 게 이 그림의 **3-Layer 프로토콜 스택**입니다.
>
> **Layer 1, MCP** — Agent와 Tool·Resource 사이의 표준입니다. 단일 Agent가 외부 도구·데이터에 닿는 층입니다. Chapter 3에서 본 내용입니다.
>
> **Layer 2, A2A** — Agent와 Agent 사이의 표준입니다. ACP가 합쳐졌고요. Multi-Agent 시스템에서 다른 Agent에게 Task를 위임하는 층입니다.
>
> **Layer 3, WebMCP** — Agent와 웹 환경 사이의 신생 표준입니다. 웹 콘텐츠가 LLM Agent에 대응되는 방식을 표준화합니다. **2026년 들어 떠오른 영역**이고, 아직 상위 두 층만큼 성숙하진 않지만 컨센서스 후보로 거론됩니다.
>
> 세 층 모두 **Agentic AI Foundation**(Linux Foundation 산하)이 거버넌스합니다. Anthropic·Google·OpenAI·Microsoft·AWS·Cloudflare 등 146개 회원사가 들어와 있습니다. **한 회사 표준이 아니라 산업 표준**이라는 점이 결정적입니다.
>
> 한 줄 의사결정 — **단일 Agent에 도구를 붙이려면 MCP, 여러 Agent를 협업시키려면 A2A**. 둘 다 모르고는 2026년 Agent 아키텍처를 그릴 수 없습니다.

## Slide 12 — LangChain vs LangGraph
**[화면]**
- 2열 비교 카드
  - LangChain: 빌딩 블록, 선형 Chain
  - LangGraph: 실행 엔진, StateGraph

**[스크립트]**
> 아키텍트에게 가장 혼란스러운 부분이 이거예요. LangChain과 LangGraph. 같은 회사에서 만든 건데 뭐가 다르냐.
>
> 먼저 **LangChain**이 뭔지부터. LangChain은 **LLM 애플리케이션 개발용 빌딩 블록 라이브러리**예요. OpenAI, Anthropic 같은 LLM 래퍼, RAG용 Retriever, 문서 로더, 프롬프트 템플릿, 출력 파서 — 이런 부품들을 모아 놓은 거죠. 이 부품들을 파이프처럼 연결하는 **선형 Chain** 형태로 조립하는 게 기본 사용법입니다.
>
> **LangGraph**는 다른 레이어에 있어요. 이건 **실행 엔진**, **런타임**이에요. 상태 그래프(StateGraph)를 기반으로 복잡한 실행 흐름을 관리합니다. 분기, 루프, 병렬 실행, 사람 승인, 체크포인트, 재개 — 이런 고급 기능들을 1급 시민으로 지원해요.
>
> 관계를 쉽게 말하면 이래요. **LangChain은 부품, LangGraph는 조립대**입니다. LangChain 부품들을 LangGraph 안에서 노드로 쓰는 게 전형적인 조합이에요.
>
> 그럼 어느 쪽을 쓰느냐.
>
> **LangChain만으로 충분한 경우**: 단순 RAG 챗봇처럼 "질문 받기 → 검색 → 프롬프트 → LLM → 응답"의 선형 흐름이면 LangChain의 LCEL(선언적 체인)이면 됩니다. 코드 몇 줄로 끝나요.
>
> **LangGraph가 필요한 경우**: **다단계 + 재시작 + 사람 승인 + 감사 로그**가 조건이 되면 LangGraph입니다. 장시간 실행되는 워크플로, 중간에 사람 개입이 필요한 프로세스, 실패 후 이어서 가야 하는 시스템 — 이런 엔터프라이즈 요구사항은 LangGraph의 영역이에요.
>
> 2026년 현재 GitHub 스타 수에서 LangGraph가 CrewAI를 추월했어요. 엔터프라이즈 채택이 크게 늘고 있습니다.

## Slide 12-1 — Agent vs Workflow · 둘 다 LangGraph로 *(신규)*
**[화면]**
- 비교표

  | | Workflow | Agent |
  |---|---|---|
  | 경로 결정 | 개발자가 사전 정의 (deterministic) | LLM이 매 step 동적 결정 |
  | 예시 | Routing · Parallelization · Orchestrator-Workers · Evaluator-Optimizer | ReAct 루프 · Plan-and-Act |
  | 예측 가능성 | 높음 · 테스트 쉬움 | 낮음 · trace 분석 필수 |
  | 비용·지연 | 낮고 안정 | 높고 변동 |
  | 적합 작업 | 도메인 좁음 · SLA·감사 중요 | 탐색·문제 다양 |
  | LangGraph 표현 | Edge · Conditional Edge로 명시 흐름 | ToolNode + LLM 루프 + Conditional Edge |

- 한 줄: **LangGraph는 Agent 전용이 아님** · 같은 StateGraph 위에서 Workflow와 Agent를 자유롭게 섞을 수 있는 게 차별점

**[스크립트]**
> LangGraph를 "Agent 만드는 라이브러리"로 잘못 알고 있는 경우가 많아요. **LangGraph는 Workflow와 Agent를 같은 그래프 위에서 다 다룰 수 있는 실행 엔진**입니다. 이 차이를 짚고 가야 5 요소를 보는 시야가 달라집니다.
>
> 둘의 차이를 정리하면, **Workflow는 개발자가 경로를 사전 정의**합니다. "검색 → 요약 → 메일 발송" 같은 deterministic 흐름이에요. **Agent는 LLM이 매 step에서 다음 행동을 동적으로 결정**합니다. ReAct 루프가 대표적이죠.
>
> Anthropic이 2024년 12월 "Building Effective Agents" 글에서 정리한 분류가 이미 표준이 됐어요. **Workflow 패턴 네 가지** — Routing(질의 분기), Parallelization(병렬 실행), Orchestrator-Workers(작업 분배), Evaluator-Optimizer(자가 평가) — 와 **Agent 패턴**(LLM이 도구 선택 + 자가 판단)으로 구분합니다.
>
> 선택 기준은 단순해요. **도메인이 좁고 SLA·감사가 중요하면 Workflow**가 안전합니다. 예측 가능, 테스트 쉬움, 비용·지연 안정. **탐색이 필요하고 문제 형태가 다양하면 Agent**가 강합니다. 대신 trace 분석 없이는 디버깅이 어려워요.
>
> LangGraph가 다른 프레임워크와 차별되는 지점은 — **하나의 StateGraph 위에서 두 패턴을 자유롭게 섞을 수 있다**는 점입니다. 사내 지식 RAG는 Workflow 노드들로, 코드 생성 부분은 Agent 루프로 — 같은 State 위에 두 패턴을 묶을 수 있어요. CrewAI는 Agent 중심, n8n은 Workflow 중심인데 LangGraph는 둘을 한 평면에 둡니다.
>
> 다음 장의 5 요소(State·Node·Edge·ToolNode·Checkpointer)는 **Workflow와 Agent 둘 다에 통하는 최소 어휘**라고 보시면 됩니다.

## Slide 13 — LangGraph 5 요소
**[화면]**
- 5 번호 카드: State · Node · Edge · ToolNode · Checkpointer

**[스크립트]**
> LangGraph를 이해하는 핵심 5 요소예요. 이 다섯 개만 잡으면 LangGraph의 70%가 들어옵니다. **Workflow든 Agent든** 이 5개로 표현됩니다.
>
> **1번 State**. Graph 안에서 공유되는 **데이터 컨테이너**예요. Python의 TypedDict로 정의합니다. 대화 이력, 중간 결과, 사용자 식별자 같은 것들을 담아요. 모든 노드가 이 State를 읽고, 업데이트를 반환합니다. 아키텍처 관점에선 **이벤트 소싱의 이벤트 저장소**와 비슷한 역할이에요.
>
> **2번 Node**. 실제 일을 수행하는 함수예요. State를 입력으로 받아서 업데이트된 State(또는 일부 필드만)를 반환합니다. LLM 호출, 도구 실행, 외부 API 호출 모두 노드가 될 수 있어요.
>
> **3번 Edge**. 노드 간 전이를 정의합니다. 단순 연결은 그냥 A → B 그으면 되고, **조건부 전이**가 필요하면 Conditional Edge를 써요. "State의 이 필드 값이 X면 노드 A로, Y면 노드 B로" 같은 로직이죠.
>
> **4번 ToolNode**. LangGraph가 제공하는 **prebuilt 노드**예요. Tool 실행 전용으로 최적화돼 있고, 에러 처리, 타임아웃 같은 것도 내장돼 있습니다. 직접 Tool executor 만들 필요 없이 이걸 쓰시면 돼요.
>
> **5번 Checkpointer**. 이게 **LangGraph의 킬러 기능**이에요. State를 SQLite나 Redis에 **자동 저장**합니다. 프로세스가 죽어도, 사람 승인 때문에 멈췄어도, 일주일 뒤에 재개해도 — **정확히 멈춘 지점부터 이어서 실행**할 수 있어요.
>
> 체크포인터가 없는 Agent 프레임워크에서 장기 실행 워크플로를 만들려면 직접 구현해야 하는데, 이게 만만치 않아요. LangGraph는 이걸 1급으로 지원한다는 게 엔터프라이즈 선호의 이유예요.

## Slide 14 — 기본 Tool-use Agent 루프
**[화면]**
- 다이어그램
  ```
  Agent → (tool_calls?)
          yes → Tools → back to Agent
          no  → END
  ```

**[스크립트]**
> LangGraph로 만들 수 있는 가장 단순한 Agent 구조가 이 그림이에요. **두 노드와 조건부 엣지** 하나로 끝납니다.
>
> 흐름을 따라가 볼게요. 사용자 질문이 들어오면 **Agent 노드**에서 시작해요. 이 노드 안에서 LLM이 호출됩니다. 응답에 tool call이 있는지 확인하는 게 다음 조건부 엣지예요.
>
> 만약 LLM이 "이 도구를 써야겠다"라고 판단했으면(tool_calls=yes) **Tools 노드**로 넘어갑니다. Tools 노드가 실제 함수를 실행하고 결과를 State에 추가해요.
>
> 그 다음 **다시 Agent 노드로 돌아갑니다.** LLM이 도구 결과를 보고 또 판단해요. 더 필요하면 또 도구, 충분하면 최종 응답.
>
> 최종 응답이면(tool_calls=no) END로 빠져나가면서 전체 루프가 종료됩니다.
>
> 이 두 노드 루프가 **Agent의 심장**이에요. 대부분의 Agent 프레임워크가 내부적으로 이 구조를 변주한 것에 불과합니다. 오늘 보여드리는 모든 예시가 이 최소 구조 위에서 확장됩니다.

## Slide 15 — State 설계: 직렬화 가능해야 한다
**[화면]**
- 코드 블록
  ```python
  from typing import Annotated, TypedDict
  from langgraph.graph.message import add_messages

  class AgentState(TypedDict):
      messages: Annotated[list, add_messages]
      user_id: str
      tool_budget: int
      needs_approval: bool
  ```

**[스크립트]**
> State 설계를 실제 코드로 보여드릴게요. LangGraph에서 State는 **TypedDict**로 정의합니다.
>
> 필드들을 하나씩 볼게요.
>
> **messages**. 대화 이력이에요. `Annotated[list, add_messages]`라고 돼 있는 게 독특한데, 이건 "이 필드는 덮어쓰지 말고 **계속 추가**하라"는 지시예요. 노드가 새 메시지를 반환하면 기존 리스트에 append 되는 구조입니다. 이게 없으면 매번 덮어써서 이력이 날아가요.
>
> **user_id**. 누가 이 Agent를 실행 중인지 추적하는 필드예요. 권한 검사, 비용 추적, 감사 로그에 쓰입니다.
>
> **tool_budget**. 이 필드가 정말 중요해요. **남은 tool 호출 횟수**입니다. 예를 들어 10으로 초기화하고, tool 호출할 때마다 1 감소시켜요. 0이 되면 루프를 종료합니다. **무한루프 방지**의 핵심 메커니즘이에요.
>
> **needs_approval**. 승인 필요 플래그예요. 민감 도구를 호출하려 할 때 True로 세팅하고 체크포인트에서 멈추게 합니다.
>
> **중요한 설계 원칙** 하나. State에 들어가는 모든 필드는 **직렬화 가능(JSON-serializable)** 해야 해요. 그래야 Checkpointer가 저장할 수 있거든요. 파일 핸들, DB 커넥션 같은 걸 State에 넣으면 안 됩니다.

## Slide 16 — Tool 설계 6 체크리스트
**[화면]**
- 6개 체크박스
  - 01 Docstring 명확 · 02 인자 스키마 엄격 · 03 Idempotent · 04 타임아웃 · 05 권한 · 06 결과 크기 제한

**[스크립트]**
> Tool을 만들 때마다 이 여섯 가지를 물어보는 습관을 들이세요.
>
> **1번 Docstring이 명확한가.** 앞에서 강조했죠. LLM이 읽는 유일한 문서예요.
>
> **2번 인자 스키마가 엄격한가.** Pydantic이나 JSON Schema로 타입을 **엄격하게** 정의하세요. `date: str`이 아니라 `date: str (format=YYYY-MM-DD)`이어야 해요. LLM이 `date="내일"` 같은 값을 넣어도 검증 단계에서 걸러집니다.
>
> **3번 Idempotent한가.** 같은 호출을 두 번 해도 결과가 같은가예요. 조회형 도구는 대부분 idempotent인데, **실행형 도구는 조심**해야 해요. 이메일 전송, 결제 같은 건 기본적으로 non-idempotent입니다. 이럴 땐 **멱등 키(idempotency key)를 직접 구현**해야 해요. "이 키로 요청 받았으면 이미 실행했으니 다시 안 한다" 같은 로직이요.
>
> **4번 타임아웃이 있는가.** 외부 API 호출하는 도구라면 반드시요. 기본 30초, 핫 경로면 10초 정도가 흔한 설정입니다. 타임아웃 없으면 외부 서비스 지연이 그대로 Agent 응답 시간으로 전파됩니다.
>
> **5번 권한 체크가 있는가.** `user_id` 기반으로 해당 사용자가 이 도구를 쓸 권한이 있는지 확인하세요. LLM이 누군가의 계정을 넘보는 액션을 시도할 수 있어요.
>
> **6번 결과 크기 제한이 있는가.** 이게 간과되기 쉬운 부분이에요. 도구가 10MB짜리 JSON을 돌려주면 다음 LLM 호출의 컨텍스트 윈도우가 터집니다. 최대 반환 크기를 정하고, 넘으면 요약하거나 절단하세요.
>
> 이 여섯 가지가 Tool 하나하나에 다 녹아 있어야 프로덕션 안전성이 확보됩니다.

## Slide 17 — 관측성 설계
**[화면]**
- 2열
  - 필수 항목: 노드별 OTel span, Tool 결과 trace attr, 실패는 State에 기록
  - 도구: Langfuse · LangSmith · OpenTelemetry

**[스크립트]**
> Agent는 **비결정성** 때문에 관측성 없이는 디버깅이 불가능해요. 처음부터 관측성을 빌트인으로 설계해야 합니다.
>
> **필수 항목 세 가지**를 정리했어요.
>
> **첫째, 노드별 OpenTelemetry span**을 남기세요. 각 노드 진입·종료 시점, 실행 시간, 성공·실패 여부를 span으로 기록합니다. 그러면 특정 요청이 어느 노드에서 얼마나 걸렸는지 한눈에 볼 수 있어요.
>
> **둘째, Tool 호출 결과의 요약을 trace attribute로** 붙이세요. 어떤 도구를 호출했는지, 입력은 뭐였고 결과는 뭐였는지를 trace에 남겨야 나중에 "왜 이 답이 나왔지?" 추적이 가능합니다.
>
> **셋째, 실패 메시지는 예외로 던지지 말고 State에 기록하세요.** 이게 흥미로운 패턴이에요. 도구 호출이 실패했을 때 그냥 예외로 던지면 Agent가 멈춥니다. 대신 **에러 메시지를 `state.messages`에 추가**하면 LLM이 다음 반복에서 그 에러를 **읽고 스스로 복구 시도**를 해요. "아, 이 도구가 실패했네. 다른 방법으로 시도해야겠다"라는 판단이 가능해집니다.
>
> 도구는 **Langfuse**, **LangSmith** 같은 것들을 씁니다. OpenTelemetry 표준을 따르면 기존 관측성 스택에 자연스럽게 통합돼요.

## Slide 18 — 프로덕션 7 체크리스트
**[화면]**
- 7 리스트: Step Budget · Tool Timeout·Retry · Observability · HITL · Policy · Evals · Rollback

**[스크립트]**
> Agent를 프로덕션에 올리기 전에 반드시 확인할 일곱 가지예요.
>
> **1번 Step Budget**. 최대 루프 횟수와 최대 토큰 예산. 앞서 이야기한 tool_budget의 연장이에요. 요청당 상한을 둡니다.
>
> **2번 Tool Timeout과 Retry**. 각 도구별로 타임아웃이 설정돼 있는지, 재시도 시 멱등성이 보장되는지 확인하세요.
>
> **3번 Observability**. Trace가 쌓이고 있는지, 토큰·비용이 요청별로 집계되는지, 장애 상황에 알람이 가는지.
>
> **4번 Human-in-the-loop**. 민감 동작은 사람 승인 경로가 있는지, interrupt와 resume이 잘 되는지.
>
> **5번 Policy**. 사용자별 Tool 권한이 적용되는지, PII 스캔이 들어가 있는지.
>
> **6번 Evals**. 이게 특이해요. Agent의 평가는 **응답 문자열**만 보면 안 됩니다. "이 질문에 이런 **도구 호출 시퀀스**로 도달해야 한다"를 함께 평가해야 해요. 예를 들어 "서울 날씨와 환율"이란 질문에 **두 도구를 모두 호출했는가**를 체크하는 거죠. 경로를 보지 않으면 우연히 맞은 답까지 정답으로 카운트돼서 회귀를 놓칩니다.
>
> **7번 Rollback**. 프롬프트 버전이나 모델을 이전으로 되돌릴 수 있는가. 문제가 터졌을 때 1분 안에 되돌릴 수 있어야 해요.
>
> 이 일곱 가지 중 하나라도 "아직"인 게 있다면 프로덕션 배포는 미루세요.
